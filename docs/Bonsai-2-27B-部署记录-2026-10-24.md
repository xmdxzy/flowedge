# Ternary Bonsai 2 27B 本地部署记录（2026-10-24）

> 目的：把本机 27B 级模型从 Q4_K_M（15.65GiB 权重）换成三值 PTQ1_0（5.53GiB），
> 换取「单卡能同时挂视觉 + 长上下文」和接近 2 倍的解码速度。

## 1. 落位

| 项 | 路径 / 值 |

| 根目录 | `D:\AI\bonsai2\` |
| 运行时 | `bin\` — PrismML fork 预编译 `llama-prism-b10787-73bfe6c-bin-win-cuda-12.4-x64.zip`（47 个 exe，含 `ggml-cuda.dll`） |

本机没有编译环节——官方有 Windows CUDA 12.4 预编译包，不需要 cmake/MSVC。

## 2. 为什么不能用 Ollama

g128 组缩放 + Walsh-Hadamard 旋转没合进主线 llama.cpp。stock llama.cpp / Ollama / LM Studio
要么拒载，要么**载进去输出流畅的胡言乱语**（遗留 `Q2_0` 文件是典型触发物）。
官方明确要求 `PrismML-Eng/llama.cpp` fork。

## 4. 实测数据（RTX 3090 24GB，同二进制、同参数）

`llama-bench -p 512 -n 128`：

| 模型 | 权重 | pp512 | tg128 |
|---|---|---|---|
| **Bonsai 2 PTQ1_0** | **5.53 GiB** | **1515.1 tok/s** | **80.44 tok/s** |
| qwen3.8:27b Q4_K_M | 15.65 GiB | 1336.8 tok/s | 43.05 tok/s |

- 解码 **1.87×**，预填充 **1.13×**，权重省 **10.1 GiB**。
- 带视觉塔 + 32K 上下文（`-ctk/-ctv q8_0`）实际占 **+7.07 GB**，同卡还能留 10GB 给桌面/其它。
- 长 prompt（7350 tokens）首次 TTFT 9.2s、prefill 791 tok/s（冷启动口径）。

## 5. 三个必须知道的行为

1. **`max_tokens` 给小了会返回空 content**。模型默认 thinking，思考预算算在输出里。
   512 起步，agent 类任务给 16384；`reasoning_effort` 只认 `low/medium/xhigh`（`high` 报 500）。
2. **单会话要 `-np 1 --cache-ram 24576`**，否则服务端把 cache 分给多个 slot，
   长对话每轮重复 prefill（表现为「越聊越慢」）。
3. **能力分布不均**：数学/编码与 FP16 持平（编码甚至 +0.35），知识推理 −5.7、视觉 −5.2。
   多步 agent（SWE-bench 60.8 vs 80.6、Terminal-Bench 52.8 vs 69.7）只有基线约 3/4。
   所以它是「省显存换上下文与速度」的形态，不是全场景替代。

## 6. 接入引擎（已接通并端到端验证）

## 9. 端口避让与全局切换（2026-10-24 05:10）

**发现一个会咬人的冲突**：最初把 Bonsai 放在 8081，而 `8080/8081` 是引擎自己的端口约定——
`运行\1-启动 FlowEdge.bat` 会依次探测 8080、8081 判断「后端是否已在运行」，
`运行\2-停止 FlowEdge.bat` 会 `for %%P in (8080 8081)` 去停进程。
占着 8081 的后果：① 双击启动脚本直接判定「已在运行」并打开浏览器到 Bonsai 的 WebUI；
② 点「停止」可能把 Bonsai 当引擎杀掉。

**处置**：Bonsai 迁到 **8088**（未被占用），`start-server.bat` 里写死并注释原因；
profile 的 `base_url` 同步改 `http://127.0.0.1:8088`。

**全局默认也切了**（改 `运行\1-启动 FlowEdge.bat`，原件备份 `.tmp/1-启动 FlowEdge.bat.bak-20261024`）：

```bat
set "OLLAMA_BASE_URL=http://127.0.0.1:8088"
set "OLLAMA_MODEL=ternary-bonsai-2-27b"
```

- 位置在 `set "PORT=8080"` 之后，`setlocal` 里，只影响本脚本拉起的引擎。
- **下次用该脚本启动引擎才生效**；当前跑着的引擎没重启（重启会连带停它托管的 ComfyUI/TTS）。
- 回退方式：删掉这两行 → 回到默认 `localhost:11434`。

**老工作流也切了**：#73 `station-selftest-llm` 的 llm 节点加 `llm_profile=bonsai-2-27b`，
`model` 改 `ternary-bonsai-2-27b`（原件备份 `.tmp/wf73-backup.json`）。

**验证**（改端口与切节点之后重跑，两次都 success，且 `/api/ps` 仍为空）：

```
run 139 (wf 123) llm: 三元量化用更少比特表示权重（通常约 1–2 bit/参数），因此相比 4bit 量化能显著降低模型权重的显存占用。
run 140 (wf 73)  llm: 阳光入大气后，短波蓝光散射更强，使天空显得蓝色。
```

**纠正一处此前的错误结论**：`/api/llm/profiles` 的 `default` 字段前端只用于
`LLMProfilesEditor` 的界面显示（`frontend/src/components/LLMProfilesEditor.tsx:24`），
**不会**给新建的 llm 节点自动填 profile。新节点默认 `llm_profile` 为空 ⇒ 走全局端点。
所以「新节点自动用 Bonsai」是错的，真正兜底靠第 9 节那两行环境变量。

## 11. 上下文容量事故与修正（2026-10-24 07:00）

WorkBuddy 切到 Bonsai 后报：

```
400 request (39373 tokens) exceeds the available context size (32768 tokens)
```

**根因不是接入配置，是我把 `-c` 开小了**。WorkBuddy 单请求自带系统提示词+历史就近 4 万 token，
32K/64K 都装不下。查 GGUF 元数据（`scripts/gguf_meta.py`，纯标准库解析头部 KV）：

```
general.architecture = qwen35     （Qwen3.5-VL 混合架构：64 层，16 层全注意力 + 48 层 SSM）
qwen35.context_length = 262144    ← 原生就是 256K，之前 32K 是人为砍的
qwen35.attention.head_count = 24 / head_count_kv = 4（GQA，KV 很省）
qwen35.rope.dimension_sections = [11,11,10,0]（mrope）
```

结论：**原生 256K 之内不需要 YaRN**（freq_base 1e7），直接开满即可。

### 11.1 实测（RTX 3090 24GB，`-ctk/-ctv q8_0`）

| 配置 | 显存占用 | 备注 |
|---|---|---|
| `-c 32768` | 9.15 GB | 被 39K 请求打爆 |
| `-c 65536` | 10.22 GB | 增量 ≈ 1.07GB/32K ⇒ **约 34 KB/token** |
| `-c 262144` | **16.9 GB**（余 7.4GB） | 现役配置 |

长请求实测（`scripts/longctx_test.py`）：

| 场景 | prompt_tokens | 耗时 | prefill |
|---|---|---|---|
| 冷请求 | 26,904 | 23.1s | 1163 tok/s |
| **同前缀 + 短尾巴** | 26,915 | **3.0s** | **9081 tok/s** |

⇒ slot 前缀缓存生效（8×）。WorkBuddy 每轮带相同系统提示词，只有第一轮付全量 prefill
（4 万 token 约 34s），之后按增量算。

### 11.2 改了什么

1. **`start-server.bat` 上下文自动化**：
   `set "CTX=auto"` → 用 `nvidia-smi` 读空闲显存，按 34KB/token 反推能开多大，
   向下取整到 32768 的倍数，**封顶原生 262144**，下限 8192；仍可手动覆盖
   `start-server.bat <model> <ctx>`。硬性越界（>262144）不自动加 YaRN，宁可封顶。
2. **服务端现役 `-c 262144`**，`/props` 回读 `n_ctx = 262144` 已验证。
3. **客户端 `~/.workbuddy/models.json`**：`maxInputTokens` 30000 → **245760**
   （256K 减去输出预留 16384）。原文件备份 `models.json.bak-20261024-ctx`。
   这也是一处逻辑错配：服务端 32K 的同时客户端又限 30K，两边都堵。

**待确认**：`qwen3.8:27b` 条目仍在 `models.json` 里，但权重已按第 7 节删除 → 悬空条目。
当前会话若正引用它，移除后可能影响会话恢复，等张越拍板再删。
