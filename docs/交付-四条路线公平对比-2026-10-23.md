# 四条路线公平对比（最终结果）

> 日期：2026-10-23 · 资产 `.tmp/pipeline-bench/` · 两轮重复 · 全部数字为实测
> 前置文档：`交付-多流程基线四条路线实测-2026-10-23.md`（首轮）、`交付-WorkBuddy可编程性排查-2026-10-23.md`（② 的通道结论）

## 一、最终结论

| # | 路线 | 轮1 | 轮2 | 中位数 | 用例 | 判定 |
|---|---|---|---|---|---|---|
| ④ | **WorkBuddy 子 agent（无引擎）** | 114.6s | 180.4s | **147.5s** | 68/68 ×2 | 通过，最快 |
| ③ | **单 DSH（无引擎）** | 180.1s | 390.7s | **285.4s** | 68/68 ×2 | 通过 |
| ①′ | **FlowEdge 编排 + DSH（4 路 + 条件短路）** | 471.3s | 727.4s | **599.4s** | 68/68 ×2 | 通过，最慢 |
| ② | FlowEdge 编排 + WorkBuddy | — | — | — | — | **N/A：产品缺可编排入口** |

**排序：④ > ③ > ①′（④ 比 ①′ 快 4.1 倍）**

三条能跑的路线**结果完全一致**（都是 68/68、`cheated=false`），差别只在耗时与可审计性。

## 二、为什么"拆成 4 路并行"反而更慢

关键不是并行效率，而是**固定成本被复制**：

| 指标 | ①′ 轮1 | ①′ 轮2 |
|---|---|---|
| 四个 agent 耗时 | 192 / 259 / 216 / 249s | 263 / 369 / 352 / 205s |
| agent 耗时之和 | 916s | 1189s |
| 实际墙钟（配额 2，分两批） | 471.3s | 727.4s |
| **并行效率（之和 ÷ 墙钟）** | **1.94×** | **1.63×** |

并行本身是有效的（1.6–1.9×，配额 2 的理论上限就是 2×）。**问题在分子**：
每个 agent 都要独立做一遍「读 CONTRACT → 通读自己模块的测试 → 探索实现 → 跑测试 → 改 → 复跑」，
这套固定成本单次约 60–100s。拆 4 份就重复 4 次，多花 240–400s，
超过了并行省下的时间（相比一次完整跑，节省约 300–500s）。

净结果：① 的总墙钟比其他两条路线多 2–4 倍。

**这就是"编排不总是赢"的定量解释**，不是玄学：
当子任务的固定成本 × 份数 > 并行省下的时间时，拆并行就是负优化。

## 三、什么条件下编排才会赢

同一张图，本文档之前测过一次 **配额 4 + 上游较慢** 的情形：

| 配置 | 四路 agent | 墙钟 | 并行效率 |
|---|---|---|---|
| 配额 4（19:51 那次） | 205 / 237 / 241 / 341s | **346.3s** | 2.96× |
| 配额 2（本次两轮） | 192–369s | 471–727s | 1.63–1.94× |

配额 4 时 346.3s，比当时同一时段的单跑（827.4s）快 2.4 倍。**同一张图，结论可以完全相反。**

所以"编排好不好"这个问题本身没有答案，只有「在这个配额、这个子任务粒度、这个上游速度下」的答案：

- 子任务粒度大（每路 ≥5 分钟）→ 拆分划算
- 子任务粒度小（每路 1–3 分钟）→ 单 agent 划算
- 并发配额高 → 拆分划算

## 四、路线 ② 为什么是 N/A（不是"没测"）

完整排查在 `交付-WorkBuddy可编程性排查-2026-10-23.md`，这里只给结论：

| 通道 | 结果 |
|---|---|
| `codebuddy -p` | 无产出（exit 0、stdout/stderr 全空） |
| `codebuddy --serve` + Bearer 认证 | **服务可用、能提交任务（202）、能建会话，但没有 worker**：消息只更新会话标题，`/history` 的 `requests: []`，零 `agent_message_chunk` |
| `codebuddy --acp`（stdio） | `initialize` 无回包 |
| ACP over HTTP（serve 实例） | 握手全通（`initialize`/`session/new`/`session/prompt` 均 200，`bypassPermissions` 生效），但 agent 不推理 |
| 桌面端 worker（8895） | **能真干活**（出现真实 `tool_call`），但 `session/new` 不新建会话，sessionId 恒等于用户当前活动会话 → 跑评测会污染用户 cwd 与会话历史，已停用 |

**缺的是一个"能为外部调用者新建独立会话、并带 worker"的执行入口**。这不是配置问题，FlowEdge 侧无法绕过。

## 五、公平性说明

| 项 | 状态 |
|---|---|
| 同一任务 | 同一份 fixture（9 项待办 / 68 用例 / 基线 27/68），四轮都用同一判分器 |
| 同批时段 | ①′ 轮1 21:13、③ 轮1 21:24、④ 轮1 21:01；①′ 轮2 21:37、③ 轮2 21:44、④ 轮2 21:44 —— 两轮各自紧邻 |
| 执行体信息对等 | ①③ 拿到的是"只写了规格的陌生代码库"；④ 用**干净上下文的子 agent**（prompt 与 ③ 的信息量一致，且明确禁止读上级目录的判分器） |
| 作弊检测 | 四条全部 `cheated=false`，`tests/` 6 个文件 sha256 未变 |
| **已知偏差** | ① 的并发被压到 2（原因见 §六）。配额 4 时它有 346.3s 的记录，**比本次 471–727s 快得多**。所以本文的 ① 成绩是"受限配置下的成绩"，不代表它的上限 |
| 样本量 | 每条 2 轮。上游单次耗时波动 4.6 倍（③ 从 180s 到 827s），所以绝对值只能看中位数与并行效率，不宜逐秒比较 |

## 六、本轮新撞到的环境限制

**DSH 并发写 `~/.dsh/sessions` 会被 sandbox 拒绝**（`file-write` 被拒 → DSH exit 1 → agent_task 判失败）。

- 单并发正常；4 并发时 5 个节点挂了 2 个。
- 根因：评测脚本由工具调用启动，整条进程树（脚本 → 引擎 → DSH）都在沙箱内，DSH 写自己的会话日志被拦。
- 规避：把 `agent_concurrency` 降到 2（也是引擎默认值），两轮 8 个 agent 全部成功。
- 彻底解法：用**用户自己起的 8080 引擎**跑图（不在工具沙箱内）。但那需要先双击 `运行\3-应用更新并重启.bat` 把引擎升到新版（含 `command` 节点），这是下一步。
