## ① 一句话结论

这一年多镜一致性的增量**几乎全在训练-free 的推理期改造与 LLM 编排层**。能零成本落到 FE 的只有两类：

1. **把「首镜锚帧 / 上一镜末帧」当参考图回填**（STAGE 的 start-end frame pair、CineWeaver 的 anchor memory、MVAgent 的 continuity memory 指向同一件事）；
2. **参考图按「当前镜所需元素」筛选，而不是「历史出现过的都塞」**（Complementary Retrieval + VMem-Bench 的反证——后者实测出「记忆越多，精度越差」）。

两者都不需要训练、不需要改 DiT、不需要新权重，只改 `shotlist` 的参考图装配与 `consistency_plan.go` 的审计码。**为什么值得立即吸收**：FE 已知的生成侧光比漂移（`plan.color_shift`）是 plan 门管不到的缺口（`docs/AGENTS.md` 记录过「plan 两镜都写冷色、生成一暖一冷」）；端帧回填是用**真实生成结果**而非文字锁约束下一镜的唯一手段。而「记忆越多越好」已被 VMem-Bench 用 30 个因果故事、2824 个片段证伪——FE 现在 `require_ref_images_every_segment=true` 正踩在这个反证上。

## ⑥ 没验证的部分（不许省）

1. **本调研没跑过任何一条论文代码**。结论全部来自摘要、LaTeX 方法节与消融表，属**二手（论文自述）**；任何「提升 X%」都是**论文自报**。
2. **几乎所有论文都没报显存**。表中「显存未取到」不是没查，是摘要与方法节里确实没有。**不要**拿 CineWeaver 的 832×480 或 KeyID 的 121 帧去反推 FE 的 24GB 能否跑——那是跨参数外推，§0.3 明令禁止。
3. **开源状态只核到摘要/项目页字面**。`cineweaver.github.io` 实际 fetch 过（HTTP 200），Code 按钮写 `Code _soon_` ⇒ 截至 2026-10-31 **未放出**。其余「未在摘要出现」只是我没在摘要里看到链接，**不代表仓库不存在**。
4. **`Shot.RefImages` 只读到类型与注释**（`*bool`）。F1 的「扩成可寻址集合」是**改造建议**，非现有能力；改造前需确认 `ref_images` 装配路径（`comfy_media.go:589-610` 是 node 级 `ref_image_%d` 映射）。
5. **「参考图最多 9 张」是两处独立约束**（`filmgates.go:61` 的 `max_ref_images` 与 `comfy_media.go:589` 的硬校验）。当前值一致，但**改一处不改另一处会静默漏检**——未验证测试是否钉住一致性。
