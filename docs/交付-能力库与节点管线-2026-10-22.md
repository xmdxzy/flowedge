# 交付：能力库 + 节点处理管线（2026-10-22 04:20–06:00）

这轮回答的是一个结构问题：**三类卡不能同时存在**。答案是它们本来就不是"三选一"，
而是**一个节点的三个处理阶段**。同时把选择方式从"三个平铺 tab"升级成"三个库"。

---

## 一、核心改动：一张卡 → 三段管线

一个节点干的事其实是三步，以前只能挂一张卡，等于逼用户把三步拆成三个节点：

```
上游文本 → [输入处理] → [本体：类型 + 角色] → [输出处理] → 下游
```

数据模型：`node.data.bindings: [{kind, id, stage, order}]`

| stage | 语义 | 上限 | 执行位置 |
|---|---|---|---|
| `input` | 上游文本先过它：翻译 / 清洗 / 抽字段 | 多张，按 order 串行 | `execLLMNode` 取到上游文本后、拼提示词前；`execText2ImageNode` 翻译与 scene_lock 之前 |
| `body` | 换掉角色设定（agent/skill） | **1 张**（两个 system prompt 会打架） | 替换节点 prompt；agent 还带默认工具 |
| `output` | 本体产出再整形 | 多张，串行 | `applyOutputStage`，只改 `text` 字段 |
| `replace` | 整个节点换成一条工作流 | **1 张**，仅 workflow | `executeNode` 拦截，走 `executeInnerWorkflow`，有嵌套深度保护 |

规则：`replace` 与 `body` 互斥（本体都被替换了，角色没有落点）；
`replace` 与 `input`/`output` **可以共存**（先进输入处理 → 跑工作流 → 再处理产出）。

**旧数据兼容**：`binding`（单选）读时自动迁移（agent/skill→body，workflow→replace），不写回，
不会在你保存时偷偷改数据。

**成本可见**：面板实时显示"会调用 N 次模型"。每张 agent/skill 卡都是一次 LLM 调用，
不显示数字用户会在输入段堆五张卡，然后疑惑为什么一键运行半分钟还没出图。

---

## 二、能力库：三个库 + 大类 + 标签 + 搜索

| 库 | 分类维度 | 现状 |
|---|---|---|
| 智能体库 | 编剧 / 视觉 / 研究 | 4 张内置 |
| 技能库 | 翻译 / 结构化 / 压缩 / 拆分 / 质检 | 5 张内置 |
| 工作流库 | 轻量（≤5 节点）/ 完整流水线（>5） | 从你的工作流自动派生（当前 12 条） |

每张卡带 `category`（大类）与 `tags`（细类），库视图支持：三库切换 + 大类 chip + 搜索（名称/用途/标签）。
选卡是弹层（660px 两列），不是在 288px 面板里挤——选卡是"浏览比较"的动作。

---

## 三、节点外观：多徽章 + 接线

- **多徽章**：横排在节点**上方**，最多 3 枚，其余折成 `+N`；顺序 = 执行顺序（输入→本体→输出→替换）；
  形状仍是 agent=圆 / skill=六边形 / workflow=三层；整条 `pointer-events:none`，不挡拖拽与连线。
- **接线**：面板顶部显示 `← 上游节点(type)` / `→ 下游节点(type)`，**点一下直接选中那个节点**，
  不用回画布上找。这就是"谁接入我、我接出到谁"。

## 五点五、第二轮补强（05:00–06:00）

第一轮只把三段接在 LLM 与文生图上，等于"四段管线"只对一两个节点成立。这一轮补齐：

| 改动 | 为什么 |
|---|---|
| **输入段全局化**：`applyInputStage` 放进 `executeNode`，所有节点生效 | 20 个执行体各写一遍必然漏，新加节点默认没有；预处理只关心"文本进节点前长什么样" |
| **输出段全局化**：`applyOutputStage` 对称放在派发后 | 否则"输出处理"只对 AI 推理节点成立，UI 会撒谎 |
| 输入段**不改原 upstream map** | 同层并行时上游 map 可能还被别的节点读着，就地改是只在并发下偶发的 bug |
| 任务书输出**处理链**（`SpecModule.Cards`） | 任务书是给智能体读的；不写"这一步是短剧导演在拆镜"，智能体会绕过卡片直接调模型 |
| 工作流卡名字反查（`SetWorkflowNameResolver`） | 任务书里写 `workflow 12` 没人读得懂 |
| **卡片可编辑**：`PUT /api/cards` + `CardEditor`（新建/改提示词/删） | 不能建卡的"库"是假库。删内置卡要能真删——用 `hidden` 列表记住，否则下次加载又冒出来 |
| **文生图权重可选**：节点级 `ckpt` 覆盖（`GenerateImageWithCkpt`） | "每个节点选自己的模型"要落到出图上；快/质两条线并存 |
| **视觉模型改下拉** | 原来自由文本框 + placeholder `qwen2.5vl:7b`，等于让用户猜 |
| **绑定保存校验**：工作流卡不存在 / 指向自己 / 本体多张 → 400 | 贴错卡要到运行到那一节点才炸，而且是"跑一半才炸" |
| **节点下方显示接线**：`← 上游 · → 下游`（名字来自 `/api/modules`） | 用户要求"知道每个节点接入的是谁、接出的是谁"，面板里有点击跳转，画布上也要看得见 |
| 本体段只在 AI 推理节点可用（面板置灰 + 说明） | 其他节点没有"角色"可替换，宁可说清楚也不静默无效 |

**自捉 bug（第二枚）**：工作流库的分类筛选里，item 的 `cat` 恒为空串，
选中"轻量（≤5 节点）"会一条都筛不出来。已按节点数分桶，与后端 `categories` 口径对齐。

## 五点六、第三轮补强（06:00–07:00）

| 改动 | 为什么 |
|---|---|
| **卡片执行留痕**：`output._cards = [{stage,kind,id,ok,error}]`，面板显示"上次运行的卡片 ✓/✕" | 没有它卡片是黑盒：贴了"中译英"跑完只看到英文，不知道是卡翻的还是模型本来就会；某张卡报错会被静默降级吞掉 |
| **保存期第三条硬拦**：`sub_workflow` / `loop` 节点再贴工作流卡 → 400 `binding_conflict` | 两套 workflow_id 打架，卡会覆盖节点自带那条；用户以为是"再套一层"，实际是"换掉" |
| **任务书告警**：贴了工作流卡的节点，产物以工作流为准，可能与声明端口不一致 | 智能体照着任务书接下游，不写这条会接错 |
| **节点下方接线**：`← 上游 · → 下游`（名字取自 `/api/modules`，前端不手抄清单） | 面板里能点跳转，画布上也要一眼看见"谁接入我" |
| **视觉模型改下拉**：列本机真实模型 + 体积，标注只有 VL 模型能看图 | 原来 placeholder 写 `qwen2.5vl:7b`，等于让用户猜 |
| **库默认页签按阶段选**：输入/输出→技能库，本体→智能体库，替换→工作流库 | 少一次切页 |
| 卡片显示标签（`#分镜 #英文`） | 让"细类"真的可见，而不只是能搜 |
| 本体卡接管时，任务预设旁标注"不生效" | 两处都能改提示词，不说清楚会互相覆盖 |

## 五点七、第四轮收尾（07:00–07:40）

| 改动 | 为什么 |
|---|---|
| **面板显示显存侧别**：`语言侧 · 重任务（与其他重任务互斥，切侧约 180 秒）` | 编排效率的关键信息，以前只存在于代码注释里。数据来自 `/api/modules` 的 `side`/`heavy` |
| 卡片"复制一份" | 微调内置卡的正确姿势；直接改内置卡会让"原厂设定 vs 我改过"分不清 |
| 任务书不再原样贴 `bindings` JSON | 处理链段落已经展开成人话，参数区再贴一遍是重复噪音 |
| 任务书告警补充 | 贴工作流卡的节点，产物以工作流为准；智能体照着接下游才不会接错 |

**一个查证比修改更重要的例子**：`text2video` 在 NodeSpecs 里标的是 `language`（不是 diffusion）。
第一反应是"标错了，H3 明明是扩散模型"，但 `vram.go:63-72` 写明了口径——
按"该节点起飞时**第一个**进入的侧别"归类，这样它能和同层 LLM 凑一批、只换一次侧；
执行器内部到第 429 行才 `enterSide(sideDiffusion)`，且 `TestNodeSideMappingRegression`
会用源码扫描盯住这个对应关系。**结论是它没标错，是我差点改坏它。**

**美术上的自我修正**：多徽章从「最多 3 枚」改成「最多 2 枚 + N」。
3 枚 × 96px 会把 180px 的节点撑到 300px 宽，相邻节点的徽章会叠在一起——
"看得见"不等于"看得清"。接线摘要也加了 `right:0` 约束在节点宽度内。

## 六、未做 / 已知缺口

1. ~~`output` 段只对文本产出生效~~ → **已补（2026-10-22 12:00）**：媒体卡走视觉模型。
   以前"做不到"的真实原因不是缺能力，是我把输出段的契约定成「只改 `text` 字段」，
   而图节点产物里根本没有 `text`，这条路径一次都没跑过。补法见下：
   - `SkillCard.Media`（目前 `image`），内置两张：**画面审片**（打分 + 可执行改法）、**图转画面描述**（反推英文提示词）
   - `runMediaStage`：产出含 `image`/`images` 时调 `VisionChat`，结论写 `review`；节点原本没有 `text` 就补上，下游质检门能直接吃
   - 调用前 `enterLanguageSide(model)`：VL 在语言侧，换侧代价约一分钟起 → 所以**可选、不默认**
   - 没有 VL 模型时只记 `_cards` 失败，出图结果保留（不能因为审片挂掉把整步判死）
   - 前端：媒体卡标「［看图］」，图节点的输出段不再置灰，改为提示"只有看图卡生效"
2. **`input` 段目前接在两个节点上**（LLM、文生图）。其余节点（asr/vision/tts…）还没接，属于下一批。
3. **文生图的权重仍不能在节点里选**，只显示当前 ckpt（切换要进 配置·模型）。要做成下拉需要 bundle 选择写进 data 并在执行期覆盖，属于结构性改动。
4. **工作流卡不做端口校验**（把一个 image 输出节点换成 text 输出的流水线，保存期不拦，任务书会标不匹配）。
5. **美术仍未做像素级验证**（截图通道受限）。多徽章的排布是按坐标算的，没有肉眼确认过。
6. **外部接入方（WorkBuddy / dsh 等 MCP 客户端）没有在节点上标出**——现在显示的是"节点级上下游"，
   不是"外部谁在调这条工作流"。要做需要工作流级元信息（触发器/客户端身份），这一轮没做。
