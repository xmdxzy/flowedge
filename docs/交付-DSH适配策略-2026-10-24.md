# DSH 适配策略：FE 能否直接调用 DSH？

> 日期：2026-10-24 · 资产 `.tmp/agent-orch-bench/` · 全部数字为实测

## 一、结论

**能，而且早就能了**——之前几轮的 943.1s / 1039.1s / 73 条全绿，都是 FE 的 `agent_task` 直接调 DSH 跑出来的。

但"能调"和"调得好"之间差一层适配。这一轮把那层补齐了，并实测出两个之前没暴露的并发缺陷。

| 项 | 适配前 | 适配后 |
|---|---|---|
| 单次调用 | 17–180s（正常） | 15–17s |
| **4 路并发** | 受工具沙箱限制，被迫降到 2 | **4 路全通**（实测各 15.0–16.8s） |
| 无响应 | 引擎侧 900s 超时，dsh 子进程可能挂着不退 | 硬超时 + `taskkill /T /F` 杀整棵进程树 |
| 429 / 首包超时 | 直接失败 | 指数退避重试（业务错误不重试） |
| 产出 | 纯文本，只能用 chars / contains 判断 | 软契约 `RESULT {...}` → 结构化 meta，解析不到就退化按退出码 |
| 并发留痕 | 无 | 每次调用落 `.adapter/<pid>-<ms>.json` |
| 长 prompt | argv 超 32767 会爆 | 超 6000 字符自动落文件，改传"读这个文件" |

## 二、为什么 FE 能直接调 DSH（而调不动 WorkBuddy）

DSH 具备那三件套，WorkBuddy 不具备：

```bash
dsh headless --patch dsh-model.yml "<prompt>"   # prompt 从 argv 进
                                                # 结果到 stdout
                                                # 退出码表示成败
```

WorkBuddy 的 `-p` 有参数但没产物（`dist/` 里只有 `codebuddy-lite-wb.mjs`，缺 headless bundle），
所以它只能人机协作。这件事的完整证据在 `交付-WorkBuddy可编程性排查-2026-10-23.md`。

## 三、适配器做了什么（`dsh_adapter.py`）

原包装 `dsh_agent.py` 只有 69 行：读密钥、`cmd /c dsh headless`、透传 stdout。够跑通，但编排里跑多了会暴露六个问题。适配器逐个补：

### 1. 硬超时 + 杀进程树

`dsh` 在 Windows 上是 `.cmd` 包着 node。只 `proc.kill()` 会留下 node 子进程继续写会话文件，下次调用撞锁。

```python
proc = subprocess.Popen(cmd, ...)
try:
    out, err = proc.communicate(timeout=args.timeout)
except subprocess.TimeoutExpired:
    kill_tree(proc.pid)          # taskkill /T /F
```

### 2. 分层重试（可重试 vs 别浪费时间）

```
可重试：429 / rate limit / timeout / 502-504 / NO_ADAPTER / 空产出
不可重试：session does not exist / unknown option / invalid argument
          / not found / cannot find module / permission denied
```

**这条是实测踩出来的**：第一版把 `--session-id` 指到一个不存在的会话，报错信息里没有 429 之类关键词，
但因为"产出为空"被判成可重试，白跑了一遍 69 秒。现在配置类错误优先匹配，直接放弃。

### 3. `--session-id` 的真实语义

```
dsh: session "fe-13cb8112c7c5" does not exist; omit --session-id to start a new Session
```

**它是「恢复会话」，不是「新建会话」**。所以适配器默认**不传**这个参数——让 dsh 自己新建，
并发时各进程天然各用各的会话目录。要复用上下文时才显式指定。

### 4. 软契约 `RESULT`

prompt 末尾追加：

```
收尾格式（务必遵守，编排器要靠它判定成败）：最后单独一行给出
RESULT {"ok": true, "summary": "...", "files": ["..."]}
```

适配器的解析是**宽容**的：`RESULT {...}` / `RESULT: {...}` / 大小写差异都认，多个匹配取最后一个；
**解析不到就退化成"退出码为 0 即 ok"**——不能因为 agent 没按格式写字就把它判成失败。

实测：短任务（"写一个文件"）agent 通常只给自然语言确认，不给 JSON；
长任务（exprkit 那种）更可能遵守。**所以契约是增强，不是门槛。**

### 5. 长 prompt 落文件

Windows 命令行总长 32767。超过 6000 字符就把 prompt 写到 `<workdir>/.adapter_prompt.md`，
改成"读这个文件然后执行"。

### 6. 并发留痕不撞名

第一版用 `auto-<HHMMSS>.json` 命名，四路并发同一秒内落盘 → **4 个 meta 只剩 1 个**。
改成 `auto-<pid>-<毫秒取模>` 后 `meta_count: 4`。

这个 bug 只有真并发才会暴露，单次测永远看不到。

## 四、并发实测（4 路）

图 `#125「并发验证｜4 路 DSH（适配器版）」`，四个 agent 各写一个文件，`agent_concurrency=4`：

| 节点 | 状态 | 耗时 | 产物 |
|---|---|---|---|
| a1 | success | 16.8s | `f1.txt` = `alpha` |
| a2 | success | 16.7s | `f2.txt` = `bravo` |
| a3 | success | 16.2s | `f3.txt` = `charlie` |
| a4 | success | 16.7s | `f4.txt` = `delta` |

```
all_files_ok: true
meta_count:   4          ← 修撞名之前是 1
attempts:     1,1,1,1    ← 零重试
elapsed_s:    15.0–15.4  ← meta 里记的单次耗时
```

**关键**：`8080` 是用户自己起的引擎，**不在工具沙箱内**，所以 4 路并发写 `~/.dsh/sessions` 不再被拒。
之前所有 FE+DSH 实验被迫用 `agent_concurrency=2`，纯粹是因为评测脚本由工具调用启动、
整条进程树（脚本→引擎→DSH）都在沙箱里。**用主引擎跑就没有这个限制。**

## 五、怎么用

`运行\data\agents.json` 里的 `dsh` 条目不变：

```json
{
  "id": "dsh",
  "command": "...\\python.exe",
  "args": ["...\\agent-orch-bench\\dsh_agent.py", "{{prompt}}"],
  "timeout_sec": 900
}
```

`dsh_agent.py` **已替换为适配器**（每次调用重新读脚本，不需要重启引擎）。默认参数即 `--timeout 900 --retries 2`。

手工调用：

```bash
python dsh_agent.py "任务描述"
python dsh_agent.py --prompt-file p.txt --timeout 1200 --retries 3 --workdir W
python dsh_agent.py "..." --no-result-spec        # 不要结果行要求
python dsh_agent.py "..." --session-id <已有id>    # 复用上下文
```

退出码：`0` 成功 / `2` 空 prompt / `3` 密钥或 dsh 缺失 / `4` 重试后仍失败 / `5` 超时。

meta 落在 `<workdir>/.adapter/*.json`，字段：

```json
{"ok":true,"exit":0,"timed_out":false,"attempts":1,"elapsed_s":15.2,
 "attempt_history":[{"attempt":1,"ok":true,"exit":0,"timed_out":false,
                     "elapsed_s":15.2,"stdout_chars":1234,"stderr_tail":"..."}],
 "session_id":null,"model":"(from patch)","patch":"...dsh-model.yml",
 "result_line":{...},"had_result_line":false}
```

## 七、还没解决的（诚实清单）

| 项 | 现状 | 影响 |
|---|---|---|
| RESULT 行遵守率 | 短任务基本不遵守，长任务较可能遵守 | 有 meta 兜底，不影响判分 |
| dsh 冷启动 | 15–90s 不等（免费池首包波动） | 分段编排时每段都要付一次，这是它慢的主因 |
| 模型通道 | opencode-go 免费池，会 429 / 60s 超时 | 已重试兜底，但会拉长墙钟 |
| 会话上下文 | 默认每次新会话（不继承上一段） | 这是"分段不如一把梭"的根因之一 |
| 沙箱 | 用工具调用起的引擎会连带限制 agent | **用主引擎（8080）跑即可绕开** |
