# 视频链路性能与队列卫生（2026-10-26 实测）

> 结论先行：这台 3090 的**算力早已占满（GPU 利用率 100%）**，能提的不是"找闲置算力"，
> 而是把白烧的 GPU 秒收回来。按实测，白烧来自两处：**权重的部分加载（换页）** 与
> **中止不生效（幽灵任务 + 排队）**。前者 5–27 倍，后者每轮 15–21 分钟。

## 1. 现场数字（全部可复算）

统计口径：`运行/data/flowedge.db` 的 `workflow_runs` / `run_events`。

| 观测 | 数值 | 来源 |
|---|---|---|
| film 运行（10-25 20:00 起 13 小时） | 21 次：14 成功 / 6 失败 / 1 超时 | `workflow_runs` |
| 整片耗时 | 最短 2.9 min，**平均 11.3 min**，最长 20.5 min | 同上 |
| 同参数（608×352 / 56 帧 / 12 步）单镜 | 84s / 129s / 167s / 190s / 322s / 352s / 509s / **2701s** | `shot_progress.data.elapsed_ms` |
| 健康基准 | 1.2 秒/帧（56 帧 ≈ 67s） | `shotSecPerFrame` |
| 显存前瞻（run 226） | 空闲 23218MB < 模型 20480 + 预留 4096 → **差 1358MB** | `engine.log` |

## 2. 根因

### 2.1 `--reserve-vram 4` 在 24GB 卡上是算术不可满足

ComfyUI 全量加载的判据是「模型 + `EXTRA_RESERVED_VRAM`」同时空闲（`model_management.py:944`）：

```
20480MB(H3) + 4096MB(预留) = 24576MB = 整张卡
桌面基线 ~1.3GB ⇒ 永远差 1.3GB ⇒ 每次退化成「部分加载」：权重留内存、按步换进显存
```

表现就是同一镜 87s → 2269s（27 倍）。修法：`运行/data/deps.json` 里

```json
"h3": { "reserve_vram": 0 }
```

→ `POST /api/deps/reload` → 重启 `comfy_h3`（引擎托管启动才带得上新参数）。

**注意**：如果 H3 是手工 bat 起的，引擎只会"探活复用"，不会改它的参数——
必须先停掉那份进程，让引擎自己派生，配置才生效。

### 2.2 中止没有真的中止

`/interrupt` 只作用于**正在执行**的那一条，**排队中的动不了**；而代码原来也只打 `/interrupt`。
实测时间线：

| run | 提交 | 真正开始执行 | 结局 |
|---|---|---|---|
| 224 | 08:41:21 | 08:47:27（排队 6.1 min） | 看门狗 08:47:08 触发时它还在排队 → 无效；21.1 min 才返回 |
| 225 | 08:56:21 | 09:02:43（排队 6.4 min） | 12 min 节点超时失败 |

修法（`backend/service/comfy_queue.go`）：中止 = **删 pending + 停 running + 复核**，
并且把 ctx 一路传进 `RunGraphAtCtx`——原来那条轮询链路**完全不看 ctx**，
节点判超时之后它还会自己跑满 20 分钟预算。

### 2.3 贪睡常数：估时基准不含分辨率与步数

`shotSecPerFrame = 1.2` 只对 608×352 / 12 步成立。768×448@20 步（run 217/222）
真实成本约 2.5 倍，于是那一档**每一镜都会被"慢镜告警"误判**，预算也少给一半多。
修法：`shotCostSeconds(frames,width,height,steps)`，预算/看门狗/慢镜告警共用。

### 2.4 "已完成镜已落盘、重跑复用"只写在注释里

`shotlist.go` 的报错文案承诺复用，`reusedCount` 却只初始化、从没查过任何存储；
DB 里 `shot_jobs` 表建好了（`prompt_hash/seed/elapsed_ms/vram_peak_mb`）却 0 行。
结果：一晚 6 次失败，每次都从第 1 镜重烧。

修法（`backend/service/shot_cache.go`）：按「提示词 + 宽高帧步 + 后端 + turbo」哈希缓存
产物到 `<产物目录>/shot-cache/<hash>.mp4`，命中就跳过生成；缓存写在音频治理之后，
存的是最终交付那一版；台词段不缓存（画面取决于当次 TTS 音轨）。

### 2.5 顺手挖出来的真 bug：`attachDepLog` 自锁，整块 deps 接口挂死

现象：`/api/deps` 20s+ 不返回、`/api/deps/comfy_h3/start` 返回 202 却**再也不派生进程**，
而 `/api/health`、`/api/runs` 完全正常。看起来像"H3 起不来"，实际是锁：

```
Start() 在 spawn 路径上持有 s.mu  →  s.attachDepLog() → depLogPath() 又 s.mu.Lock()
Go 的 Mutex 不可重入 ⇒ 永久死锁 ⇒ 之后所有碰 s.mu 的调用全部挂住
```

只在 `logDir` 有值时触发（`depLogPath` 返回空就提前返回），所以"平时好好的"，
一旦引擎配了依赖日志目录，第一次真正 spawn 就死。修法：`depLogHandleAt` 做成无锁纯函数，
路径在锁外算好；`deps_deadlock_test.go` 钉住契约。

### 2.6 看门狗把"排队"当成"在算"

计时从**提交那一刻**起，可提交后可能先在 ComfyUI 队列里干等。run 224 就是这样被误杀的：
看门狗 5m35s 触发时那条 prompt 还在排队，压根没开始算图。
修法：`MediaRequest.OnPhase` 上报 `queued`/`running`，看门狗 `Pause()`/`Resume()`，
只累计"真在算"的时间；中止日志里单独打印排队时长。


| 文件 | 改动 |
|---|---|
| `运行/data/deps.json` | 新增 `h3.reserve_vram = 0` |
| `backend/service/comfy_queue.go` | 新增：`QueueIDs` / `DeleteQueued` / `ClearPendingQueue` / `Interrupt` / `AbortPrompt`（含复核） |
| `backend/service/comfy_media.go` | 新增 `RunGraphAtCtx`：ctx 感知轮询、取消即中止、提交时打印排队情况、提交被弄丢时快速失败 |
| `backend/service/engine_v2.go` | `interruptComfy` 先清 pending 再 interrupt |
| `backend/service/shotlist.go` | 生成链路带 ctx；镜头复用接入；`shots_reused` 如实计数 |
| `backend/service/shot_watchdog.go` / `shotlist.go` | 预算/看门狗/慢镜告警改为 `shotCostSeconds(frames,w,h,steps)` |
| `backend/service/nodespec.go` | `shotListTimeout` 传宽高步，长镜不再少给预算 |
| `backend/service/deps.go` | 修 `attachDepLog` 自锁（`depLogHandleAt` 无锁纯函数，路径锁外算好） |
| `backend/service/shot_watchdog.go` | 只累计"在算"时间；`Pause/Resume`；排队时长单独记 |
| `backend/service/comfy_media.go` | `MediaRequest.OnPhase` 上报 queued/running |

测试：`comfy_queue_test.go`（中止删 pending / 停 running / 取消快速返回 / 丢单快速失败）、
`shot_cache_test.go`（键稳定性与参数敏感性、坏产物不缓存、容量清理）、
`shot_watchdog_test.go`、`shot_speed_test.go`（分辨率敏感）。

## 4. 验证口径（改下一版照这个做）

1. **A/B 单镜**：同一分镜连跑 3 次，取 `shot_progress.data.elapsed_ms`；
   健康档应回到 1.2–1.5 秒/帧（56 帧 ≈ 67–85s）。
2. **中止是否真省时间**：跑一镜，中途点停止；看 `engine.log` 是否出现
   `[queue] 生成被取消，已中止 prompt=…（已离开队列=true）`，以及
   `/queue` 里是否真的空了。**"中止了"和"省下时间了"必须分开验证**。
3. **复用是否命中**：同一分镜跑第二次；`engine.log` 应出现
   `[shotlist] 命中复用缓存`，`shots_reused` > 0，且总耗时接近装配时间。
4. **显存是否全量加载**：`engine.log` 的显存前瞻不再出现 `还差 …MB`；
   `nvidia-smi` 峰值 21–22GB（而不是贴 23.8GB 换页）。

## 5. 已知风险 / 未验证

- `reserve_vram=0` 的收益**尚未做本机 A/B**（历史上 27 倍是单例，不是对照实验）。
- 图像实例（8188）驻留 17GB 时仍会挤 H3；引擎有跨实例 `/free`（`comfy_evict.go`），
  但它只在"不够时"触发，且要求实例可被 `/free`。**视频前手动停 8188 仍是最稳的**。
- 复用键不含随机种子：同提示词会复用同一镜（这是有意的），
  想换一条就改提示词或删缓存文件。
- 文本编码器 14.6GB `nvfp4_awq` 在 Ampere 上是否走反量化路径，未测。

## 6. 实测反转：reserve=0 生效了，但慢的不是它

2026-10-26 13:00，H3 以 `--reserve-vram 0` 手工实例运行后实测：

| 观测 | 数值 |
|---|---|
| 8189 空闲显存 | 485MB（即 ~23.2GB 全量驻留，**不再是部分加载**） |
| GPU | 100% 利用率、1950MHz（上限 2100）、172W、无降频 |
| torch | 2.14.1+cu130，CUDA 可用，RTX 3090 |
| 同一镜（39 帧 / 384×256 / 8 步） | **仍撞 12 分钟节点超时** |

也就是说：**"切 reserve 0 就能回到 1.2 秒/帧"的假设不成立**（本机 39 帧都跑不完 12 分钟 ≈ 18s/帧，
而项目自己记录过 608×352×124 帧 120s ≈ 1s/帧，差近 20 倍）。

下一个要验的假设（未验证）：
1. **每步在 DiT 与文本编码器之间搬权重**——19.5GB DiT + 14.6GB TE 在 24GB 卡上无法共存，
   而 `--cache-none` 的语义正是"减少 RAM/VRAM 占用、每个节点都重算"；
2. 三个 ComfyUI 实例（8188 / 8189 / 8190 MOSS）同时活着，开任意两个就互抢；
3. int8_convrot 权重在 Ampere 上是否需要按步反量化（无 fp8 tensor core）。

验证前提：H3 必须**由引擎托管启动**，它的 stdout 才会落到 `运行/logs/comfy_h3.log`；
手工 bat 起的实例没有日志，这类问题只能靠猜。

## 7. ComfyUI 自己的日志说了什么（2026-10-26 13:10，决定性证据）

`运行/logs/h3-final.log`（reserve=0 的实例，8 步）：

```
Model MiniMaxH3 prepared for dynamic VRAM loading. 19995MB Staged. ...
  0%|          | 0/8 [00:00<?, ?it/s,   Model Initializing ...  ]
  0%|          | 0/8 [04:14<?, ?it/s,  Model Initialization complete!  ]
 12%|█▎        | 1/8 [04:14<29:43, 254.86s/it]
 25%|██▌       | 2/8 [04:56<14:48, 148.06s/it]
 38%|███▊      | 3/8 [04:56<00:03,  1.60it/s]
100%|██████████| 8/8 [04:59<00:00,  1.60it/s]
```

拆开看：
- **模型初始化 4 分 14 秒**（19995MB 权重 staged）；
- 初始化完之后 **8 步采样只用 45 秒**（1.6 it/s，末 6 步约 0.6s/步）；
- 同进程里已经初始化过的提交（`h3-run-reserve0.log`）**12 步只要 29 秒**（2.17 s/it）；
- `h3-run.log` 里 4 次提交分别耗时 432s / 781s / 478s / 646s，全是"多分钟级"。

⇒ 结论修正：**慢的不是采样，是"每次都要重新初始化模型"**。
这解释了为什么 reserve 从 4 改到 0 没有解决问题——它解决的是换页，不是重复初始化。

**待验假设**（下一步 A/B）：`--cache-none`（"减少 RAM/VRAM 占用、每个节点都重算"）
让 staging 每次重做。已做成配置项 `data/deps.json` → `"h3": {"cache_none": false}`，
reload + 重启依赖即可切换，不需要重编 exe。

A/B 口径：
1. `cache_none: false` 启动 H3，**连跑两次**同一镜；
2. 第二次若仍在 4 分钟量级 → 假设不成立，回头查 dynamic VRAM staging 本身；
3. 第二次若降到 ~40–60s → 确认，之后把 `cache_none: false` 写进默认。
   注意代价：ComfyUI 会缓存节点结果，**同图重复提交会秒回旧结果**——
   这也是当初选 `--cache-none` 的原因；重跑换种子/换提示词即可规避，
   而"故意复用"现在由引擎的 shot-cache 显式负责（`shots_reused` 可查）。

## 8. 实测验收（2026-10-26 14:00–15:00，生产环境）

启动参数：`--reserve-vram 0 --cache-lru 2`（`deps.json` 的 `h3.args` 整体覆盖）。

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 39 帧 / 384×256 / 8 步（冷启动，含模型初始化） | **12 分钟 → 超时失败**（run 236/237） | **3.1 分钟 → 成功**（run 240） |
| 同一镜再来一次（热态） | 12 分钟（重复初始化） | **0.5 分钟（30 秒）→ 成功**（run 241） |
| 中途点停止 | 等 12 分钟节点超时，ComfyUI 继续烧 | **2.2 秒收起**（run 242），`/queue` 1 → **0/0** |

结论：**稳态 30 秒一镜**（39 帧 ≈ 1 秒/帧），与项目自己记录的基线一致。
`--cache-none` 是主因——它让每个 prompt 重做 4 分 14 秒的模型 staging。

## 9. 顺手修掉的两个「构建期」坑（都不是本任务引入的）

1. **`data/pipelines.json` 被写入了 UTF-8 BOM**（EF BB BF）。
   Go 的 `encoding/json` 不认 BOM → 引擎启动直接 `log.Fatalf`，`pipeline_test.go` 6 条全红。
   修法：按 `utf-8-sig` 读、去掉前 3 字节写回（不要整篇 reformat，会丢手工排版）。
   **用 PowerShell `Set-Content -Encoding UTF8` 写这个文件会重新引入 BOM**（PS 5.1 默认带）。
2. **`text_overlay.go` 的 `buildOverlayFilter` 改成了 3 返回值**（filter, cleanup, error），
   但函数内部 3 处 return 与测试的 7 处调用还停在 2 值 → 整个 package 编译不过。
   补齐：错误路径 `cleanup(); return "", noop, err`，成功路径返回 `cleanup`
   （临时文字文件要等 ffmpeg 跑完才能删）。

## 10. 后期并行：评估后决定**不做**（附数字）

用 run 246 的真实分解算过上限：

| 阶段 | 耗时 |
|---|---|
| 第 1 镜（冷，含模型初始化） | 144.7s |
| 第 2 镜 | 87.9s |
| 整轮 wall time | 244s |
| ⇒ 装配 + 音画对齐 + 响度 + 拼接过场 | **≈11.4s（占 4.7%）** |

也就是说：把整个后期阶段做成完全并行，一支 2 镜片最多省 11 秒；
而代价是 ffmpeg 并发读写同一批中间文件、以及"哪一步失败降级成什么"的复杂度上升。
**收益上限 5% 换来一类新的偶发故障，不划算**。等真出现 8–10 镜长片（后期占比升到 15%+）
再动，那时优先并行的是插帧（CPU 密集）与逐镜音频抽检（ASR）。

## 11. 真 ETA：第一次跑也能给出剩余时间（2026-10-26 21:40）

实测 `node_progress` 事件里 `eta_ms` 长期恒为 0——因为 `ETAFor` 只用"同类节点历史 EWMA"，
第一次跑某类节点必然没有样本，进度条只能空转。

修法：shotlist 在开工时按分镜表算出**本次运行的总工作量**
（`Σ 帧数 × 像素比 × 步数比`，复用 `shotCostSeconds` + 装配/后期固定开销），
登记成 `SetRunPrediction`；心跳优先用它算剩余，没有预测才退回历史均值。
单测 `run_eta_test.go`：剩余不为负、只影响登记过的 run、清理后失效、runID=0 不登记。

注意：命中复用缓存时实际耗时远小于预测（run 248 只用 10 秒），
此时 ETA 会显得偏大——这是"预测按最坏情况给"的取舍，宁可先给大数再迅速收敛。

## 12. 预检门的误伤与修法（2026-10-26 18:00，现场发现）

加上预检门后第一次实战就抓到自己一个 bug：run 247 被 **409** 拦下，理由是
"空闲 5318MB < 模型 20480MB"，可那会儿 H3 **已经把模型装在显存里了**（热实例），
一次加载都不需要。

> "空闲少"和"装不下"是两件事。只看空闲，就会把每一个热实例都判成装不下。

修法：`AlreadyResidentForNodes` —— 已用显存 ≥ 需求 60% 就认定"模型已驻留"，放行并记一行日志。
（取 60% 是因为热态还有 VAE/激活的额外占用，而冷实例通常只占桌面 2–3GB，两档不会混淆。）
单测覆盖四种档位 + 探不到实例时保守不放行。
