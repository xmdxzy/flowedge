# H3 视频工作流：为什么慢、为什么吃显存，以及怎么改

> 2026-10-29 实测于 RTX 3090 24GB / 64GB RAM / ComfyUI 0.41.0 / torch 2.14.1+cu130。
> 所有数字都来自本机 A/B，不是估算；未验证项单独列在最后。

## TL;DR

- **慢的主因不是采样，是「每换一个提示词就把 15GB 文本编码器 + 20GB 主模型重新搬一遍」。**
  同一提示词命中缓存 66.6s；换提示词 172–179s；冷启动 274s。
- **显存吃满的原因**：DiT 19.53GB + TE 14.61GB + 视频 VAE 4.85GB + 音频 VAE 0.56GB ≈ 40GB，
  24GB 卡物理上放不下，ComfyUI 的 DynamicVRAM 只能把权重放在 NVMe 上按需换入。
  峰值 23.8GB 里约 20GB 是 DiT，剩下是激活/VAE；不是“泄漏”。
- **再往下一层**：一次换提示词实测物理盘读 **35.38GB / 113s ≈ 313MB/s**，而盘本身
  `winsat` 能跑 **2615MB/s**；同时 64GB 内存 commit 到 64.3GB、页面文件峰值 27GB。
  **真正的双重瓶颈是「35GB 工作集 + 64GB 内存」**，显存只是表面。
- **已落地**：`--use-ck-attention`（ComfyUI 自带 comfy-kitchen INT8 注意力）。
  换提示词 178.8/172.4s → 94.8/84.7s，**约 2×**；采样 4.4s/步 → 2.66s/步。
- **反例（别再试）**：`--disable-fast-disk` 把内存吃到只剩 3.5GB 并换页；
  `--disable-dynamic-vram` 全量加载后 6 分钟无采样进度；
  `--disable-fast-disk --disable-pinned-memory` 两镜读盘 61GB、274/302s；
  Defender 排除模型目录无稳定收益（197/304s，方差大）。以上都已停掉/撤销。
- **下一步最值**：① 内存换 2×64GB（主板最大 128GB，零画质损失，能把 35GB 从盘搬到内存）；
  ② 退而求其次，W4A8 DiT（12.54GB）+ fp8 VAE（2.6GB）把峰值显存压到 17–18GB；
  ③ 多镜片做「整片一次 TE / 一次 DiT」的批量构图（3 镜以上才有明显收益）。

## 1. 现状基线（608×352×124 帧，12 步，res_multistep/simple，无 turbo）

直接向 8189 提交与引擎相同的 API 图，固定 seed，只改提示词：

| 场景 | 服务端耗时 | 峰值显存 | 说明 |
|---|---:|---:|---|
| 冷启动第一条 | 272.4s | 23.8GB | 35GB 权重从盘上首次载入 + 编译 |
| 同一提示词再跑 | 65.9s | 23.5GB | `execution_cached` 命中 1/2/3/4/5/8/41/7/9，TE 与加载器都没跑 |
| 换提示词 | 177.9s | 23.8GB | 生产里每镜都是这一档 |
| 再换提示词 | 170.6s | 23.8GB | 稳定复现，不是偶发 |

结论：**“同一提示词 66s、换提示词 178s”这 112s 的差，就是 TE 重新加载/编码 + DiT 重新换入的代价。**
镜头之间的提示词必然不同，所以生产永远付这 112s。

## 2. 根因拆解

### 2.1 40GB 工作集 vs 24GB 显存，注定要换入换出

```
minimax_h3_fl2va_pruned_int8_convrot   19.53 GB
qwen3vl_32b_minimax_h3_nvfp4_awq       14.61 GB
minimax_h3_video_vae_fp16               4.85 GB
minimax_h3_audio_vae_fp32               0.56 GB
turbo LoRA（可选）                       0.73 GB
-----------------------------------------------
合计                                   ~40.3 GB
```

24GB 卡再扣桌面 ~1.3GB，TE 与 DiT 不可能同时驻留。ComfyUI 0.41 的 DynamicVRAM 策略是
`fast_disk=True`（日志原文），把权重放 NVMe、按需流式载入；所以“能跑”，但每换一次提示词就重搬。

### 2.2 DynamicVRAM 的“换 dtype 后每 prompt 重载”是已知问题

ComfyUI issue #14276 记录的触发条件与本机完全一致：同一会话里从 fp16 切到 nvfp4/int8 混合精度后，
后续每个 prompt 都出现 `Requested to load`，耗时从 23–28s 变成 120–190s。
本机日志也是每个 prompt 都 `Requested to load MiniMaxH3TEModel_` / `MiniMaxH3`，且 `0 models unloaded`。
这不是“模型没缓存”，是 DynamicVRAM 在流式换入。

### 2.3 注意力跑在 PyTorch SDPA 上，没用上 INT8 内核

启动日志：`Using pytorch attention`。而 `comfy_kitchen.int8_attention_is_available()` 在 3090（sm_86）
返回 True。社区实测（8GB 陷阱那篇，56 heads × 128 / S=8192）：
SDPA 143.1ms vs comfy-kitchen INT8 22.8ms，**6.3×**，且误差比 SageAttention 低 2.4×。
本机开 `--use-ck-attention` 后采样 4.4s/步 → 2.66s/步（1.65×），端到端约 2×——
没有社区数字那么夸张，因为换权重那 112s 不受注意力影响。

### 2.4 文本编码器 NVFP4 在 Ampere 上是“模拟”的

启动日志：`Native ops: ... int8_tensorwise; emulated ops: mxfp8, nvfp4, ...`。
3090 没有 FP4 张量核，NVFP4 权重只能反量化后计算。TE 又是 32B，编码一次不便宜；
这就是“换提示词”比“同提示词”多出的一大块。H3 专用 TE 只有 32B 三档（bf16 / int8 / nvfp4），
**没有 8B 版本**；`qwen3vl_8b_int8_convrot` 是别的模型的，不要拿来替。

### 2.5 视频 VAE 解码也是固定成本

视频 VAE 4.85GB fp16 + 音频 VAE 0.56GB fp32，124 帧解码是几十秒级；它和采样、换权重叠加，
构成“一条 5 秒片 2–6 分钟”。社区有 fp8mix 视频 VAE（2.6GB），可同时降显存和解码带宽。

### 2.6 更底层的主因：每镜 35.4GB 磁盘读 + 64GB 内存上限

给一次换提示词跑动加物理盘计数，结果非常直接：

```
wall 113.2s，物理盘读 35.38GB → 平均 313MB/s
```

而 `winsat disk -drive d -read -seq` 测出来是 **2615MB/s**。盘没问题，是 ComfyUI 的
`fast_disk` 权重流式读只跑出 ~300MB/s（小块/按需读 + Windows 内存压力），35GB 工作集
正好对应 112s。再叠加系统内存：

- 本机 **64GB RAM，只有 2 个 DIMM 槽，已插 2×32GB，主板最大 128GB**。
- 跑 H3 时 commit 到 **64.3GB**，页面文件峰值 **27GB**（`D:\pagefile.sys`，和模型同一条 NVMe）。
- 所以 303s 那种离群值不是模型慢，是**换页 + 磁盘读 + 内存压缩**一起发作；同一配置实测
  113s / 198s / 304s 三档，方差极大。

这也解释了为什么 `--disable-fast-disk` 会失败：把 40GB 权重塞进 64GB 内存，还要留给
Windows/桌面/激活，必然换页。**64GB 是这台机器的真正瓶颈，不是 24GB 显存。**



## 3. 本机 A/B 结果

| 配置 | 换提示词耗时 | 采样速度 | 峰值显存 | 结论 |
|---|---:|---:|---:|---|
| 基线（DynamicVRAM + fast_disk） | 177.9 / 170.6s | 4.4s/步 | 23.8GB | 现状 |
| + `--use-ck-attention` | **94.8 / 84.7s** | **2.66s/步** | 23.8GB | 已采用，~2× |
| + `--disable-fast-disk` | >360s（中止） | 4.0s/步 | RAM 只剩 3.5GB | 负优化：权重进内存导致换页，采样优势也被抵消 |
| + `--disable-dynamic-vram` | >360s（中止） | 无进度 | 23.7GB | 负优化：全量加载 20GB 后卡在初始化/换页 |
| + `--disable-fast-disk --disable-pinned-memory` | 274.9 / 302.6s | — | 23.9GB | 负优化：两镜读盘 61.2GB，权重没有留在内存 |
| Defender 排除 `D:\AI\Models` | 197.9 / 304.0s | — | 24.2GB | 方差太大、无稳定收益；已撤销 |

> 注：以上都在 CK 注意力基础上做，所以“采样没变快”不是 CK 失效，而是换权重/换页成了新瓶颈。
> 113s 那次同时测得物理盘读 **35.38GB**（≈313MB/s），确认 112s 主要是 35GB 工作集的磁盘读。


### 真实引擎链路（改完 CK 后）

| 运行 | 分辨率/帧/步 | 引擎墙钟 | Comfy 服务端 | 说明 |
|---|---|---:|---:|---|
| run 338 | 608×352×124×12 | 393s | 386.1s | 冷启动首镜（35GB 首次载入） |
| run 339 | 608×352×124×12 | 156.7s | 151.9s | 换提示词第二镜，`0 models unloaded` |

历史同链路 run 337（512×896×73×12）是 225s；按像素×帧折算，新配置约快 2×。
首镜 6.5 分钟仍是冷启动成本，**不要拿它估整片**；整片应按“首镜 6–7 分钟 + 后续每镜 2.5–3 分钟”报区间。

## 5. 部署方案（按投入产出排序）

### P0 已完成：开 INT8 注意力

```json

```

改完：

```powershell
curl --noproxy '*' -X POST http://127.0.0.1:8080/api/deps/reload
curl --noproxy '*' -X POST http://127.0.0.1:8080/api/deps/comfy_h3/start

验证：`GET :8189/system_stats` 的 `argv` 含该 flag；日志出现 `Using Comfy Kitchen attention`。
回滚：删掉该行 → reload → 停/起 `comfy_h3`；或恢复
`运行/data/deps.json.bak-ckattn-20261029-115614`。

**不要**同时加 `--disable-fast-disk` / `--disable-dynamic-vram`（本机实测负优化）。
`--reserve-vram 0` 保持不动（改成 4 会让 H3 永远部分加载，历史实测 87s→2269s）。

### P0.5 硬件：把 64GB 内存换到 128GB（零画质损失，最高杠杆）

本机 `Win32_PhysicalMemoryArray`：**2 个槽，最大 128GB**；当前 2×32GB DDR4-2666 ECC RDIMM
（Samsung M393A4K40CB2-CTD）。要升级只能**换成 2×64GB ECC RDIMM**（不是加一条）。

- 收益：40GB 工作集可以完整驻留内存，`--disable-fast-disk` 不再换页；换权重从“NVMe 35GB
  按需读”变成“PCIe 从内存搬”，112s 的磁盘读有望降到个位数秒级，且不再有 300s 离群值。
- 代价：两条 64GB ECC RDIMM 的采购成本 + 拆装；买前核对主板 QVL 是否支持 64GB 4Rx4。
- 过渡：出片时关掉 UnrealEditor / blender / vmmemWSL（本次实测三者合计约 3GB 工作集），
  能给 H3 多留一点内存，但解决不了 40GB 工作集的根本矛盾。

### P2 结构优化：整片一次 TE、一次 DiT、一次 VAE（预计 3–5 天）

现在每镜是一个独立 ComfyUI prompt，所以每镜都重搬 TE/DiT。把 `shotlist` 改成阶段批处理：

1. 一个图里放 N 个 `MiniMaxH3ImageToVideo`（各自 prompt），共享同一个 CLIP/VAE/DiT；
2. TE 驻留时把 N 条 conditioning 全编码完；
3. 再换入 DiT，连续跑 N 个 `SamplerCustomAdvanced`；
4. 最后换入 VAE，连续解码 N 条。

**关键坑**：ComfyUI 的执行顺序不保证“所有 TE 节点先跑完”。直接把 N 个采样器接在同一个
CLIP 上，执行器可能 TE→DiT→TE→DiT 交替，等于没批。需要显式屏障：
- 方案 A：写一个极小的 no-op conditioning 节点（接收全部 conditioning，按原样输出），
  让所有采样器依赖它；
- 方案 B：两阶段图——阶段 1 只跑 TE 并把 conditioning 落盘，阶段 2 只加载 conditioning 采样。
  KJNodes 没有 conditioning 存/读节点（本次已查），需要自己写 ~50 行 custom node。

收益：换权重次数从 3N 降到 3。6 镜约 15 分钟 → 9–13 分钟；2 镜收益很小（甚至持平）。
代价：单镜失败会拖累整批，需要按 3 镜一组分块 + 失败重试。


### P3 试验性加速（有余力再做）

- TE-Speed 3.5 / Spectrum：二选一，独立工作树，单变量 A/B；闭源 pyd 注意供应链。
- Ref2VA-VSA：只对角色参考镜启用，先跑 3 条比对一致性。
- PDD 8 步：与现有 turbo v4 二选一，重点听台词有没有爆音/错位。

## 6. 引擎侧要改的两处“误导”

1. **显存预检**：`produce.go` 仍按 `模型 20480MB` 与“空闲显存”比较，DynamicVRAM 下必然报
   `too_small`。这不是错误，但会让人误以为要加 reserve/降分辨率。建议改成
   “DynamicVRAM 将流式换入，预计首镜 X 秒/后续 Y 秒”，并按实测 150–390s 给 ETA。
2. **估时口径**：文档里的“单镜 6.6 分钟”是冷启动口径；稳态是 2.5–3 分钟（CK 后）。
   报整片用“首镜 6–7 分钟 + 后续每镜 2.5–3 分钟 + LLM/装配”，不要用单一常数乘镜数。

## 7. 未验证 / 风险

- **画质**：CK 与基线同 seed 的 SSIM 只有 0.69（不是 bit-identical）。抽帧目检（第 60 帧）
  构图/光影都正常，但**没有做整片多镜一致性验收**；上线前建议用同一分镜跑 2–3 镜，
  看角色/场景锁是否漂移，并跑 `verify-media.py --asr` 查台词。
- **音频**：只确认了 AAC 流存在（5.167s / 163 帧），没有做 CK 前后的听感/ASR 对比。
- **W4A8 / fp8 VAE / PDD / VSA / TE-Speed**：均未安装、未实测，收益是社区数字或按字节数推算。
- **长稳**：没有跑 >1 小时的连续出片；23.8GB 峰值只剩 ~0.8GB 余量，夏季/桌面占用升高时仍有

## 9. 定稿方案（社区证据版，2026-10-29）

> 本节不引入新的本机实测；只依据官方索引、模型卡、社区复现报告做取舍。
> 目的：在 RTX 3090 24GB / 64GB RAM / Windows / ComfyUI 0.41 上，定一条**可维护**的主链路，
> 而不是把能装的加速全叠上去。

### 9.1 决策

**生产主链路（定稿）**

```
H3 pruned INT8 ConvRot 19.53GB
+ Qwen3-VL 32B NVFP4 AWQ TE 14.61GB
+ MiniMax H3 video VAE fp16 4.85GB / audio VAE fp32 0.56GB
+ comfy-kitchen INT8 attention（--use-ck-attention）
+ 非台词镜：PDD 8-step Acc LoRA（FL2VA / Ref2VA 各一份）
+ 台词/口型镜：回 base 12 步（或 Turbo 12 步），不用 PDD 8
+ 3 镜以上：shotlist 阶段批处理（TE 一次、DiT 一次、VAE 一次）

**显存紧张时的备选（不默认）**：W4A8 DiT 12.54GB + fp8 VAE 2.6GB；Q2 TE 7.91GB 只用于草稿，
不用于终稿。**不把 PDD 与 Turbo/FastH3 叠加**——社区明确“蒸馏适配器不要乱叠”。

### 9.4 提效优先级（按收益/风险）

1. **消除每镜重载**（最大头）：128GB 内存让 40GB 工作集驻留，或 3 镜以上阶段批处理。
   社区没有“内存换速度”的 benchmark，但 ComfyUI 的 DynamicVRAM 机制决定了这是结构性收益。
2. **少步数**：非台词 PDD 8（相对 12 步采样 −33%，相对 20 步 −60%）；台词保 12。
3. **便宜注意力**：CK INT8（已落地；社区 6.3× kernel，端到端取决于 attention 占比）。
4. **小权重**：W4A8 省 7GB 显存、换入字节 −18%；fp8 VAE 再省 2.2GB。
5. **块缓存/稀疏**：TE-Speed、VSA、Spectrum 均有 20–43% 量级宣称，但闭源/近似/适配风险，
   只在 1–4 做完仍不够时，按单变量实验引入。
6. **分辨率/帧数**：草稿 608×352×124；终稿再升，不要一上来 768p/长帧。

### 9.5 明确不做

- 不叠 PDD + Turbo + FastH3（蒸馏适配器互斥）。
- 不用 SolAttn / Sol-H3 / FastH3 / VDN（硬件/平台不匹配）。
- 不为了“省显存”默认换 Q2 TE（32B→Q2 的语义损失会直接反映在提示词遵循上）。
- 不再试 `--disable-fast-disk` / `--disable-dynamic-vram` / 关 pinned / Defender 排除
  （本机已验负；社区也没有把它们当加速手段）。

### 9.6 迁移步骤

1. 装 PDD 8-step：`MiniMax-H3-FL2VA-Acc-8Step` + `MiniMax-H3-Ref2VA-Acc-8Step`；
   先确认 ComfyUI 0.41 LoRA-bank 能完整加载 32 个输出头，不行再用
   `ComfyUI-MiniMax-H3-PDD-Acc` 节点。
2. 在 `shotlist` 增加“按镜选步数/LoRA”：有台词 → base/Turbo 12；无台词 → PDD 8。
   这是当前 `film` 缺的能力（现在全局 steps/turbo）。
3. 实现阶段批处理（≥3 镜）：两阶段图 + conditioning/latent 存读节点，或 no-op 屏障；
   按 3 镜一组，失败可单组重试。
4. 显存仍紧再上 W4A8 + fp8 VAE；Q2 TE 只给草稿档。
5. 最后才评估 TE-Speed / VSA；每次只动一个变量。
