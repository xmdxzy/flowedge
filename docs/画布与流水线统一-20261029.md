# 画布与流水线统一：保留「用户自定义工作流」的最优形态（2026-10-29）

> **本文纠正 v2 的一个产品判断。**
> `docs/多模态出片台-v2.md` 写「图不再由用户画」，并把画布平台形态整体删除（commit `33ff130`）。
> 记录在案的理由是「组合空间里绝大多数是垃圾」「用户从来没画对过」。
> 这个观察是真的，但归因错了：**不是画布不好，是当时的画布没有护栏**。
> 删画布等于砍症状。正确做法是保留画布，把五道护栏补上。

> **好消息：执行层从来没被删。** 被删的是「面」（UI / CRUD / 目录 / 估算），不是「里」。
> 因此恢复成本远低于重写——见第一节的证据表。

## 一、现状盘点：什么还在，什么没了

| 能力 | 现状 | 代码证据 |
|---|---|---|
| 任意图执行（按 workflow ID 取图跑） | **在** | `main.go:206` `engine.SetResolver` 从 `workflows` 表按 ID 返回 nodes/edges |
| 改图跑一次但不写回库（单镜重跑） | **在** | `run_service.go:77` `Resume(runID, fromNode, nodesOverride)`，注释明确「不写回数据库」 |
| DAG 结构校验 | **在** | `dag.go`，6 个稳定码：`cycle` `self_loop` `dangling_edge` `duplicate_edge` `orphan_node` `no_start`，带 `error`/`warn` 分级 |
| 节点参数校验（带人话修复建议） | **在** | `nodeparams.go:32` `ValidateNodeParams(nodes, hasInbound)` |
| 依赖预检 | **在** | `preflight.go:64` `PreflightDeps(nodes, caps, sup)` — **入参是 nodes，不是 pipeline** |
| 质量门与诊断补丁 | **在** | `quality_gate.go:239` / `quality_loop.go:96-153` |
| 节点级事件与耗时 trace | **在** | `Event{NodeID}` + `GET /api/runs/:id/trace` |
| 取消 / 续跑 / 排队态 | **在** | `/api/runs/:id/cancel`、`comfy_queue.go` |
| 工作流 CRUD API | **没了** | `/api/workflows*` 已删 |
| 按图运行入口 | **没了** | 只剩 `POST /api/produce {pipeline, params}` |
| 节点目录 API（调色板数据源） | **没了** | `NodeSpecs` 仅内部可读，未对外 |
| 成本预估 | **没了** | `/api/estimate` 已删 |
| 画布 UI | **没了** | 前端只剩 3 个页面（`ProducePage` / `RunsPage` / `ArtifactsPage`），`@xyflow/react` 依赖一并移除 |
| 起步模板 | **没了** | 随画布删除 |

**结论：`PreflightDeps` 和 `ValidateNodeParams` 本来就是图形态入参。**
画布的 dry-run 不需要新写校验层，把这两个函数接到 HTTP 上就是 80% 的护栏。

### 被删前的画布到底多大（实测，`git show 071bdff`）

| 项 | 数值 |
|---|---|
| v1 `frontend/src` | 96 个文件 / **18,314 行** |
| 其中 `nodes/*.tsx` 节点组件 | 21 个文件 / **1,008 行**（≈48 行/个，早已是 `GenericNode` 薄壳） |
| 当前 `frontend/src` | 29 个文件 / **3,509 行** |

关键读数：**每个节点组件只有 ~48 行**，说明 v1 的画布不是"27 个手写 UI"，而是"1 个通用组件 + 27 份配置"。
所以"恢复画布"不等于"回到 18k 行"——上限取决于检查器/调色板/页面写多细，不是取决于节点数。
这也正是第二节第 5 条（元数据双写）应该被当成护栏做掉、而不是当删画布的理由。

## 二、旧画布输在哪：5 条真原因

| # | 真原因 | 当时的症状 | 护栏 |
|---|---|---|---|
| 1 | **空画布起步** | 新人打开一片空白，只能靠猜和抄；抄来的图节点类型对不上 | 从 7 条流水线**反向生成起步图**（已有 `PipelineStore.Build`），再给 3 个教学图 |
| 2 | **无类型系统** | `image` 输出能连到 `prompt`（text）输入，存得下，跑到一半才炸 | 端口类型 + 连线校验（新错误码 `type_mismatch`） |
| 3 | **无成本预估** | 不知道这一版要 40 分钟还是 6 分钟，也不知道会不会 OOM | 图级估算：逐项拆 + 区间 + 最坏（AGENTS §0.3 口径） |
| 4 | **无 dry-run** | 想验证只能真跑，一次 20 分钟 | 结构 → 类型 → 参数 → 依赖 四段干跑，不生成 |
| 5 | **节点元数据双写** | 加一个节点要改：前端组件、前端默认值、后端执行体、后端校验、预检，5 处 | 节点元数据单一来源（扩 `NodeSpec`），UI 从 API 生成 |
| 6 | **画布没有验收层** | 画布里出来的片子无人审，qc 只存在于流水线 | 门 profile 变成**图级字段**，两个视图都能挂 |

第 6 条是 v1 真正的能力缺口，也是 v2 唯一真正赚到的东西。保留它，别随画布一起丢。

## 三、目标形态：一张图，两个视图

```
                     ┌──────────────────────────────────────────┐
   专家路径 ───────▶  │  画布视图：任意 DAG、拖拽、检查器、dry-run │
                     │                                          │
   新手路径 ───────▶  │  出片台视图：7 条预置，填字段即出片        │
                     └──────────────────┬───────────────────────┘
                                        │  同一份数据
                                        ▼
                       workflows 表（nodes / edges / schema_version / tags）
                                        │
                                        ▼  同一个编译器 + 同一条校验链
              ┌─────────────┬─────────────┬─────────────┬──────────────┐
              │ 结构校验     │ 类型校验     │ 参数校验     │ 依赖预检      │
              └─────────────┴─────────────┴─────────────┴──────────────┘
                                        │
                    资源仲裁（分道队列/单侧驻留）→ 执行 → 门控 → 产物
```

三条原则：

1. **唯一数据是 `workflows` 表**（`model/workflow.go:20`），不是 pipelines.json。
2. **`pipelines.json` 降级为"预置图生成器"**。这不是新设计——`produce.go:392` 现在就在做：把流水线组装出的图落成 `qc:` 前缀的临时 workflow 再执行。**流水线与画布本来就已经同构，只是没承认。**
3. **两个视图共用校验链与执行体**。禁止为画布另写一套执行器。

推论：流水线 = 「命好名、填好默认值、固定校验过」的一张图。画布 = 「同一张图的编辑器」。
于是新增能力只有一条路：加节点元数据 + 加执行函数。**画布不会成为第二套系统。**

## 四、逐点评估与优化（17 点）

每点四行：现状 → 问题 → 优化 → 判据。

### 1 数据模型
- 现状：`Workflow{ID, Name, Nodes, Edges, CreatedAt, UpdatedAt}`。
- 问题：没有版本号，没有归属前缀语义，没有软删。图 schema 一改，旧图只能炸 `unknown node type`。
- 优化：加 `schema_version int`、`origin string`（`user` / `pipeline` / `template` / `qc` / `agent`）、`deleted_at`（软删）；名称前缀约定只做展示分组，判定一律读 `origin`，不解析字符串。
- 判据：`produce.go:68` 的 `name LIKE 'qc:%'` 清理改为按 `origin='qc'`；`workflow_store_test.go` 钉住旧图加载不 panic。

### 2 节点契约（扩 `NodeSpec`）
- 现状：`{Type, Side, Heavy, Media, Timeout, MaxTimeout}` — 只有调度元数据，**没有 IO、没有字段 schema、没有成本**。
- 问题：这正是 v1 前端要手写 27 份组件、27 份默认值的根因。
- 优化：扩成四段（仍是单一来源）：
  ```go
  type NodeSpec struct {
      Type string; Side string; Heavy, Media bool      // 保留
      In   []Port        // {Key, Type} Type ∈ text|image|video|audio|any
      Out  []Port
      Fields []FieldSpec // {Key, Kind(text|int|float|bool|enum|file), Default, Min, Max, Options, Hint}
      Cost  CostModel    // {GPUClass, BaseSec, SecPerFrame, VramMB, ColdLoadSec}
  }
  ```
- 判据：新增一个节点只改 `nodespec.go` 一处 + 执行函数一处；`nodespec_test.go` 断言 12 种节点全部有 In/Out/Fields。

### 3 节点目录 API（调色板唯一来源）
- 现状：`NodeSpecs` 内部可读，前端拿不到。
- 问题：前端硬编码节点类型 = 双写（v1 的原罪）。
- 优化：`GET /api/node-catalog` 返回 12 种节点的 In/Out/Fields/Cost/Side。前端调色板、检查器表单、连线校验**全部**由它生成。
- 判据：前端 grep 不到任何节点类型字符串字面量（除测试夹具）；新增节点前后调色板条目数自动变化。

### 4 三层校验 + 一档干跑
- 现状：三层函数都在，但没有 HTTP 入口。
- 问题：画布无法在保存/运行前拦住错图。
- 优化：`POST /api/graph/validate` 一次返回四段结果：`dag issues` / `type issues` / `param issues` / `dep requirements`。分级 `error` 阻断、`warn` 放行。
- 判据：`cycle` / `dangling_edge` / `type_mismatch` / 缺必填参数 四类各有用例，都是 400 且带稳定 code。

### 5 端口类型检查（新）
- 现状：无。
- 问题：见第二节 #2。
- 优化：新建 `portcheck.go`，`IssueTypeMismatch = "type_mismatch"`，规则：`any` 兼容一切、同名类型互连、`image→text` 报 error。**故意不支持隐式转换**（隐式转换会制造"看起来能跑但语义错了"的图）。
- 判据：`portcheck_test.go` 覆盖非法/合法各 6 组。

### 6 dry-run
- 现状：`/api/preflight` 只吃 `{pipeline, params}`。
- 问题：画布没有"不花钱验一遍"的路径。
- 优化：`POST /api/graph/dry-run`，复用 `PreflightDeps(nodes, caps, sup)`，返回：缺哪个依赖、可否一键启动、预计耗时区间、预计显存峰值、门会查哪些项。**不提交、不占卡。**
- 判据：dry-run 一次 <300ms（全本地探测），且不改变任何进程状态（前后 `/api/deps` 一致）。

### 7 成本估算
- 现状：`/api/estimate` 已删。
- 问题：画布用户不知道一版多少钱（时间就是钱）。
- 优化：按 AGENTS §0.3 口径——生成（宽×高×步×段）+ LLM 分镜 + 冷加载 + 装配，**逐项拆、报区间 + 最坏**，禁止单值。用 `trace` 回写校准 p50/p90。
- 判据：抽 10 次历史 run，预估 vs 实测 p50 误差 ≤30%；输出结构里没有单一 `seconds` 字段（只有 `{p50, p90, worst}`）。

### 8 起步模板
- 现状：无。
- 问题：空画布 = 必然画错（v1 的头号败因）。
- 优化：`GET /api/workflows/templates` = 7 条流水线用 `PipelineStore.Build(id, 默认值)` 反向生成的图，`origin='template'`，只读。另加 3 个教学图：最小文生图、图生视频、带门的多镜。**新建画布默认从一个模板派生，不是空白。**
- 判据：`template_test.go` 断言 7 条流水线都能 Build → 落库 → 读回 → 通过四段校验（这条同时钉住"双视图同构"）。

### 9 画布边界（不重复造运行面板）
- 现状：出片台有运行看板、产物页、依赖抽屉。
- 问题：v1 画布里塞了运行/日志/产物，和主站重复，维护两套。
- 优化：画布**只做三件事**：编图、校验、发起运行。运行过程看节点染色（订阅 WS），详情点进去跳主站 run 页。
- 判据：画布代码库里没有产物列表/依赖管理组件；run 详情一律复用 `/runs/:id`。

### 10 运行中可视化
- 现状：`Event{NodeID}` + trace 已在。
- 优化：前端订阅既有 WS，按 `node_id` 染色（pending/running/success/failed/skipped）。不做轮询。
- 判据：一次真实运行里，节点状态变化与 `GET /api/runs/:id` 的 `node_states` 完全一致。

### 11 失败诊断落到节点
- 现状：6 个 `ErrorCode`（timeout/config_missing/upstream_failed/retry_exhausted/cancelled/cycle）已定义；`nodeparams` 带修复建议。
- 优化：节点卡片直接显示 code + 人话 + 修复建议；门失败（`gate_checks`）挂到**产出该媒体的节点**上，而不是只挂 run。
- 判据：故意让 TTS 未启动跑一次，失败节点上显示 `config_missing` + "点这里启动 TTS"。

### 12 质量门的位置（v2 唯一赚到的东西，必须留）
- 现状：`qc` 是流水线字段，服务端包一层 `start → quality_loop → end` 壳。
- 优化：改成**图级字段** `qc: {enabled, profile, target_score, max_rounds}`，`profile ∈ basic|av|film|semantic`。包壳逻辑（`produce.go:392`）不变，只是"从哪读 qc"改成图优先、流水线字段兜底。
- 判据：同一张图，`qc.enabled` 开/关各跑一次，节点数差 3、耗时差 ≈ max_rounds 倍；关掉时行为与现在完全一致（回归）。

### 13 ComfyUI 逃生舱（生态）
- 现状：`comfy_workflow` 节点已删；`data/comfy_workflows/` 模板目录仍在库里（`multimodal.go:127`）。
- 问题：遇到没封装的玩法就绕开 FlowEdge，画布再强也留不住人。
- 优化：加回一个 **`comfy` 节点**（不是旧的任意图节点）：`{template, instance, timeout}` 或内联 `workflow_json`。预检用 `/object_info` 校验节点与模型存在（缺就 400 点名）；执行走既有 `comfy_compat`；门只看技术项；**明确不做语义猜测**。
- 判据：拿一个社区 API-format 工作流跑通；故意写一个不存在的 ckpt 名，返回 400 并指出缺哪个模型。

### 14 版本与迁移
- 现状：无 `schema_version`。
- 优化：加载时对未知节点类型标 `status=unknown`，**只读、不许保存/运行**，UI 显示"该图包含本版本不支持的节点（v1 遗留）"；不做静默转换。
- 判据：喂一张含 `if_else` 的 v1 图，返回可读拒绝原因，不返回 `unknown node type` 裸错误。

### 15 隔离与删除语义
- 现状：`qc:` 前缀隔离 + 启动时清扫。
- 优化：预置/模板**禁止被覆盖保存**（保存到别的 ID）；用户图软删；`qc` 与 `agent` 图可硬删并可自动过期。
- 判据：试图保存到 `origin='template'` 的 ID → 409；`qc` 清扫测试仍绿（`produce_test.go` 已有）。

### 16 测试策略
- 现状：`pipeline_test.go` 拿真 JSON 逐条组装（很好的范式）。
- 优化：三个新测试文件
  - `workflow_contract_test.go`：12 种节点各一张最小图，组装→校验→dry-run 全绿。
  - `portcheck_test.go`：非法/合法连线矩阵。
  - `template_test.go`：7 条流水线反向生成图并能通过校验（**双视图同构的守门人**）。
- 判据：`python scripts/check-all.py` 全绿，且新增测试数是 3 个文件。

### 17 与 MCP / agent 的统一
- 现状：5 个工具，都是"出片"。
- 优化：加 2 个（不要更多）：`flowedge_graph`（读图）、`flowedge_graph_validate`（干跑）。agent 建的图 `origin='agent'`，**默认不自动运行**。
- 理由：agent 能出图却不看图，等于只能"点按钮"；但自动运行 agent 生成的图 = 自动烧卡，必须显式。
- 判据：agent 生成的图在界面上有 `agent` 标记，且必须人工/显式 API 才运行。

## 五、实施顺序（4 阶段，每阶段独立可交付）

| 阶段 | 内容 | 判据（可执行） |
|---|---|---|
| **P0 后端三件套** | `GET /api/node-catalog`、`/api/workflows` CRUD、`POST /api/graph/validate` + `/dry-run`；扩 `NodeSpec`；`portcheck.go` | curl 建图 201；非法图 400 带 code；dry-run 给出依赖清单 + 区间；`go test ./...` 绿 |

## 六、不许破的硬约束

1. **前端不许硬编码节点类型**。调色板/检查器/连线校验全部读 `GET /api/node-catalog`。
2. **画布不许绕过校验**。保存与运行前必须过四段校验，`error` 级一律拒绝。
3. **不许为画布新增执行器**。执行体只有 `engine_v2_nodes.go` 一处。
4. **`pipelines.json` 的 `bind` / `when` 语义不许破**（`pipeline_test.go` 钉住）。
5. **不许猜参数**。缺必填就报错点名，不静默填默认值（v1 的"我明明填了却没生效"就是这么来的）。
6. **`qc` 默认关**。质量循环贵 3–4 倍，不能在画布上默认打开。

## 七、风险与未验证

- **体积**：v1 用的是 `@xyflow/react ^12.3.0`，gzip 约 130–150KB。与 v2 的"轻"目标冲突。取舍：画布做成**独立懒加载 chunk**，出片台首屏不加载。
- **工作量为估算**：P0 ≈ 600–800 行 Go + 3 个测试文件；P1 ≈ 800–1200 行 TSX；P2 ≈ 1500–2500 行 TSX。未实测。
- **`unknown` 只读策略**会让 v1 老图全部打不开。若你希望"尽力打开"，需要节点别名映射表（`if_else→?`），这会引入语义猜测，我倾向不做。
- **当前工作树有 16 个文件未提交改动**（`git status`）。动手前先落盘/提交，否则 P0 的改动会和别人正在改的东西混在一起。
- **本文档的第七节写于编码前**，落地结果见下一节。

## 八、落地记录（2026-10-29 夜，P0 + P1 已实现）

### 8.1 新增了什么

### 8.2 四处偏离原计划（各自都有实测理由）

| 原计划 | 实际 | 为什么改 |
|---|---|---|
| 类型不匹配 = `error`，拒绝保存 | 降为 **warn（死线）** | 现网 `image_edit` 流水线 `start-1(text) → up-1(只收 image)` 会被自家校验拦下。这条线是纯执行顺序依赖，运行期无害（引擎把上游产物并进 map，节点按 key 取）。 |
| 只做「类型不匹配」检查 | 新增 `input_unreachable` = **error** | 真正该拦的是它掩盖的洞：必填输入既无兼容入边、节点自身也没值。这才是 v1「我明明连了却没生效」的正面修法。 |
| 模板入库（`origin='template'`），保存时禁止覆盖 | 模板**不入库**，按 `pipelines.json` 现生成 | 入库会让模板与产品漂移（改 JSON 后库里的模板还是旧的）。现生成永不过期，代价是毫秒级 `Build`。 |
| 非法图 `validate` 返回 400 | `validate`/`dry-run` 返回 **200 + ok 布尔** | 它们是「查询」，用 4xx 会让前端丢掉详情；**保存**仍然是 400 + 报告。 |

### 8.4 运行入口（当晚补齐）

计划的 P2 收尾件是「画布的图能跑」。已实现 `POST /api/workflows/:id/run`：

- 与流水线出片**同一条链路**：`p.preflight` → `vramBlockNow` → `queue.EnqueueClass` →
  `engine.ExecuteWithRunID`。没有另开运行时，因此门控、队列分道、取消语义全部继承。
- 运行前**再校验一次**三层（结构/端口/参数）：保存时的校验挡不住"保存后被手改的库记录"。
- `PipelineID` 记成 `graph:<id>`（质检时 `graph:<id>:qc`）；`/runs/:id/rerun` 对这类运行
  自动分流回同一张图，不会掉进「没有这条流水线」。
- `qc=true` 开质量循环，语义与流水线完全一致：内层图落成 `qc:` 临时工作流，
  外层换 `start → quality_loop → end`，跑完即删。**预检与参数校验仍对内层图做。**
- 失败路径会 `dropTransient`，不留空壳。

验证：`verify-exe-isolated.py` 的画布段共 **34 条断言全 PASS**（成品 exe、隔离端口、deps 不自动启动），
包含：节点目录 12 种且都带中文名/成本/端口、10 条模板零阻断且有坐标、合法图 201、
必填输入没来源 → 400 + `input_unreachable`、干跑四档单调且无单一总时长、运行不存在的图 → 404、
合法图运行 → 202 且带 `run_id`、删除 200。

### 8.5 两条我写错的假设（记下来，别重犯）

| 我当时以为 | 实际 | 教训 |
|---|---|---|
| 依赖没起时运行图一定 503 | ComfyUI **不按"是否在跑"拦**——引擎会 `ensureComfy` 按需拉起，只有"拉不起来"才拦。所以 t2i 图在 deps 没起时正常 202 | 断言前先读判定逻辑，别按直觉写验收 |
| "TTS 没起"可以作为 503 的样本 | 本机 TTS 在 **:8101** 活着（ls 只看到 8103 不可达就下了结论），`caps.TTS.OK=true`，所以还是 202 | 端口不可达 ≠ 服务不可用；探活要按配置的 base_url 探，别自己猜端口 |

结果：运行断言改成**与环境无关**的三条（不存在 404 / 被拦带 error / 入队带 run_id / 绝不 500）。
验收里凡是"取决于这台机器此刻状态"的东西，都不该写成断言。

### 8.6 没验证的部分（老实清单）

- **没有真机跑一次「画布 → 保存 → 运行 → 出片」**。运行链路的守门（400/404/202）与
  qc 包壳（单测 `TestWrapGraphQCBuildsShell`）都验过，但**没有让一张画布图真的生成出画面/音频**。
  那需要 GPU 与几分钟，本轮未做。
- **没有在浏览器里目视过画布**。React Flow 的拖拽/连线/缩放只在类型与打包层面验证过；
  jsdom 跑不了它（要 ResizeObserver），所以前端测试只覆盖纯逻辑（10 条）。
- **估算误差未标定**。基准取自 AGENTS 既有实测点（88.7s@CK 12 步、130s@1 镜、45–60s@flux），
  但**没有做「预估 vs 实测」回归**（计划判据：抽 10 次 run，p50 误差 ≤30%）。
- **`type_mismatch` 降级为 warn 后，画布对"连错线"的阻断力变弱**。这是有意的取舍
  （宁可提示也不拦合法图），但用户把 image 连到 text 上只会看到黄色提醒，不是红色错误。

## 九、P3 收尾：`comfy` 逃生舱节点（2026-10-30 凌晨）

### 9.1 它解决什么

12 种节点只覆盖已封装的链路。社区工作流（ControlNet 组合、自定义采样器、双阶段放大）
永远封装不完——用户遇到没封装的玩法就会绕开 FlowEdge 直连 ComfyUI，「统御工作流」落空。
`comfy` 节点把**用户自备的 ComfyUI API 图**接进画布，并且照旧受管辖：
GPU 道排队、显存单侧驻留、节点超时、取消语义、产物归集一个不少。

### 9.2 设计边界（刻意不做的三件事）

1. **不解释图的语义**：质量门只看技术项，不做"画面好不好"的判断。
2. **运行期不查 /object_info**：那是 dry-run 的职责；运行期再查会把"实例刚被卸载"变成假失败。
   真缺模型时把 ComfyUI 的原话原样带出来。
3. **占位符不兜底**：模板用了 `{{prompt}}` 而节点没拿到值 → 显式报错。
   悄悄填空串的后果是"跑成功但画面是空的"。支持的占位符只有
   `{{prompt}} {{image}} {{width}} {{height}} {{seed}}`——多了会变成一门语言。

### 9.4 两个修正（写的时候就修了）

- **未知实例名必须先拦**。`ensureComfy` 对不认识的实例名会静默退回默认实例——
  不拦的后果是用户选了 h3 写错成 h4，图被提交到默认实例，表现为"跑成功了但不是我要的实例"。
- **`{{width}}` 等数值占位符没填就不写值**，让替换函数报"缺什么"，
  而不是填 "0"（宽 0 的图 ComfyUI 必然拒绝，且报错看不懂）。
