## 二、优化一：`command` 节点

### 定位（写进代码注释与项目手册，不只是文档）

它是 **`agent_task` 的确定性对偶**：

| | `agent_task` | `command` |
|---|---|---|
| 干什么 | 把需要判断的活儿交给智能体 | 跑我们自己的东西并如实报告 |
| 可复现 | **不承诺**，输出带 `nondeterministic: true` | 同一命令同一输入必然同一结论 |
| 典型用法 | 改代码、写文案、给意见 | 跑测试、跑构建、调校验脚本 |

编排里最需要的就是这两者相邻：**agent 改，command 验**。

### 参数与输出

| 参数 | 说明 |
|---|---|
| `command` | 可执行文件名或绝对路径。**不经 shell，argv 逐个传参**，因此没有注入面 |
| `args` | JSON 数组优先（`["a","b c"]`），否则按空白分隔；支持 `{{input}}` 占位 |
| `workdir` | 工作目录，不存在直接报错而不是静默用 cwd |
| `timeout_ms` | 默认 2 分钟，受引擎 30 分钟硬上限约束 |
| `fail_on_nonzero` | 默认 **true**：命令挂了图必须挂。设 false 才往下传，但 `exit_code` 如实记录 |

输出：`text`（stdout）、`status_code`（退出码）、`stderr`、`elapsed_ms`、`truncated`。

单流输出上限 512KB，超了截断并置 `truncated` —— 不设限会让一次 run 把内存和事件日志吃穿。

### 超时的正确姿势

`exec.CommandContext` 只杀父进程。`python` 会拉子进程、`npm` 会拉 node，超时后残留子进程会继续吃 CPU。所以超时后复用既有的 `killAgentTree` 补一刀，杀整棵进程树。

### 安全边界（说清楚，不含糊）

引擎是本地单用户工具，`agent_task` 早就能起任意命令，所以本节点**不扩大攻击面**。真正的收益是**可审计**：「跑了什么」写在节点参数里、进任务书（`spec?format=md`），而不是藏在某个 agent 的临时决定里。

## 三、优化二：运行级并发配额

### 问题

```go
func agentMaxConcurrency() int { n := 2 ... }   // 引擎级，改一次要改环境变量 + 重启
```

配额是**运行级**参数：同一张图在不同机器、不同 agent 上能扛的并发完全不同（实测 dsh headless 一个约 300MB，Claude Code 是几百 MB 到几 GB）。引擎级硬编码还带来一个副作用：**两次并发 run 会互相抢名额**。

### 改法

配额池放进 context，生命周期等于一次运行：

```go
ctx = withRunControl(ctx, rc)
ctx = withAgentPool(ctx, rc.AgentConcurrency())   // 0 = 用引擎默认，行为与改动前完全一致
```

`acquireAgentSlot` 返回**实际使用的池**，释放时交回同一个 —— 不让 Release 去猜，因为猜错的后果是漏释放名额（表现为「第二次运行凭空少一个并发位」）。

调用侧：

```bash
POST /api/workflows/120/run
{"invoked_by":"workbuddy","agent_concurrency":3, ...}
```

越界值（<0 或 >16）返回 400 `bad_agent_concurrency`，不静默截断。

### 增加的测试（3 个，钉住机制而不是钉住数字）

| 用例 | 盯什么 |
|---|---|
| `TestAgentPoolHonorsRunQuota` | 配额 3 就真能进 3 个，第 4 个必须等（超时 ctx 验证）；归还一个后能立刻再拿到 |
| `TestAgentPoolFallsBackToEngineDefault` | 没声明时走引擎默认池，且运行级池与默认池**不是同一个对象** |
| `TestRunControlAgentConcurrency` | 越界值退回 0（=用默认）而不是把配额设成 0 个；nil 控制对象安全 |

## 四、优化后评测（同一天紧邻两次跑，只改一个变量）

图结构不变（9 节点 / 3 路扇出 / 汇聚 / 门），只把两个 `http_request` 换成 `command`：

```
start → prep(command) → fix-a/b/c(agent_task ×3) → judge(command) → gate(if_else) → end-ok / end-fail
```

| 组 | 审图方式 | agent 并发 | 墙钟 | 三个 agent 耗时 | 判分 | 结果 |
|---|---|---|---|---|---|---|
| 优化前 run1（上午） | http_request + 常驻 svc | 2（默认） | 135.6s | 58.3 / 73.2 / 74.8 | 1546ms | 29/29 |
| 优化前 run2（上午） | 同上 | 2 | 155.5s | 78.9 / 84.2 / 75.1 | 744ms | 29/29 |
| **优化后 c3（下午）** | **command** | **3** | **196.8s** | 193.9 / 147.4 / 146.6 | 1545ms | 29/29 |
| **优化后 c2（下午）** | **command** | 2 | **256.6s** | 141.5 / 110.5 / 120.5 | 1824ms | 29/29 |

### 归因：机制是对的，而且能和排队模型对上

下午两次紧邻、只有并发数不同：

- **c2**：2 路并行，第三路排队 → 141.5 + 120.5 = **262s**，实测 256.6s（差 2%）
- **c3**：3 路齐跑 → max(193.9) + 少量开销 = **196.8s**，实测吻合

**省 59.8s / 23%**。配额 2 时第三路干等第一路那 141.5s，这是纯浪费。

### 为什么上午 135.6s 比下午 196.8s 还快

不是引擎退步，是上游模型池下午变慢：agent 单次耗时从 58–75s 涨到 110–194s。
**而 agent 越慢，并行收益越大** —— 上午子任务小，启动成本摊不薄；下午子任务重，并行立刻划算。
这正好回答了上一轮「编排比单智能体慢」的疑问：那是任务规模的问题，不是编排方向的问题。

### 判分环节对比

| | 优化前 | 优化后 |
|---|---|---|
| 依赖 | 常驻 `svc.py`（HTTP 服务） | 无外部进程 |
| 耗时 | 1546ms / 744ms | 1545ms / 1824ms |
| 失败面 | 服务没起 → 整图废 | 命令失败 → 节点报错，原因就在 stderr |

耗时同级，**省掉的是一个常驻进程和它带来的失败面**。
