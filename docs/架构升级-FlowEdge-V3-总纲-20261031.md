# FlowEdge V3 架构升级总纲（2026-10-31）

> 本文是**决策文档**，不是功能清单。它回答三个问题：FE 到底该是什么、底层哪七处结构错了、按什么顺序改。
> 每条判断都带证据（文件:行 / 实测数字），每条改动都带**可测判据**。没有判据的条目一律视为未定义。
> 外部对标见同目录 `调研-GitHub机制对标-20261031.md`、`调研-前沿论文可落地清单-20261031.md`。

## 0. 一页结论

### 0.1 定位（一句话）

**FE 是「本地、单卡、可验收、成本可承诺的 AI 制片流水线」。**

不是节点工具，不是云平台，不是通用编排器。三条都不做，三条的活都干。

| 对手类型 | 代表 | 它们强在哪 | 它们的**结构性**硬伤（不是功能缺失，是形态决定的） |
|---|---|---|---|
| 节点工具 | ComfyUI / InvokeAI / SwarmUI | 能力上限极高、社区节点海量、任意图 | 每次从零搭；**没有验收**（出片好坏靠人眼）；没有成本模型；没有"这一版比上一版好在哪"的度量 |
| 云平台 | Runway / Kling / Veo / Pika | 画质与稳定性领先 | 按次付费、不可审计、隐私外流、**管线不可改**、不能批量本地跑、不能拿权重自己调 |
| 通用编排 | n8n / Dify / Langflow / Airflow | DAG、重试、可观测成熟 | **不生产媒体**：没有显存仲裁、没有模态驻留、没有媒体验收、没有帧级/音轨级语义 |

**结论：FE 的竞争空间不在"谁能生成得更好"，而在"谁能把生成变成可交付的生产"。**
画质由模型决定（H3/FLUX 已够用），而**可验收、可复现、可承诺成本、跨片资产复用**由架构决定——这四件事云平台不给你，节点工具做不到。

### 0.2 五条护城河（按"别人复制的难度"排序）

| # | 护城河 | 现状 | V3 目标 | 为什么别人难复制 |
|---|---|---|---|---|
| M1 | **验收闭环**（生成 → 量化验收 → 定点重拍 → 再验收） | 已有雏形：段级 ASR 验词、接缝色温门、`verify-media.py` 四件套、quality_loop 带 repairPatch | 升级为**五维质量向量**（保真/可控/创意/物理/常识，对齐 VBench-2.0），每片留基线 | 需要"媒体语义 + 模型能力 + 重拍执行"三者同栈，云平台不开放重拍粒度 |
| M2 | **单卡资源编排**（显存单侧驻留 + 侧别感知 + 批量构图 + 空闲回收） | 成熟：`vram_idle.go` / `engine_v2.go:989` 侧别分组 / `comfy_media_batch.go` 批量 2× | 加**预测性预热**与**跨 run 复用已加载权重** | 云平台不需要（它有无穷卡），本地工具做不到（它们不托管进程） |
| M3 | **确定性复现**（全量血缘 + 内容寻址） | **缺**：`shotCacheKey` 只哈希 prompt/宽高/帧/步数/backend/turbo/pdd，**不含权重版本、seed、参考图 hash** | ArtifactStore：key = 全量输入 hash，manifest 落盘，run 引用 | 需要把"模型/权重/参数/参考图"全当数据管；节点工具把这些散在 UI 里 |
| M4 | **成本/时间承诺**（跑前给区间、跑中超预算可停、跑完对账） | **缺**：只有 EWMA ETA 与 `shotCostSeconds` 估算，无预算门、无对账 | 预算门 + 预估区间 + 实耗对账（GPU 秒/墙钟/成本三项） | 需要精确的节点级耗时模型，且敢在跑之前承诺 |
| M5 | **跨片资产复用**（角色圣经 / 场景库 / 风格卡 / 镜头库） | **缺**：`characters`/`style` 是每片手填的字符串 | Asset Library + SceneState 持久化，越用越一致、越用越快 | 这是**复利**：用得越久越难被替代，云平台账号级资产不可迁移 |

> M1+M2+M3 是"现在就有、但没被当成产品卖点"的；M4+M5 是"必须新建"的。四条加起来 = 从"玩具"到"生产线"的分界。

### 0.3 底层七处结构性缺陷（诊断摘要，详见 §2）

| # | 缺陷 | 一句话后果 |
|---|---|---|
| D1 | 执行器是**层屏障 BFS**，不是数据流 | 同层等最慢的；无法"边生成边配音"；重试只能整节点重跑 |
| D2 | **无内容寻址与血缘** | 换权重/换参考图，缓存照样命中 → 拿旧片当新片；三个月后无法复现任何一版 |
| D3 | 类型系统是**warn 级** + 元数据双写 | 契约靠人记；加节点漏一处就静默失效 |
| D4 | 质量层只有**低层指标** | 能证明"有画面、有声音"，不能证明"这版比那版好" |
| D5 | **无预算模型** | 用户问"30 秒片要多久"，只能回"看情况" |
| D6 | 能力面窄（14 节点，无音乐/lip-sync/VLM 质检/相机控制/3D） | 竞品一条指令能做的，FE 要人肉拼接 |
| D7 | 交互层薄（4 页，无时间线/逐镜编辑/对比） | 引擎再强，用户摸不到 |

### 0.4 升级节奏（先改地基，再加能力）

- **P0（1 周，零 GPU 成本，纯代码）**：D2 血缘与内容寻址、D5 预算门、D4 补两维质量（身份一致性 + 美学）。→ 这三项**不需要重跑任何片子**就能验证，且立刻把 M3/M4 变成可卖的东西。
- **P1（2–3 周）**：D1 执行器数据流化 + 部分重跑、逐镜 A/B 择优、SceneState 跨镜记忆。
- **P2（3–4 周）**：D6 补音乐 + lip-sync + VLM 质检；D7 时间线编辑器。
- **P3（探索）**：3D/动作控制、模板与插件市场。

## 1. 竞争定位：FE 该占哪一格

### 1.1 三维坐标系

把"AI 出片"拆成三个正交维度，就能看出谁占哪一格：

| 维度 | 取值 | 谁占 |
|---|---|---|
| **控制粒度** | 一句话出片 ←→ 任意 DAG | 云平台在左端；ComfyUI 在右端 |
| **交付确定性** | 抽卡 ←→ 可验收可复现 | 几乎所有人都在左端；**FE 要在右端** |
| **成本归属** | 按次付费 ←→ 自有硬件边际成本≈0 | 云平台在左端；本地工具在右端但没利用 |

**FE 的位置：控制粒度中右（预置流水线 + 画布兜底）、交付确定性极右、成本归属极右。**

这个格子现在基本空着：
- ComfyUI 有能力但没确定性（无验收、无血缘、无成本模型）；
- 云平台有确定性（SLA）但没控制权（管线不可改、不可审计）；
- 本地工作流工具（n8n/Dify）有编排但不懂媒体。

### 1.2 一句话卖点（对外）

> **"别人的 AI 视频是抽卡，FE 的是能验收的成片。"**
> 每一版都有指标、有血缘、有预算对账；不满意的地方**只重拍那一镜**，不重来一遍。

### 1.3 三个必须承认的劣势（诚实清单，写进产品预期）

1. **画质上限受限于本地模型**：H3 在 608×352 下的细节不如 Veo/Kling 的 1080p。FE 的解法是"用确定性和可控性换画质上限"——不跟它们比单帧，比"能不能稳定交付 30 秒叙事片"。
2. **单卡串行，吞吐有限**：同时只能跑一条重任务。这不是 bug，是物理。FE 的解法是"把等待变成可预期的等待"（预算门 + ETA + 队列可见）。
3. **无社区节点生态**：ComfyUI 有上万节点。FE 的解法是"不追求节点数量，追求 14 个节点的完成度"+ 保留 `comfy` 逃生舱（任意 ComfyUI 工作流可挂进来）。

## 2. 现状架构解剖（带证据）

### 2.1 执行内核：分层屏障 BFS

**证据**：`backend/service/engine_v2.go:722-1063`

```
for len(current) > 0 {           // 一层
    // 层内：light 全速并行 + heavy 按侧别分组、组间屏障
    launch(light); ...
    for _, s := range sideOrder { launch(heavy[s]); hwg.Wait() }   // :1026-1033
    wg.Wait()                                                     // :1036 层屏障
    current = next
}
```

**事实**：
- 拓扑正确性由 `remaining[]` 前驱计数保证，`join=any` 可提前入队（:771）——这部分设计是对的。
- 但 `wg.Wait()` 在层尾是**硬屏障**：同层内任一节点慢，全层等它。
- 侧别分组（扩散→语言→语音）是**有意的**优化（减少换侧，:989-997 注释写明"换侧是最贵开销"），但它把"并行"进一步降级为"按侧别串行"。

**后果（用户可感知）**：
- 一条图里若有 `[出图, 出视频, 配音]` 三个互不依赖的节点，理论上可 3 个协程推进（受显存约束），实际被侧别屏障串成 3 段，且每段都要等最慢的。
- 更致命的是**无法流水线**：30 秒 6 镜的片子，第 1 镜出完本可以立刻开始配音，现在必须等全部镜出完（因为都在同一个 `shotlist` 节点内部串行——见 2.2）。

**判据（现状）**：`CoexistCount()/SideSwitchCount()` 已有计数器（`engine_v2.go:172-194`），但**没有"同层空转率"指标**——即"层尾等待时间 / 层总耗时"。这是 V3 要补的第一个可观测指标。

### 2.2 节点粒度：一镜是黑盒，整段是黑盒

**证据**：`shotlist.go:191-1065`（`execShotListNode` 一个函数 875 行）

节点内部自己做：分镜循环 → 批量分组 → TTS 前置 → 提交 ComfyUI → 逐镜 ASR 验词 → 定点重拍 → 装配 → 响度归一 → 声床 → 字幕。

**好的部分（已经很强，别推翻）**：
- 定点重拍（:395 注释"单镜验收不过就只重跑那一镜"）
- shot-cache（:404-448）
- 段级门 `segment_retry`（:343）
- 批量构图 `batchRunLen`（:554）

**问题**：
1. **重试粒度在节点边界**：`shotlist` 节点失败 → 引擎层重试 = **整片重来**（虽然 shot-cache 能救回已生成的镜，但 TTS/装配/门检全部重做）。用户看到的是"跑了 12 分钟，第 6 镜挂了，又从第 1 镜开始"。
2. **进度是事件流，不是状态**：`emitShotProgress`（:1307）发 `shot=3 phase=generating`，但**没有持久化"每镜状态机"**。刷新页面后不知道第 3 镜到底在哪一步，断点续跑只能从节点级 `persist`（:1057 每层落库）恢复。
3. **875 行单函数**：任何一镜的新能力（比如加 lip-sync）都要改这个巨型函数，回归面巨大。

**判据（现状）**：一次 6 镜片，第 5 镜失败后的**重跑成本** = 1 镜生成 + 装配 + 门检 ≈ 2–3 分钟；目标应 ≤ 1 镜生成时间（即只重跑那 1 镜，装配/门检走增量）。

### 2.3 缓存与血缘：内容寻址是残的

**证据**：`shotlist.go` 的 `shotCacheKey`

```go
fmt.Fprintf(h, "%s\x00%d\x00%d\x00%d\x00%d\x00%s\x00%t\x00%t\x00%s",
    prompt, width, height, frames, steps, backend, turbo, pdd, shotCacheVersion)
```

**缺什么**（每一条都对应一次真实风险）：
| 缺失项 | 后果 |
|---|---|
| **权重版本 / 模型文件 hash** | W4A8 转正时（v2.8.1）靠人改 `shotCacheVersion` 规避；忘改就拿旧权重的片当新片 |
| **seed** | 同参数不同 seed 会命中同一缓存 → 无法做 seed A/B |
| **参考图 hash** | 换定妆图不失效 → 角色长相变了但缓存仍命中 |
| **LoRA / 工作流版本** | 换 PDD LoRA 不失效 |
| **prompt_opt 结果** | 提示词优化是 LLM 生成的，同一原始 prompt 可能优化出不同文本 → 缓存键却是原始 prompt |

**更根本的问题**：**没有任何"这次运行用了什么"的清单**。`runs` 表记 params，节点记 output，但没有 manifest：`{模型: sha256, 权重: sha256, seed, 完整参数, 上游产物 hash}`。所以：
- 三个月后无法复现任何一版；
- 无法回答"这版比上周那版好在哪"（因为不知道除了 prompt 还有什么变了）；
- 无法做"同一输入换权重"的对照实验（这是模型升级的唯一可靠方法）。

### 2.4 类型系统与元数据：双写 + warn 级

**证据**：
- `nodespec.go`（调度元数据：Side/Heavy/Timeout）与 `nodecatalog.go`（端口/字段/成本/Label）两张表；
- AGENTS 已记录"两张表键集合不一致时 `nodecatalog_test.go` 立刻红"——这是**靠测试兜住的约定**，不是类型保证；
- `type_mismatch` 是 warn 不是 error（AGENTS §0.16）。

**后果**：加一个节点要改 3 处（spec、catalog、执行器注册），漏一处不会编译报错，只在运行期静默失效（`pipelines.json` 的 `bind` 漏写就是这个家族，AGENTS 已记录一次）。

**判据**：`nodecatalog_test.go` 只能保证"键集合一致"，保证不了"端口语义一致"（比如 `shotlist.out.path` 是视频还是图片）。

### 2.5 质量层：能证明"有"，不能证明"好"

**证据**：`quality_gate.go`（gateRules/probeGateMedia/runGateChecks）+ `filmgates.go` + `verify-media.py`

现有度量：
- 低层：流列表、帧数、时长、静音缺口、响度（mean/max）、削波
- 语义：ASR 验词（`verifyDialogueLine`）、场景锁句字节全等、色温 U/V 漂移 >6
- 结构：分镜 plan 审计（轴线/光比/节拍/冷开场）

**缺的（正是"质量"二字的实质）**：
| 维度 | 现状 | 需要 |
|---|---|---|
| 身份一致性 | 人眼抽帧 | **量化**：跨镜角色 embedding 相似度（DINOv2/CLIP）+ 阈值 |
| 美学质量 | 无 | Q-Align/one-align 本地打分（VBench-2.0 的 Creativity 维） |
| 物理合理性 | 无 | VLM 抽帧问答（"手有几根手指""杯子有没有穿模"） |
| 可控性 | 部分（提示词 audit） | 生成是否真的遵循了分镜表（镜头类型/运动/构图） |
| 常识 | 无 | VLM judge |

**判据**：现在无法回答"这版和上版哪个好"——只能回答"这版有没有坏"。V3 要求每次出片产出**质量向量**（5 维 0–1），存 manifest，可跨版本比较。

### 2.6 资源与调度：强，但缺"预测"

**证据**：`gpu_scheduler.go`、`queue.go`（GPU 道串行/CPU 道并行）、`vram_idle.go`、`comfy_media_batch.go`、`engine_v2.go:989` 侧别分组

**已有（这在开源里属于领先水平，要写进对标文档）**：
- 显存单侧驻留 + 换侧前卸载 + 轮询 `vram_free≥16GB`
- 空闲 600s 统一回收（TTS /unload + ComfyUI /free + Ollama keep_alive=0，进程保留）
- 批量构图 2×（屏障节点两阶段）
- 队列分道（GPU 串行 / CPU 并行）+ 入队不阻塞 + 可取消

**缺**：
1. **无预测性预热**：知道下一镜要用 H3，但现在才 3 秒后要 TTS → 无法"提前 30 秒开始加载下一个模型"（因为换侧是互斥的，但可以在"另一侧空闲窗口"预载）。
2. **无跨 run 复用策略**：run A 跑完卸不卸？现在统一 600s 回收。若用户 30 秒后要跑第二条，重新冷加载 180s。应该"按队列深度决定卸不卸"（队列非空 → 不卸）。
3. **无资源账单**：不记录"这次跑了多少 GPU 秒、峰值显存多少、电费多少"。

### 2.7 交互层：4 个页面，没有"片场"

**证据**：`frontend/src/pages/`：ProducePage(16KB)、CanvasPage(24KB)、RunsPage(15KB)、ArtifactsPage(8KB)

**缺**：
- **没有时间线**：30 秒 6 镜的片，用户看不到"第 3 镜在哪一秒、它的台词是什么、它和前后镜怎么接"。
- **没有逐镜操作**：想重拍第 4 镜，只能改 prompt 重跑整片（或手动调 API）。
- **没有 A/B 对比**：两版并排播放、逐帧对比、指标对比。
- **没有资产库**：角色/场景/风格散落在 prompt 字符串里。

**判据**：用户从"看片"到"改一镜再出片"的**操作步数**：现状 ≈ 6–10 步（改 JSON/重跑整片）；目标 ≤ 2 步（点该镜 → 改参数 → 重拍）。

## 3. 目标架构 V3：五层

```
┌─────────────────────────────────────────────────────────────┐
│ L4 交互层  ProducePage / TimelinePage / ShotInspector / A-B  │
│            时间线 · 逐镜编辑 · 对比 · 资产库                  │
├─────────────────────────────────────────────────────────────┤
│ L3 质量层  QualityVector(5维) · VLM Judge · 定点重拍策略      │
│            identity/aesthetic/physics/control/commonsense    │
├─────────────────────────────────────────────────────────────┤
│ L2 能力层  Node Registry(单表) · Modality Adapters            │
│            image / video / audio / music / lipsync / 3d      │
├─────────────────────────────────────────────────────────────┤
│ L1 执行层  Ready-Queue Scheduler · Side-Aware · Budget Gate   │
│            partial rerun · 预算/ETA/对账 · 预测性预热         │
├─────────────────────────────────────────────────────────────┤
│ L0 资产层  Content-Addressed Artifact Store · Manifest        │
│            key=hash(全量输入) · 血缘 · 跨片复用               │
└─────────────────────────────────────────────────────────────┘
```

### 3.1 L0 资产层：内容寻址 + 清单（P0，最高优先）

**目标**：任何产物都能回答"你是谁生的"（血缘）与"重跑一次会不会一样"（确定性）。

**设计**：
```go
// service/artifact_store.go
type ArtifactKey struct {
    NodeType   string            // "text2video"
    Params     map[string]any    // 节点 data 全量（排序后序列化）
    ModelID    string            // "h3-ref2va-w4a8"
    ModelHash  string            // 权重文件 sha256 前 16（启动时算一次，缓存）
    Seed       int64
    InputsHash string            // 上游产物 hash 的串联
    CodeVer    string            // 引擎版本 + shotCacheVersion
}
func (k ArtifactKey) Hash() string   // sha256(规范 JSON)[:32]

type Manifest struct {
    RunID, NodeID string
    Key           string
    Artifacts     []ArtifactRef      // path, sha256, bytes, media meta
    Timing        Timing             // queued/gen/load/total
    Resources     Resources          // gpu_seconds, peak_vram_mb
    Quality       *QualityVector     // L3 回填
    Env           map[string]string  // 驱动/ComfyUI/venv 版本
}
```

**关键约束（防踩坑）**：
- 缓存**默认关**，`FE_ARTIFACT_CACHE=1` 才开——因为 AGENTS 已明确"缓存命中会让重跑变成假重跑"。V3 不是把缓存加回来，而是把**血缘**加回来；缓存只是血缘的一个可选消费者。
- 命中必须**校验产物 hash**，且 manifest 里记 `cache_hit: true`，UI 必须显示"复用"，不允许静默复用。

**判据**：
1. 同一参数连跑两次，第二次 manifest 的 `key` 相同，产物 sha256 相同（若缓存关闭，则两次独立生成，key 仍相同 → 证明 key 完备）。
2. 改权重文件（哪怕同路径）→ `ModelHash` 变 → key 变 → 不命中。
3. 改参考图 → `InputsHash` 变 → key 变。
4. `GET /api/runs/:id/manifest` 返回上述结构，且能据此**离线复现**（脚本 `replay-manifest`）。

### 3.2 L1 执行层：从层屏障到就绪队列（P1）

**目标**：节点完成即触发下游，不再等整层；重试粒度降到"子步骤"。

**设计**：
```go
// 就绪队列替代分层循环
type scheduler struct {
    ready   chan string      // 前驱全满足的节点
    slots   chan struct{}    // 总并发
    sideSem map[string]chan struct{}  // 每侧一个令牌（扩散=1，语言=1，语音=1）
}
```
- 每个节点完成后 `propagate` → 递减前驱 → 若归零则 `ready <- id`。
- **侧别令牌**替代侧别屏障：同侧并发受令牌限制，跨侧天然可重叠（扩散与语音真的能同时跑，只要显存允许——这由 `VRAMCoexist` 决定，已有开关）。
- **保留**"换侧前卸载"的正确性：换侧由令牌 + 显存仲裁共同决定，不再靠"整层串行"这种粗粒度保证。

**风险控制**：保留 `sideAwareOff` 回退路径（已存在，:1017），新调度器用开关 `FE_SCHEDULER=ready` 切换，默认仍走旧路径，A/B 通过后再改默认。

**判据**（可测，不需要真跑 GPU）：
- 构造 `A(3s) → B` 与 `C(10s) → D` 两条独立链的图，旧调度总耗时 ≈ 10s + B+D，新调度 ≈ max(3+B, 10+D)。
- 单测：`scheduler_test.go` 用 sleep 节点钉住"就绪即跑"。

### 3.3 L1 预算门（P0）

**目标**：跑之前给区间，跑中超预算可停，跑完对账。

**设计**：
```go
type Budget struct {
    MaxWallClock time.Duration  // 墙钟上限
    MaxGPUSeconds float64       // GPU 秒上限
    OnExceed     string         // "stop" | "warn" | "continue"
}
```
- `POST /api/produce` 新增可选 `budget`；`POST /api/preflight` 返回**区间**（P50/P90，来自历史 EWMA + 分镜表规模），而不是单值。
- 运行中每个节点完成 → 累加实耗 → 超限按 `OnExceed` 处理（stop = 优雅取消并保留已完成产物）。
- 完成后写对账：`{predicted_p50, predicted_p90, actual, gpu_seconds, peak_vram}`。

**判据**：连续 3 次真跑，`actual` 落在 `[p50, p90]` 内的比例 ≥ 2/3；超限时 `stop` 真的停（进程退出、ComfyUI 被 interrupt）。

### 3.4 L2 能力层：单表注册 + 模态适配器（P1/P2）

**目标**：加节点只改一处；每个模态有统一接口。

**设计**：
```go
type NodeDef struct {
    Type     string
    Side     string          // "" | diffusion | language | audio | music
    Heavy    bool
    Ports    Ports           // in/out 类型（强类型，validate 用它判 error）
    Fields   []FieldDef      // UI 与校验同源
    Cost     CostModel       // 用于预算门
    Exec     NodeExecutor
}
var Registry = map[string]NodeDef{}
```
- `nodespec.go` 与 `nodecatalog.go` 合并为 `Registry`，编译期单源。
- `Ports` 强类型化：`type_mismatch` 从 warn 升为 error **仅在画布新建图时**；旧图/流水线保持 warn（兼容）。

**判据**：删掉 `nodecatalog.go` 后 `go build` 仍通过，且 `/api/node-catalog` 输出字段与旧版逐字段相等（用快照测试钉住）。

### 3.5 L3 质量层：五维向量（P0 起）

**目标**：从"有没有坏"升级到"好不好、比上版如何"。

**五维（对齐 VBench-2.0）**：
| 维 | 度量 | 本地实现 | 成本 |
|---|---|---|---|
| Human Fidelity | 身份一致性（跨镜 DINOv2 相似度）+ 面部清晰度 | DINOv2-small / CLIP ViT-L（本地已有 ComfyUI venv） | 秒级 |
| Controllability | 分镜遵循度（镜头类型/运动/构图是否与 plan 一致） | VLM 抽帧问答（Ollama qwen2.5-vl 或本地 VLM） | 10–30s/片 |
| Creativity | 美学分 | Q-Align / one-align（pyiqa） | 秒级/帧 |
| Physics | 物理合理性 | VLM judge（"有无穿模/多指/漂浮"） | 10–30s |
| Commonsense | 常识 | VLM judge | 同上 |

**判据**：同一 prompt 跑 2 个 seed，五维分差 ≥ 0.05 才认为"有区分度"（否则指标无意义，需换模型）；人工抽检 10 个样本，VLM 判"坏"的与人工判"坏"的一致率 ≥ 70%。

### 3.6 L4 交互层：时间线 + 逐镜（P2）

**目标**：从"填表单"到"剪片"。

**最小可用形态**：
- `TimelinePage`：横向时间轴，每镜一个块（缩略图 + 时长 + 台词），点击 → `ShotInspector`（该镜 prompt/seed/参考图/质量分/重拍按钮）。
- `CompareView`：两版并排（同步播放 + 指标 diff）。
- 资产库：角色/场景/风格卡片，可拖进 shot。

**判据**：改一镜并重拍的操作步数 ≤ 3；重拍只跑该镜（日志可见 `shot=4 only`）。

## 4. 多模态能力补强（D6）

每个模态按「现状 → 缺口 → 借鉴源 → 成本」给，落地位置精确到文件。

| 模态 | 现状 | 缺口 | 借鉴源 | 成本 | 优先级 |
|---|---|---|---|---|---|
| **图** | FLUX 文生图、image2image、inpaint、upscale | 无局部重绘强度控制、无参考风格迁移、无批量变体择优 | ComfyUI 的 IPAdapter/ControlNet 生态；InvokeAI 的统一画布 | S | P2 |
| **视** | H3 文生/图生视频、多镜 film、Ref2VA 身份锁 | 无相机运动控制、无轨迹控制、无 lip-sync、无首尾帧插值 | HoloCine（镜间稀疏条件 → 工程化为 SceneState）；ControlNet 系 | M | P1/P2 |
| **音-语音** | Kokoro / edge-tts（CPU，音色确定） | 无情感/语速细控、无多角色对话自动分轨 | Chatterbox / CosyVoice2 / IndexTTS（本地） | S | P2 |
| **音-音乐** | **无**（只有 brown-noise 声床） | 无 BGM 生成、无与画面节拍对齐 | Stable Audio Open / MusicGen（本地，小模型可跑 24GB） | M | P2 |
| **字** | text_overlay（libass SRT 烧录） | 无动效字幕、无关键词高亮 | Remotion（AGENTS 已记产品介绍片首选） | S | P2 |
| **代码视频** | code_video（Canvas 逐帧） | 只有 blueprint 一种风格 | lemo-opuscar 59 种风格（已有库） | S | P1 |
| **3D** | **无** | 无 image-to-3D、无动作 | Hunyuan3D / Trellis（24GB 可行但慢） | L | P3 |
| **VLM 质检** | 有 `visionModel` 探测（capabilities.go:148） | 无 judge 流程、无打分卡 | Q-Align / one-align + Ollama VLM | S | P0 |

**关键判断**：**音乐生成是最高性价比的缺口**。理由：
1. 现在所有片子靠"声床"糊，观感差一档；
2. 本地小模型（Stable Audio Open 1.1GB / MusicGen-small）24GB 完全够；
3. 它是**唯一能让"片子像片子"的低成本增量**（画质提升要换模型，音乐只要加一个节点）。

## 10. 外部机制吸收（来自 `调研-GitHub机制对标-20261031.md`）

调研结论里有一条判断直接改变了本方案的优先级排序，先写在这：

> **"FE 的节点缓存已删"不是判断失误，是缺「失效声明位」的必然结果。**
> ComfyUI 把声明权给节点作者（`IS_CHANGED`）、Nextflow 给流程作者（`cache` 严格度）、
> Prefect 给调用者（`cache_key_fn`）、Snakemake 给用户（`--rerun-triggers`）——FE 四处都没有，
> 所以只能"全关"。先加一个声明位，默认打开缓存才安全。

这解释了为什么 §3.1 的设计里"缓存默认关、只加血缘"是对的，但**不该是终局**。

### 10.1 十二条机制 → FE 落点

| # | 机制（来源） | FE 落点 | 成本 | 依赖 |
|---|---|---|---|---|
| 1 | 缓存严格度四档 `false/true/deep/lenient`（Nextflow） | `ArtifactKey` 加 `strictness` 字段；抽卡类节点 `false`，纯函数节点（超分/字幕/贴字）`deep` | S | §3.1 已备好 key |
| 2 | 缓存键 = 输入 + **节点实现版本** + 运行域（Prefect） | `ArtifactKey.Code` 已有引擎版本，需再拆出**单节点实现版本**（节点源码 hash 或手写 `implVer`） | S | 同上 |
| 3 | 失败语义二维表（Argo `retryPolicy` + Dagster `allow_retries=False` + Temporal Activity 默认重试） | `NodeDef` 加 `RetryPolicy{可重试性, 需人工}`；把"显存被抢/台词念错/锁句不全/502"四类分开 | M | L2 单表注册 |
| 4 | `heartbeat_timeout`：卡住 ≠ 死了（Temporal） | 节点超时改为"多久没有新进度"；ComfyUI `/progress` 可转发为心跳 | M | L1 执行层 |
| 5 | 产物元数据带 `node_id + 参数快照 + 可作输入类型`（InvokeAI staging / Krita layer） | **Manifest 已含 params + artifacts**，缺"可作输入类型"；补一个 `usable_as` 字段即可让产物回流成节点 | S | §3.1 已落地 |
| 6 | 局部执行：只跑选中输出的上游分支（ComfyUI Partial Execution） | 画布"跑到这里"按钮；依赖 §3.1 血缘做增量判定 | S | §3.1 |
| 7 | 按文件名自动连边（Snakemake） | 画布同模板内：`output` 名 == `input` 名即自动连 | S | 无 |
| 8 | `--rerun-triggers` 五维含 **software-env**（Snakemake） | `ArtifactKey` 补 `env`（ComfyUI 版本 + torch 版本）；换 ComfyUI 后旧产物自动失效 | S | §3.1 |
| 9 | `dvc.lock` 旁挂依赖 md5 + 参数（DVC） | Manifest 就是 FE 的 `dvc.lock`；再加一个 `fe.lock` 供 git 提交（只含 key，不含产物） | S | §3.1 |
| 10 | step pin / mock：钉住满意的第 2 镜，只重跑第 3 镜（Windmill） | shot-cache 已有能力，缺**显式 pin**语义：`pinned: true` 的镜跳过一切重拍 | S | shotlist |
| 11 | asset check：一条产物 → N 条具名 check + severity（Dagster） | `verify-media.py` 已输出逐项结果；把它接成 `GateCheck[]`（name/severity/passed/value），与 §3.5 五维合并 | S | L3 |
| 12 | 会话域取消：只停当前批次，不停别的（SwarmUI） | `/runs/:id/cancel` 已是按 run；缺"批量取消"（`POST /api/runs/cancel?tag=xxx`） | S | 无 |

### 10.2 三条洞察 → 架构含义

1. **缓存键的分歧不是"哈希什么"，而是"谁有权声明失效"** → §3.1 的 `ArtifactKey` 必须预留 `strictness` 与 `invalidators` 字段（现在留空也要留位）。
2. **长任务编排的分水岭是"失败语义分类"，不是重试次数** → §3.2 的调度器改造必须**同时**做失败分类，否则只是把串行变并行，四类失败仍走一个分支。
3. **"统一画布"三家都不是画布更强，而是产物与画布同源** → §3.6 的 L4 重点不是"再做一个画布"，而是**让产物能一键回流成节点输入**（`usable_as` + 参数快照）。

### 10.3 调研明确劝退（已并入 §6 反例清单）

整套 Temporal/Argo/Nextflow（瓶颈在显存不在调度）、全局 `deep` 缓存、恢复节点缓存为默认、每帧实时（H3 冷加载 60–180s）、容器化编排、全量 OTel/Prometheus/Grafana、默认用 mtime 当失效触发器（Windows 跨盘不可靠）、"错误作为返回值"套到全部节点。

| 模型指纹（首尾 1MB 快速摘要 + 纳秒 mtime + 落盘缓存） | 同上 | `TestFingerprintCache_DetectsChange` / `_Persist`：同尺寸替换也能检出 |

| run 完成后自动写清单 + 回写路径 | `backend/handler/produce.go`（`writeRunManifest`） | 编译 + handler 测试 |
| `GET /api/runs/:runId/manifest` | 同上（`GetManifest`）+ `backend/main.go` 路由 | `TestGetManifest`：200 / 404（无清单说明原因）/ 404（run 不存在）/ 400（非法 id） |

**未验证的部分（诚实清单）**：
- 尚未在**真实出片**上跑过一次 manifest 生成（需要 GPU + 几分钟），所以 `writeRunManifest` 的真机路径未验证；
- 模型指纹解析依赖 `ModelsRoot` 扫描，若权重放在非默认目录且未设 `FLOWEDGE_MODELS_DIR`，会记 `unavailable:<name>`（不静默丢失，但需要人看）；
- `data/pipelines.json` 曾带 UTF-8 BOM 导致 handler 测试全红（已修，备份在 `.tmp/pipelines.json.bom-bak`）——这类"文件编码污染"应进 CI 检查。

## 11. 论文深读的结论（`调研-前沿论文深读-20261031.md`）——修正本方案的优先级

深读（7 主题 / 57 个 arXiv ID）给出一条直接修正 §0.4 节奏的判断：

> **FE 的真瓶颈不是模型不够强，是缺一层把「画面内容对不对」变成可执行诊断的东西。**
> 7 个方向里，只有「编排层 + 提示词层」在 24GB 单卡上是净收益——全部不需要新权重、不需要训练。

这条推翻了本方案把 L3 质量层排在 P2 的安排。**质量层不是"等能力补齐后再说"的收尾工作，它是成本最低、收益最直接的一项**：
改 VLM 判词协议不需要写引擎代码，却能把「数值全绿但画面崩」这类最贵的失败挡在交付前。

### 11.1 三条"本周就能做"（已并入 P0 尾部）

| # | 动作 | 论文 | 落点 | 判据 |
|---|---|---|---|---|
| ① | **参考镜排序 + 自动抽帧进 `ref_images`**：先拍最容易拍清的那一镜，自动抽帧当参考，不再靠人肉挑图 | GroundShot (2606.20799) | `shotlist` 的 plan 排序 + 抽帧 + `ref_images` 组装三处，不碰生成链路 | 同提示词两镜，第 2 镜抽帧与参考帧的颜色/结构比对（复用现有 U/V 均值逻辑）；副指标 `scene_lock_missing` 计数 |
| ② | **`prompt_opt` 改成「诊断—分型—定点修复」**：替换现在的"扩写式"重写 | TARA (2607.18724) | `service/prompt_opt.go` | 10 条历史失败 case 回归：audit 全绿率上升且抽帧不被改坏；每条 case 记分型与算子（天然满足"一轮只动一个变量"） |

### 11.2 为什么 ① 是"修根因"

AGENTS 已记：「只给 `characters` + 普通提示，第 2 镜会漂成黑发女仆；Ref2VA 六段式 + 3 张参考图才锁住」。
问题不在模型，在**参考图从哪来**——现在靠人肉挑 3 张。GroundShot 的观察是"首次清晰出现就决定了一致性天花板"，
所以正确顺序是：先拍最容易拍清的那一镜 → 从它抽帧 → 当后续镜的参考。这一步不碰生成链路，却能抬高一整条片子的天花板。

### 11.3 第二梯队与劝退（摘要）

- 第二梯队：3×3 身份拼图（ARGUS）、上一镜末帧进参考（FilmWeaver）、定向重拍（CoAgent，依赖 ③ 的诊断输出）、音乐+卡点（DiffSynth-Music，**只在氛围片开放**，知识科普片按 AGENTS 不加 BGM）。
- 劝退的核心逻辑不是"论文不行"，是**硬件不匹配**：Windows torch 无 triton ⇒ 全部定制 kernel 路线（Sparse-vDiT / VORTA / VMonarch / SALAD）不可行；FPSAttention 是 Hopper 专用；DMD2 自训要 teacher+student+critic 共存而 H3 权重已 20.5GB；端到端多镜（EchoShot / MultiShotMaster / ShotAdapter）需重训；相机轨迹需 3D 栈（FE 无 3D）。
- TeaCache 的 A/B **不要直接上**：8 步蒸馏模型上缓存收益会缩水，先 `h3-bench.py --teacache` 对比再决定默认值。
