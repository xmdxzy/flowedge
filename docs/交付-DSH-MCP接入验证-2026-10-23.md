## 1. 做了什么

只改了一个文件：`~/.dsh/cordis.patch.yml`，在 `xuce-hub-mcp` 之后追加 `flowedge-mcp` 条目。

```yaml
- id: flowedge-mcp
  name: "@deepseek-ai/dsh-mcp-client"
  config:
    serverName: flowedge
    transport: stdio
    command: 'C:\Users\Administrator\Desktop\flowedge\运行\FlowEdge.exe'
    args: ['--mcp']
    env:
      NO_PROXY: '127.0.0.1,localhost'
      no_proxy: '127.0.0.1,localhost'
    toolCallTimeoutMs: 300000
```

备份：`~/.dsh/cordis.patch.yml.bak-flowedge-20261023`

要点：

- **`FlowEdge.exe --mcp` 是瘦客户端**：只做 stdio ↔ `127.0.0.1:8080` 的 HTTP 转发，不在 stdio 进程里初始化引擎。否则两个引擎会抢同一张卡的显存和同一个 sqlite（`backend/mcp/server.go:7-11` 的架构选择）。
- **前置条件：引擎必须在跑。** 没起时每个工具返回「能照做的错误」，不是超时或空结果。
- `NO_PROXY` 是必需的：本机常驻 `http_proxy=127.0.0.1:5751` 会把回环请求劫持成假 502（AGENTS §0.6）。
- `toolCallTimeoutMs: 300000`：`flowedge_estimate` 要算显存与耗时，`generate_image` 是同步生成，5 分钟是下限。

### 2.2 子进程真实拉起（最硬的一条）

```
PID    PPID   创建时间              命令行                     父进程身份

12080  13160  2026-10-23 13:09:42  FlowEdge.exe --mcp         DeepSeek Harness.exe
```

父进程 PID 与命令行由 `Get-CimInstance Win32_Process` 核对：6868 = `@deepseek-ai/dsh/lib/bin.js web --port 4715 --host 127.0.0.1`，13160 = `DeepSeek Harness.exe ... --dsh\profiles\desktop`。

> 附带事实：DSH 有 web（4715）和桌面端两个运行时，各自拉一个 stdio 子进程。所以引擎不可达时会出现两条报错源，这是设计使然而非重复拉起。

## 3. 未完成：模型侧没有发起 tool_call

三次尝试，全部失败，原因分层清楚：

| # | 配置 | 结果 | 归因 |
|---|---|---|---|
| 1 | headless 默认（opencode-go-free / longcat-2.5-preview-free） | `MISSING_CREDENTIAL: OPENCODE_API_KEY 未设置` | headless profile 里 **credentials 插件被 `disabled: true`**，`.credentials.yaml` 的 refs 读不到 |
| 2 | `--patch` 打开 credentials | `PI_AI_ERROR 402: Upstream request failed: Endpoint is unavailable` | opencode.ai 免费池两个模型（step-5-preview-free / longcat-2.5-preview-free）全部不可用 |
| 3 | `--patch` 换本机 Ollama `qwen2.5:14b` | 模型正常回复，但**不调用任何工具**，反问"你想让我做什么" | 14B 在 DSH 的 agent loop 里不服从工具调用 |

第 3 条排除了"Ollama 不支持"这个可能：直连 `/v1/chat/completions`（含 `stream:true` + tools）能正确返回 `tool_calls`，模型侧能力没问题，是 DSH harness 的提示结构对 14B 太重。

**没有为此改动用户的 DSH 配置**：headless profile 未改，两个临时 patch 只在 `.tmp/` 里（`dsh-cred-patch.yml` / `dsh-ollama-patch.yml`），带 `--patch` 显式引用才生效。

## 4. 怎么用（给张越）

- **不需要重启 DSH。** 改 `cordis.patch.yml` 后热加载，几秒内拉起子进程。
- 引擎要先起：`curl --noproxy '*' 127.0.0.1:8080/api/health` 返回 200。
- 在 DSH 里直接说人话即可：「列出 FlowEdge 工作流」「取 #113 的任务书」「跑一下 #113」。工具以 `mcp__flowedge__*` 暴露。
- **让 DSH 提交运行时，务必让它填 `invoked_by: "dsh"`**——引擎会把运行记录标成 dsh，和 WorkBuddy 的调用分开统计（`backend/mcp/server.go` 的 `invoked_by` 枚举）。
- 回滚：删掉 `cordis.patch.yml` 里 `flowedge-mcp` 整段，或覆盖回 `.bak-flowedge-20261023`。

## 5. 对「DSH 比 WorkBuddy 更适合 FlowEdge 吗」的实测回答

原始论点有两半，实测各有归属：

| 论点 | 实测结论 |
|---|---|
| 「DSH 干净，WorkBuddy 原生 harness 会干扰工作流」 | **成立**：WorkBuddy 每会话注入全局 AGENTS.md + MEMORY.md（规则 1–17）+ 三层记忆；DSH 只注入工作区 AGENTS.md，接入本次只加了一个 20 行配置块 |
| 「所以 FlowEdge 在 DSH 上跑更好」 | **不成立**：FlowEdge 是独立服务，两边都只是客户端；且 DSH 当前**自己跑不动**——免费池 402、本地 14B 不服从工具调用。WorkBuddy 侧的模型链是稳的 |

**接入成本对比（实测）**：DSH 侧 = 20 行 YAML，零代码改动，热加载生效。这个成本低到值得长期保留两条通道。

**真正的分工**：DSH 适合当**无人值守的执行器**（干净、无审批打断、常驻 web 端口可远程）；WorkBuddy 适合当**带纪律的编排者**（铁律注入、验收脚本、交付协议）。两边共用同一份 spec 任务书——**纪律写在产物里，不写在 harness 里**，这才是让「谁调用都行」成立的唯一办法。
