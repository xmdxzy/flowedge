# 对照实验：DSH 自己跑 vs 引擎图指导 DSH 跑同一个任务

> 日期：2026-10-24 06:10–06:27 · 资产 `.tmp/expr-bench/`
> 任务：exprkit（5 阶段从零实现，73 条用例，基线 1/73）

## 一、结论

| 路线 | 墙钟 | 用例 | 调用次数 | 说明 |
|---|---|---|---|---|
| **DSH 一把梭** | **164.1s** | 73/73 | 1 次 | 一个 headless 进程，看完整契约 + 全部测试 |
| **FE 引擎图指导** | **738.4s** | 73/73 | 5 次（+5 个验收门） | 五段串行，每段只做一段，每段跑本段测试 |

**同一份代码、同一个模型（deepseek-v4.1-flash）、同一个适配器、同一条判分器。FE 慢 4.5 倍。**

两条都是 73/73、`cheated=false`，**正确性没有差别，差别只在墙钟与可观测性**。

## 二、FE 那 738 秒花在哪

| 节点 | 耗时 | 说明 |
|---|---|---|
| prep（建副本） | 5s | command 节点，跑 benchctl |
| s1 词法 | 60s | 13 条测试 |
| g1 验收 | ~0s | 门只花毫秒 |
| s2 语法 | **251s** | 14 条测试，最长的一段 |
| g2 验收 | ~0s | |
| s3 求值 | 90s | 13 条测试 |
| g3 验收 | ~0s | |
| s4 函数 | 166s | 17 条测试 |
| g4 验收 | 10s | |
| s5 接口 | 156s | 16 条测试 |
| g5 验收 | ~0s | |
| judge 全量 | ~2s | 73 条 |
| **合计** | **738.4s** | 五个 agent 平均 145s/段 |

**对比**：solo 用 **164s 做完了同样五段**，平均每段 33s。

差距来自三处，按影响排序：

1. **每段都要冷启动** —— dsh 一个进程起一次要加载插件、读配置、连模型（15–60s 不等）。solo 只付一次，FE 付五次。
2. **上下文不继承** —— solo 在同一个会话里从 stage1 写到 stage5，前面写过的接口它记得；FE 每段是全新会话，只能靠 prompt 里的"上游接口摘要"重建认知。s2 之所以花 251s，正是因为它要重建 parse 需要的 Token/AST 认知。
3. **验收门本身很便宜**（毫秒级），但它把失败暴露在段边界上，这在全绿场景下不产生收益。

## 三、一个意外的发现：FE 的 prep 节点其实在防一件事

第一次跑 solo 时出现了很有意思的失败：

```
elapsed_s: 225.4   grade: 1/73   stdout: 0 chars
```

但 stderr 里 agent 说"Everything done / 73 tests, 0 failures"，而且确实有一份 **73/73 全绿**的实现——**它写到了 `runs/final/work`**，那是几小时前另一轮实验留下的目录，不是这次指定的 `runs/dsh-solo/work`。

也就是说：**agent 把活干对了，但落在了错误的目录里**。它从历史上下文里"记住"了一个看起来更合理的路径。

在 prompt 里加了硬边界（"只允许在 `{work}` 内读写，不要凭记忆去改历史实验目录"）后重跑，164.1s 干净跑完、落点正确。

**这件事恰好说明 FE 的 prep 节点有个隐形价值**：它每轮强制 `rm/rename` 旧目录、从 fixture 重新 copytree。agent 想跑偏也跑不偏——**环境隔离是编排给的，不是 agent 自觉的**。

## 四、这轮顺带修的两个适配器 bug

| bug | 症状 | 修法 |
|---|---|---|
| `UnboundLocalError: adir` | 传 `--result` 时直接崩，agent 的产出全丢（stdout 0 字节） | 缩进错误：`stem`/`result_path` 掉到 `if` 外面了，挪回去 |
| 目录带偏 | agent 写到历史批次目录 | prompt 加边界约束（见 §三） |

第一个 bug 很值得记：**它让一次成功的任务看起来像完全失败**（判分 1/73）。如果没有去翻 stderr，就会把"agent 干完了但适配器崩了"记成"agent 不行"。

## 五、什么时候该用哪个

| 场景 | 选 solo | 选 FE 图 |
|---|---|---|
| 任务能被一个上下文装下（≤5 个文件） | ✅ 快 4.5 倍 | |
| 失败代价高、需要中途止损 | | ✅ 段边界有门 |
| 需要局部重跑（只有一段错） | | ✅ 只重跑那一段 |
| 需要可观测（每段耗时/产物可见） | | ✅ 节点级留痕 |
| 需要环境隔离（防 agent 跑偏） | | ✅ prep 强制重建 |
| 长流程但每段都短（<60 行） | ✅ | |

**一句话**：这次 exprkit 属于第一类——五个阶段加起来才 200 行，一个上下文完全装得下，拆开反而把固定成本付了五次。

**如果任务大到单上下文装不下**（比如 20 个文件、跨模块重构），FE 的收益才会显现：不是因为快，而是因为**每一段都在可控的上下文窗口里**。
