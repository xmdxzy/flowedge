# 交付：节点面板重构 + 能力卡片系统（2026-10-22 凌晨）

承接上一轮「模块契约 + 任务书」，这轮做两件事：
**① 把六个面板问题改掉；② 给每个节点加上「能力卡片」（智能体 / 技能 / 工作流封装）。**

---

## 一、六项面板改造

| # | 要求 | 落点 | 关键判断 |
|---|---|---|---|
| 1 | end 只留节点类型 | `NodeInspector.tsx`：删掉说明段与变量块 | 结束节点没有任何参数，面板越空越快 |
| 2 | 文生图去掉批量提示词 / 提示词 / 可用变量 | 同上，重写 text2image 区块 | 提示词**只有一个来源**（上游文本），少一个输入框就少一处"两处真相" |
| 3 | 中文自动翻译"评估必要性" | 三态：`off / auto / force` | **auto 只在语言模型已驻留时翻**——为一次翻译多付 180 秒换侧不划算 |
| 4 | LLM 模型改下拉 | `<select>`：自动探测 / 本机 Ollama / 我的模型 | 数据来自已有的 `GET /api/models`（`ollama_models`） |
| 5 | LLM 去掉"自定义提示词" | 改「任务预设」：画面改写 / 中译英 / 分镜表 / 摘要 / 自定义 | 空文本框里模型只会把输入当聊天问题回答，预设把角色与输出格式写死 |
| 6 | 工具调用更好用 | 每行带"什么时候会被调用"+ 最多轮数 + 失败即中止 + 上次 trace | 4 个无说明胶囊换成有解释的行；轮数从写死的 4 变成可配 |

### 3 的结论（单独说）
auto_translate 原来的实现是"检测到 CJK 就用同一个 Ollama 翻一遍"，位置在 `enterSide(diffusion)` **之前**。
所以：链里已有 LLM 时几乎免费；单独一个文生图节点则要**先加载 LLM、再卸载、再加载 flux**。
因此不删，改为三态，默认 off；`auto` 只在 `ResidentSide()==language` 时才翻，否则跳过并在输出里留痕。

## 二、能力卡片系统

### 三类卡，语义不同（不能混为一谈）

| 类型 | 是什么 | 贴上去发生什么 | 形状（视觉编码） |
|---|---|---|---|
| **智能体** `agent` | 一段稳定的角色设定 + 默认工具 | 节点改用这张卡的角色与工具（**提示词以卡片为准**） | 圆 + 外环 |
| **技能** `skill` | 一次确定性文本变换 | 节点做一次同输入必同输出的变换 | 六边形 |
| **工作流** `workflow` | 一整条已保存的工作流 | 节点被**替换成一次子工作流调用**（唯一改执行结构的一类） | 三层堆叠 |

形状先区分、颜色只做第二重编码 —— 色弱用户也能分辨。

### 落地位置

| 层 | 文件 | 说明 |
|---|---|---|
| 契约与内置卡 | `backend/service/cards.go` | 4 张智能体卡 + 5 张技能卡内置；`data/cards.json` 可覆盖同 ID、追加新 ID |
| 目录接口 | `backend/handler/cards.go` → `GET /api/cards` | agents / skills / workflows（后者从 workflows 表派生，不用另存） |
| 执行期拦截 | `engine_v2.go:executeNode` | `binding.kind=workflow` → 走 `executeInnerWorkflow`（含嵌套深度保护） |
| 提示词注入 | `engine_v2_nodes.go:execLLMNode` | `binding.kind=agent/skill` → 用卡片 system 替换节点 prompt；agent 还带默认工具（节点勾选优先） |
| 选择器 | `frontend/src/components/CardPicker.tsx` | 三页签 + 卡片列表 + 生效说明 |
| 画布徽章 | `App.tsx` 的 `withCardBadge` HOC | 一次包装 20 种节点类型（含以后新增的），不用逐个改 |

### 为什么徽章用 HOC 而不是改 20 个组件
徽章是**统一表达**。改组件会得到 20 份略有差异的实现，且新加节点必然漏一次。

### 为什么卡片不写成节点类型
卡片是**内容**不是**结构**。同样一张「短剧导演」卡可以贴在任何文本节点上、也可以同时贴三处；
做成节点类型立刻是 "10 节点 × N 卡" 的组合爆炸，还会让 spec / 端口 / 调度被迫认识每个内容变体。
贴卡只改参数与提示词，不改端口、侧别、依赖。

## 三、自定义模型端点（LLM Profile）

| 项 | 实现 |
|---|---|
| 存储 | `data/llm-profiles.json`（`service/llm_profiles.go`）；与 `models.json`（扩散权重）分开两张表 |
| 接口 | `GET/PUT /api/llm/profiles`；PUT **整体替换**，保存时校验名字唯一 / model 非空 / base_url 合法 |
| 鉴权 | profile 只存**凭据名**；密钥在 `credentials.json`（已加密）。请求头用 `authTransport` 统一注入 |
| 为什么用 Transport | LLM 有 6 处请求构造点（chat / stream / tools / unload / vision…），逐处加等于 6 个漏写点，漏写的症状是"某个功能 401，其他都好" |
| 执行 | `execLLMNode` 解析 `llm_profile` → 克隆独立的 `LLMService`（不动共享实例）；**自定义端点不做流式**（协议未必一致，硬套会得到空结果） |
| 编辑入口 | 配置 · 模型 → 自定义模型（`LLMProfilesEditor.tsx`） |

## 五、未验证 / 已知缺口（不假装）

1. **美术未做像素级验证**。截图通道当前报 "exceeds 10 MiB"（高 DPI 页面）且 clip 被忽略；
   三类卡片的形状/配色只核到"进了产物包 + tsc 通过"，**没有在浏览器里看一眼**。
2. **工作流卡的端口不做校验**：把一个输出 image 的节点换成输出 text 的工作流，图能存、任务书会标端口不匹配，但保存期不拦。
3. **agent/skill 卡只对 LLM 节点生效**（`execLLMNode` 内注入）。贴到别的节点上，UI 会明确警告"不会生效"，但后端不做二次拦截。
4. **`data/cards.json` 没有生成模板**：用户要自定义得自己照 `cards.go` 里的结构写；目前只有内置卡可用。
5. **自定义端点的流式被关掉**（非流式），这是有意取舍，不是遗漏。
6. **exe 未部署**：8080 上跑的还是旧二进制，需你手动替换（`运行\3-应用更新并重启.bat`）。
