## 一、为什么换题目

上一轮的 `tinykit`（3 模块 / 6 缺陷 / 29 用例 / 单阶段）暴露了一个问题：
任务太小，三个 agent 的启动成本摊不薄，编排反而是负优化。所以这一轮换成**多阶段、有依赖、有性能硬约束**的任务。

## 二、任务：`minipipe` —— 日志分析与报表管道

四个阶段串成一条真实链路：

```
日志文本 → parse（解析）→ stats（聚合）→ window（滑窗）→ report（报表）
```

| 模块 | 待办项 | 性质 |
|---|---|---|
| `pkg/parse.py` | `LEVELS` 缺 `WARN=30` | 正确性 |
| | `parse_ts` 用本地时区解释 `Z` 时间戳 | 正确性（跨时区不一致） |
| | `parse_many` 未实现（脏行容错） | 缺失功能 |
| `pkg/stats.py` | `percentile` 用最近秩而非线性插值 | 正确性 |
| | `group_by` 缺失键落到 `None` 而不是 `unknown` | 正确性 |
| | `histogram` 未实现 | 缺失功能 |
| `pkg/report.py` | `to_csv` 不按 RFC 4180 转义逗号/引号/换行 | 正确性 |
| | `render_table` 未实现（等宽表格） | 缺失功能 |
| `pkg/window.py` | `moving_avg` 开头窗口越界（切片起点为负） | 正确性（抛异常） |
| | `rolling_max` 是 O(n·k)，15 万元素 k=3000 需 5 秒内 | **性能硬约束** |

**9 项待办**，其中 1 项是算法级性能要求（必须换单调队列，不能靠调参）。

判分：**68 条用例**（parse 15 / stats 16 / report 16 / window 12 / integration 7 + 其他），
分成 4 个单元阶段 + 1 个端到端阶段。

**基线冻结：27 / 68**（14 failures + 27 errors，判分耗时 9.0s，因为性能用例真的在跑 O(n·k)）。

判分口径与上一轮一致：跑全量 unittest + `tests/` 逐文件 sha256 + skip/xfail 扫描，作弊判 0。

## 三、四条路线

| 路线 | 执行体 | 编排 | 说明 |
|---|---|---|---|
| ① | **DSH** | FlowEdge | 12 节点图：4 路并行修模块 → 合并判分 → **集成收尾 agent** → 复判 → 门 |
| ② | **WorkBuddy** | FlowEdge | 同一张图，`agent_id` 换成 `workbuddy-cli` |
| ③ | **DSH** | 无 | 单进程一次跑完全部 9 项 |
| ④ | **WorkBuddy** | 无 | WorkBuddy 会话自身执行（工具链直接改文件） |

图结构（12 节点 / 6 拓扑层）：

```
start → prep(建 4 副本)
      ├→ fix-parse  ├→ fix-stats  ├→ fix-report  └→ fix-window
           └────── 4 路汇聚 ──────→ merge(只取 owned 文件 + 越界检测)
                                        → judge-1（中间判分，留证据）
                                        → fix-int（集成收尾，可改任意 pkg 文件）
                                        → judge-2（复判）
                                        → if_else 门 → end-ok / end-fail
```

设计要点：**并行负责"各自能修的"，串行负责"必须一起对的"**。集成测试天然依赖四个模块同时正确，
所以它不能塞进任何一条并行支线——这正是多流程编排要表达的东西。

## 四、阻塞：资源治理器按游戏保护模式拒绝启动

```
POST /api/workflows/:id/run → 429
{
  "code": "governor_declined",
  "error": "资源紧张，本次运行已推迟",
  "governor": {"allowed": false, "weight": 3, "level": "critical",
               "reasons": ["游戏保护模式"]}
}
```

实测进程（只读检查，2026-10-23 17:19）：

| 进程 | 内存 |
|---|---|
| `LeagueClient.exe` | 1,250,324 K |
| `RiotClientServices.exe` | 332,588 K |
| `wegame.exe` | 433,832 K |
| `LeagueClientUx*.exe` × 3 | ~350,000 K |

这是治理器按设计工作，不是故障。四条路线每条都要起 1–4 个 agent 子进程（每个 Node/DSH 几百 MB），
与对局抢 CPU 和内存，因此**按保护策略全部推迟**。

已确认清理干净：隔离引擎实例（8081）无监听、我起的评测脚本全部退出，
5 个残留 python 全是用户常驻服务（face_score / ComfyUI-H3 / ComfyUI-MOSS / TTS ×2），不是我起的。

## 七、已知的公平性问题（先写下来，跑完照此解读）

1. **路线 ④ 的执行者是 fixture 的作者**：我知道缺陷在哪，速度必然偏快。因此 ④ 的耗时只能当"人机协作下限"看，
   不能与 ①③ 直接比较；能比较的是"结果是否达到 68/68"和"是否作弊"。
2. **路线 ② 大概率拿不到结果**：WorkBuddy CLI 的 `-p` / `--serve` / `--acp` / `--bg` 四条通道
   在本机全部静默（`--help`/`--version` 正常，业务初始化后无任何输出）。② 的价值是**把这条通路的现状钉成证据**，
   而不是产生一个成绩。
3. **上游模型池波动**：上一轮实测同一模型单次任务耗时可以从 58s 涨到 194s。
   所以四条路线必须**连续跑完再对比**，不能跨时段取数。
