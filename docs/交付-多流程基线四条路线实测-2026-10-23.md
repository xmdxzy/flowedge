# 多流程基线：四条路线的执行体对比（实测结果）

> 日期：2026-10-23 · 资产 `.tmp/pipeline-bench/` · 全部数字为实测
> 前一份设计稿：`docs/交付-多流程基线四条路线-2026-10-23.md`（含任务规格与阻塞记录）

## 一、结论先行

| 路线 | 耗时 | 结果 | 判定 |
|---|---|---|---|
| ① FlowEdge + DSH（强制集成收尾） | **1140.2s** | 68/68 | 通过，但编排设计有缺陷：白跑 820.6s |
| ①′ FlowEdge + DSH（**条件短路**） | **346.3s** | 68/68 | 通过，**比单跑快 2.4×** |
| ② FlowEdge + WorkBuddy | 5.0s | — | **通道不可用**（agent 全部失败） |
| ③ 单 DSH（无引擎） | **827.4s** | 68/68 | 通过 |
| ④ WorkBuddy 会话（无引擎） | **55.8s** | 68/68 | 通过（执行者是出题人，有信息优势） |

**三句话**：

1. **编排能不能赢，取决于图怎么画，不取决于有没有编排。** 同一张图的兜底分支让 ① 比单跑慢 38%；加一个 `if_else` 判断"已经全绿就别再兜底"，①′ 立刻比单跑快 2.4 倍。
2. **引擎侧的确定性验收是可信的**：三条能跑通的路线，判分全部 `cheated=false`，且 ① 与 ③ 走完全不同的执行路径却拿到同一个 68/68。
3. **WorkBuddy 仍然只能"人用"，不能"被程序用"**：`-p` / `--serve` / `--acp` / `--bg` 四条通道全不通，这次挖到了根因（见 §四）。

## 二、任务：`minipipe`

日志分析管道，四个阶段：**parse → stats → window → report**。

**9 项待办**：6 个正确性缺陷 + 3 个未实现功能 + 1 个性能硬约束。

| 模块 | 待办 |
|---|---|
| parse | `LEVELS` 缺 `WARN=30`；`parse_ts` 按本地时区解释 `Z`；`parse_many` 未实现 |
| stats | `percentile` 用最近秩而非线性插值；`group_by` 缺失键落 `None`；`histogram` 未实现 |
| report | `to_csv` 不按 RFC 4180 转义；`render_table` 未实现 |
| window | `moving_avg` 负索引切片越界；**`rolling_max` O(n·k)，15 万元素 k=3000 需 5 秒内** |

**68 条用例**，基线 **27/68**（14 failures + 27 errors，判分 9.0s —— 性能用例真的在跑 O(n·k)）。

判分口径三轮一致：跑全量 unittest + `tests/` 逐文件 sha256 + skip/xfail 扫描，作弊判 0。

## 三、四条路线的图与实测

### ① 引擎编排（12 节点）

```
start → prep(建 4 副本)
      ├→ fix-parse ├→ fix-stats ├→ fix-report └→ fix-window      ← 4 路并行
           └──── 汇聚 → merge(只取 owned 文件 + 越界检测)
                          → judge-1（中间判分）
                          → fix-int（集成收尾，可改任意 pkg 文件）
                          → judge-2（复判）
                          → if_else 门 → end-ok / end-fail
```

实测 **1140.2s**：

| 节点 | 耗时 |
|---|---|
| prep | 0.8s |
| fix-parse | 175.2s |
| fix-stats | 313.5s |
| fix-report | 149.9s |
| fix-window | 220.7s |
| merge | 0.5s |
| **judge-1** | 1.3s → **68/68 已全绿** |
| **fix-int** | **820.6s ← 完全白费** |
| judge-2 | 1.1s → 68/68 |

四路并行把 859.3s 的 agent 工作量压到 313.5s（压缩 2.7×），但兜底分支把省下的又吐了回去。

### ①′ 同一张图 + 一个条件分支

`judge-1 → if_else('"ok": true')`：true 直接收尾，false 才进 `fix-int`。

实测 **346.3s**，`fix-int` / `judge-2` / `gate-1` / `end-ok2` / `end-fail` 全部 `skipped`。

| | ① 强制兜底 | ①′ 条件短路 |
|---|---|---|
| 墙钟 | 1140.2s | **346.3s** |
| 省下 | — | 793.9s（**69.6%**） |
| 结果 | 68/68 | 68/68 |

差的不是能力，是**一张图里缺一个判断**。

### ② 引擎调 WorkBuddy

4 个 agent 节点全部 `failed`，整体 5.0s 结束。引擎给的错误原文：

```

wb_agent: EMPTY_OUTPUT from WorkBuddy CLI (exit=1).
stderr="Error: Cannot find module '../dist/codebuddy'
```

### ③ 单 DSH（无引擎）

**827.4s**，68/68。它自己列出修掉的 10 项，并把性能从 **8.78s 压到 0.067s**（单调队列）。

值得记一笔：它第一次判分是 66/68，并**自证**剩下 2 条是测试的差一错误（复制到 temp 只改那两行断言即全绿）。
我核对了 —— **它是对的**，是我 fixture 里两处期望值算错（`render_table` 分隔行少一格、`parse_many` 连续空行计数）。
修正测试后复核 68/68。这说明：**在带错误的规格下，agent 仍然把实现做对了，而且敢指出规格的错**。

### ④ WorkBuddy 会话（无引擎）

**55.8s**，68/68，一次通过，4 个文件全改。

**这个数字不能当能力指标**：执行者（本会话）就是题目作者，知道 9 处缺陷在哪、也知道 68 条断言的确切期望。
它的正确读法是"人机协作的下限"——**一个熟悉代码库的工程师，55 秒能交付**。

## 四、WorkBuddy 通道的根因（这次挖到了）

之前只知道 `-p` 静默。这次从引擎拿到的错误把链路指出来了：

`bin/codebuddy` 是个 launcher，它按两个开关选 bundle：

```js
const forceLiteWb = ['1','true'].includes(process.env.CODEBUDDY_FORCE_LITE_WB_BUNDLE)
const isHeadless = forceHeadless || forceLiteWb
...
if (forceLiteWb)      await importMjs('codebuddy-lite-wb.mjs')
else if (isHeadless)  require('../dist/codebuddy-headless')   // 本机没有
else                  require('../dist/codebuddy')            // 本机没有
```

本机 `dist/` 里**只有 `codebuddy-lite-wb.mjs`**，另两个 CJS bundle 不存在。
所以不设 `CODEBUDDY_FORCE_LITE_WB_BUNDLE=1` 就必然 `Cannot find module`；之前看到的"静默 exit 0"就是 launcher 在 catch 之后 `console.error + exit(1)` 被管道吞掉。

**设上之后**：bundle 能加载（不再报缺模块），但 `-p` 仍然 150 秒零输出、exit 0。
即 lite-wb 是给桌面端 Web UI 的精简构建，**根本不含非交互产出通路**。

四条通道的结论：

| 通道 | 结果 |
|---|---|
| `-p "..."` | 静默（bundle 加载成功后仍无产出） |
| `--serve --auth none` | 服务能起，所有 API `401 AUTH_REQUIRED`，`--auth none` 被忽略 |
| `--acp` | `initialize` 发出后无任何回包 |
| `--bg --name X -p` | 静默，`codebuddy ps` 挂住 |

要真正打通，需要 WorkBuddy 侧提供 headless/full bundle，或给 `--serve` 一个可用的鉴权入口。**这不是 FlowEdge 能修的**。

## 五、公平性说明（必须带着看）

1. **④ 的执行者是出题人**：55.8s 反映"熟悉代码的人"，不反映"agent 的能力"。①③ 面对的是一条只写了规格的陌生代码库。
2. **③ 比 ① 早跑了一个时段**：上游模型耗时波动很大（同一模型单次能从 149s 到 341s），所以 ① 与 ③ 的绝对值只能粗略比；① 与 ①′ 是同图同批，那两个数字的对比是硬的。
3. **② 没有成绩**：它的价值是把通路现状钉成证据，不是产出。
4. **测试被改过一次**：③ 首轮 66/68 后修正了 2 处测试自身的错误断言，① 与 ④ 从一开始就用修正后的测试。这一点对 ③ 略不利（它在错的规格下干活）。
