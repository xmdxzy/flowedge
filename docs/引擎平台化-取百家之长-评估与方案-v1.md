# FlowEdge 引擎平台化 · 取百家之长 · 评估与方案 v1

> 日期：2026-10-22 ｜ 依据：harness²（Google Research, arXiv:2610.14224）对照 + FlowEdge 源码实查 + 序策 xuce-flow 实查
> 结论先行：**FlowEdge 不该去卷"最会思考的 agent 平台"，它该成为"最不会说谎的产出平台"。**
> 它已经具备别人没有的三件东西（确定性 DAG + 数值门 + 硬件驻留约束）的唯一组合，缺的不是智能，是**两条回灌回路**。

---

## 一、定位判断：该成为什么，不该成为什么

### 1.1 三家对照的真实差异

| 系统 | 强在哪 | 弱在哪 | FlowEdge 该不该追 |
|---|---|---|---|
| ComfyUI | 节点生态、即时预览、社区工作流 | 无门、无治理、无版本、无账本 | 已借（作为执行后端），不追生态 |
| Airflow / Temporal | 幂等重跑、版本化、可恢复、可观测 | 完全不懂 GPU/显存/媒体 | **追**，且已追到 70% |
| harness² | 把"改 harness"变成有探针、有对比、有存档的闭环 | 不碰硬件、benchmark 是文本任务、无 ground truth 才靠 judge | **只借骨架，不借代码** |

**FlowEdge 的独特交集**：市面上没有第二个系统同时做到「按图执行 + 产物级数值门 + 显存单侧驻留 + 单体免安装分发」。ComfyUI 有节点没门，Airflow 有编排不懂显存，harness² 有进化不懂硬件。

### 1.2 所以不该做的事（明确写死，避免跑偏）

| 不该做 | 理由 |
|---|---|
| 把 FlowEdge 改造成通用 coding agent 框架 | 那是 OpenCode/Codex 的地盘，进去只能当第三名 |
| 引入 LLM-as-judge 做质量判定 | 你的门是数值的，引入 judge 是**主动降级**，且增加不确定性 |
| 为"更像 harness²"而引入 Python/uv 运行时 | 会毁掉 32.3MB 单 exe 这个核心卖点 |
| 让 FlowEdge 自己给自己的产出打分并宣布"改好了" | 违反「门必须有牙齿」；裁决权必须在 FlowEdge 之外 |

### 2.2 真缺的（只有两条）

> **G3 撤销（2026-10-22 动手时核实）**：原判断"run 无 paused 状态"是错的 ——
> `service/run_control.go` 有 `paused/pausedAt/reason` 三件套，`handler/debug.go`
> 有 pause/step/resume，`model.WorkflowRun` 本来就有 `PausedAt`/`PauseReason` 字段，
> 连注释都写着 `pending, running, paused, success, failed`。
> 错因：当时只 grep 了 `engine_v2.go` 里的状态字符串字面量，没查 handler 与 model。
> **这就是纪律 L 的典型：过早宣布不行。** 实际它不缺能力，只缺"把暂停次数计入评测指标"。

| # | 缺口 | 现状 | 后果 |
|---|---|---|---|
| **G1** | **压力治理** | 全库 grep `governor/pressure` 零命中。只有 `maxLoopIterations=100` 和显存 LRU | FlowEdge 能真实把机器打死：批量节点扇出、ComfyUI 队列堆积、LLM 循环空转，都不会被拦 |
| **G2** | **经验回流** | `llm_memo.go` 是问答缓存，RAG 是文档检索，都不是"改了什么+证据+适用场景" | 同一个坑换个工作流再踩一遍；改好的提示词留在某个 node.data 里没人知道 |

> 八组件对照：系统提示词✅ / 护栏✅✅（强于 harness²）/ 记忆⚠️（G2）/ 工具指引✅ / Skills✅ / 脚本✅ / 子智能体✅ / 插件✅ / 编排本身⚠️（spec 不回写）/ 人机断点✅。
> **八项全有，缺的是让它们互相喂的那条线。**

## 三、序策整合：把"单向调用"改成"双平面闭环"

### 3.1 现状：线已经有了，但只通一个方向

```
序策 xuce-flow ──(flowedge 执行器 / :30000/api/flowedge/*)──► FlowEdge COMPUTE 面
     ✅ 已通：媒体图编译、依赖预检、产物账本、血缘回溯
     ❌ 断线：FlowEdge 的探针证据回不到序策的进化 registry
```

序策侧已具备的（实查确认，**不要再造**）：

| 组件 | 位置 | 能力 |
|---|---|---|
| 资源治理器 | `xuce-flow/server/resource-governor.js`（1457 行） | 1s 采样、压力分级防抖、加权配额、死循环/劣质产出检测、分级执法、全局急停、73 断言 |
| 自进化状态机 | `%APPDATA%\Xuce\SelfEvolution\registry.json` | `proposed → evaluated → shadowing → promoted / rejected / rolled-back`
| 配对评测信封 | skill `xuce-evolution-paired-evaluation` | `{caseId, datasetFingerprint, category, passed, effectiveTokens, durationMs, critical}`，硬门禁：≥8 用例、≥2 类别、token 回归 0%、p95 延迟 ≤+10%、critical 回归 0 |
| 产物契约门 | `03-编排内核/管线质量门-规范-v1.md` | `meta.quality`（file/glob/json/stdout/dir + `newerThanStart` 防旧产物冒充）、`meta.expensive` 准入闸 |

### 3.2 目标：职责三分，权责不重叠

```
┌─────────────────────────────────────────────────────────┐
│ 序策 · 判决面（唯一有权说"更好"的地方）                  │
│   resource-governor：准不准跑                           │
│   self-evolution registry：改得对不对                   │
│   paired-evaluation：真的更好还是运气好                  │
└──────────────▲──────────────────────┬───────────────────┘
       证据信封 │                      │ 准入 / 配额
               │                      ▼
┌──────────────┴─────────────────────────────────────────┐
│ FlowEdge · 执行面（只报事实，不宣布结论）                │
│   DAG 执行 · 数值门 · 显存驻留 · 产物血缘 · 全量指标     │
└─────────────────────────────────────────────────────────┘
```

**铁律：FlowEdge 永远不自己说"我改好了"。** 它只产出符合信封的 run 记录，判决交给序策的硬门禁。这既符合「门必须有牙齿」，也天然做到"自己不能给自己打分"。

### 3.3 三条具体接缝

**接缝 A · 证据信封（最小改动，收益最大）**

run 结束时写 `运行/data/evidence/<runId>.json`，schema 直接对齐序策信封：

```json
{
  "schemaVersion": 1,
  "role": "baseline | candidate",
  "workflowId": "wf-...", "workflowVersion": 12,
  "runs": [{
    "caseId": "shot-03-night-rain",
    "datasetFingerprint": "<64位 sha256>",
    "category": "h3-video",
    "passed": true,
    "effectiveTokens": 4210,
    "durationMs": 214300,
    "critical": false,
    "gates": { "timing": 1.0, "identity": 1.0, "audio": 0.82, "technical": 1.0, "budget": 1.0 },
    "peakVramMB": 21800,
    "sideUnloadCount": 1,
    "humanInterventions": 0
  }]
}
```

字段来源全部已有：`passed` ← quality_gate 判定；`effectiveTokens` ← trace；`durationMs` ← trace；`peakVramMB` / `sideUnloadCount` ← gpu_scheduler；`humanInterventions` ← 需 G3（缺失时填 `null`，**不许填 0**）。

→ 序策直接 `--action=evaluate --baseline=a.json --contender=b.json`，不需要新增任何评测代码。

**接缝 B · 准入闸（解决 G1，不做执法只做准入）**

P0 用现成的：执行前调序策 `gov.mjs preflight --weight N`，退出码 2 就推迟。
P2 才考虑在 Go 侧内建轻量采样器（只读 `/gpu/status` + 系统负载），阈值与序策 `config.json` 同源，**不复制执法逻辑**——执法会杀进程，两边都有就是双杀风险。

**接缝 C · spec 双向化（补齐 Compose）**

现状只有 `GET /api/workflows/:id/spec`。补：

```
POST /api/workflows/:id/spec/apply
  body: { baseVersion, edits: [{ nodeId, path, from, to, reason, evidenceRef }] }
  行为: 三条硬拦（from 不匹配 → 409 / 节点不存在 → 404 / 触碰门层阈值 → 403）
        落成一个新 version，不覆盖旧版（回滚永远可用）
```

这条是把「任务书」从看板变成可写对象的唯一入口，也是 harness² 的 Compose 缺的那一半。

### 3.4 记忆与经验层：为什么不把序策的剥离给 FlowEdge（2026-10-22 评估）

> 命题：是否应把序策的经验、知识库剥离出来，专门给 FlowEdge 当记忆经验层？
> **结论：不剥离。做"可选单向导出 + 走已存在的导入通道"，不做"资产搬家"。**

#### 先看两边的真实规模（实查，不是估算）

| 资产 | 位置 | 规模 | 内容性质 | 引擎能用吗 |
|---|---|---|---|---|
| brain 语料 | `.dsh/brain/embed-edgeone` | **541MB / 2504 文件** | 某项目的整个代码库 + 向量索引 | ❌ 与出片无关 |
| 知识卡片 | `.dsh/brain/search/index` | **1388 张**（kb 1255 / builtin 103 / agent 30） | 21 字段 schema：`domain/triggers/text/weight/docKind…` | ⚠️ 分域后可 |
| 记忆沉积 | `.dsh/brain/memory-deposits.md` | 34KB | `【教训·域】+ 证据 + 状态（提案待复核）` | ❌ 引擎不读散文 |
| 铁律 | `.dsh/brain/iron_rules.md` | 6.5KB | 作业纪律（禁重启/禁杀进程/判断纪律） | ❌ 给 agent 读，不给出片引擎读 |
| 进化登记 | `%APPDATA%\Xuce\SelfEvolution\registry.json` | 430KB | `proposed→evaluated→shadowing→promoted` 状态机 | ❌ 治理记录，不是知识 |
| **FlowEdge 知识库** | `运行/data/kb` | **9 条向量 / 32KB** | 内置 `projectManual`（空库时自动灌入） | ⚠️ **内容过期** |

#### 三条反对剥离的理由（硬度递减）

| # | 理由 | 证据 |
|---|---|---|
| 1 | **边界错了**：FlowEdge 是可分发产物（32MB 单 exe）。序策记忆里含三国割草/论文/股票等私人项目记录，剥离 = 把私人记忆打进分发物 | 记忆沉积与卡片里 `domain` 覆盖全项目线 |
| 2 | **对象错了**：经验是写给"写代码的 agent"的判定纪律；FlowEdge 节点是执行器，它的 LLM 节点只吃「提示词 + 上游数据 + 检索片段」 | `memory-deposits.md` 全篇是方法论（统计单位/门控证伪/git 前置），没有一条是出片参数 |
| 3 | **收益为负**：FlowEdge 现有知识库只有 9 条且**内容是错的**，此时增加语料只会稀释命中率 | 见下节负资产清单 |

#### 但直觉对了一半：FlowEdge 确实缺"出片域经验层"

素材早就有，只是没进引擎：`AGENTS.md`（§0 作业纪律 + 各节环境坑）、`docs/多模态出片手册.md`、`MEMORY.md`（实测基准/不可用清单）、skill `local-multimodal-ops`。这些是**出片专属**的，LLM 节点与 `prompt_opt` 节点应当检索到。

#### 四个方案的取舍

| 方案 | 判定 | 理由 |
|---|---|---|
| A 把序策 brain 拆成独立服务给 FlowEdge 当记忆层 | ❌ | Node MCP vs Go 单体，跨进程依赖直接破坏单 exe 分发 |
| B 把经验/知识整体复制进 `data/kb` | ❌ | 1255 张跨项目卡片混入 → 检索噪声；私人记忆进分发物 |
| **C 按 `domain` 过滤出片域卡片，走已有 `/api/kb/import` 导入** | ✅ 次选 | 复用现成 21 字段 schema、现成导入端点与分块向量化，只装相关子集 |
| **D 内置一份"出片经验卡片"编译进 exe** | ✅ **先做** | 零外部依赖；解当前 9 条过期知识库的急；素材已在仓库里 |

顺序：**先 D（修内建负资产）→ 再 C（可选外挂个人库）**。理由：负资产没清理前，加任何语料都是往脏水里兑水。

#### 落地判据（避免做成"知识库搬运工程"）

1. 只收**出片域**（H3/flux/ffmpeg/显存/门阈值解读），不收通用作业纪律 —— 后者属序策 brain 独占
2. 卡片**编译**而非搬运：一条 = 一个可执行结论 + 证据 + 适用条件，照抄 `memory-deposits.md` 的形态
3. **负向门**：导入后跑同一组 `rag_query`，命中相关度不得低于导入前；降了就整批回退（与 §5.4 防作弊同一思路，加语料也要有门）
4. 内置卡片必须能被 `TestProjectManualCoversAllModules` 这类契约测试盯住，防止再漂

### 3.5 顺带发现的负资产：内置项目手册已过期

`service/rag_v3.go` 的 `projectManual` 是知识库种子（空库自动灌入），但内容与实现脱节：

### 3.6 Raven 对照：该借什么、不该借什么（2026-10-22 评估）

> 对象：`EverMind-AI/Raven`（Apache-2.0，★5.5k，v0.2.4，**pre-alpha**，82 个未关 issue，论文 arXiv:2609.33439）
> 一句话：**Raven 是「harness of harnesses」** —— Host Agent 把目标拆成 DAG，节点绑定「模型 + harness」对（内置 Research/Code/Design/Oncall 四个，外部 13 个预设走 ACP/CLI/OpenAI 兼容 API）。
> 它与 harness² 是同期同类问题，但答案不同：harness² 优化**一个** harness，Raven 编排**很多**个。

#### 3.6.1 三个项目独立收敛到同一组原则（这是本次评估最有价值的部分）

| 原则 | harness² | Raven | 序策 | FlowEdge 现状 |
|---|---|---|---|---|
| **改进器看不见答案** | 改进材料里删掉 criteria | 「信号里剥掉参考答案」（reference answer stripped out） | 配对信封只收 `passed` 不收评分过程 | ✅ 已做（三态 + 阈值不外露） |
| **进化器外挂，不跑在运行时里** | `harness2-judge` 独立命令 | Evolver「当库调用…develops the agents rather than running inside them」 | registry 独立状态机 | ✅ 已做（evidence.json → 序策判决） |
| **未验证不采纳** | judge 后置，失败标 unscored | 「nothing is installed before it is verified, and a failed check sends it back」 | `proposed→shadowing→promoted` 硬门禁 | ✅ 已做（`no_gate`→unscored） |

**三个互不相关的团队、三条独立路线，收敛到同一组约束。** 这不是巧合，是这类系统的结构性要求 ——
也说明我们上一轮按 harness² 做的三态/外挂判决，方向是对的，不是抄。

#### 3.6.2 能力对照（Raven vs FlowEdge）

| Raven 能力 | FlowEdge 现状 | 判断 |
|---|---|---|
| Host Agent 把**目标**编译成 DAG | ❌ **图必须人画**（或 agent 手工拼 nodes/edges JSON） | **该借，且是唯一真正拉开差距的一环** |
| 节点绑定「模型+harness」对（可换 Claude Code/Codex） | ❌ 节点是确定性执行器；`cards` 只挂 agent/skill 提示层 | **不该借**（见 3.6.4） |
| dispatch 前 admission checks | ✅ 刚做（`governor_gate.go`，200/429） | 已对齐 |
| 13 个第三方 agent 预设 | ❌ 只有 MCP 出去（外部调 FlowEdge），没有外部 agent 进来当节点 | 暂不需要：出片链路上没有「必须交给编码 agent」的环节 |
| 四策略模块 Memory/Planning/Capability/Action | ⚠️ `Modules` 是**静态契约**，不是可演化四席 | 部分该借：把「参数」与「判断」分开（见 3.6.4 第 3 条） |
| Curator 自动重写四席（实验性，不随安装包发布） | ❌ | **不该借**（见 3.6.4） |
| Evolver：候选变异/重组 + 统计筛选门 | ✅ 序策 registry 有状态机 + 配对评测（≥8 用例、token 回归 0%、p95 ≤+10%），比它严 | 已领先 |
| EverOS 跨会话记忆 | ⚠️ RAG 仅 9 条 + 序策 brain 1388 卡（见 §3.4） | 按 §3.4 的 D 方案补 |
| SkillForge（114,190 技能目录 + 微调检索） | ⚠️ `cards` 9 张内置 | 规模差 4 个数量级，但出片域不需要那么大 |
| Playbook（`playbook.md` + `raven playbook validate`） | ⚠️ `spec` 是**图→规格**（出口），没有**规格→图**（入口） | **该借**：这就是 3.6.3 的核心 |
| 默认 tracing + 失败 trace 导出做确定性回归 | ✅ `trace` / `events` / `lineage` | 已对齐；缺「trace → 回归夹具」的最后一跳 |
| DAG 内并行、失败跳过、校验 | ✅ 有 | 已对齐 |

#### 3.6.3 三家共同指向的同一个缺口：图 ↔ 规格的**双向**编译

- harness² 的 `Compose`：把编辑组合成新 harness
- Raven 的 `playbook.md`：人写规格 → `validate` → 执行（**规格 → 图**）
- FlowEdge 的 `spec`：图 → 规格（**图 → 规格**），上一轮刚补了 `spec/apply`（改图）

**FlowEdge 缺的正是「规格 → 图」。** 三个项目独立把这一步当成核心，说明它不是可选项。

#### 3.6.4 不该借的三件（附理由）

| 不该借 | 理由 |
|---|---|
| **节点变成外部 agent（ACP/CLI）** | FlowEdge 的护城河是**确定性执行器**：同 seed 同参数出同样的东西、成本可预测、显存可控。一旦节点可以"交给 Claude Code"，可复现性立刻消失，而评测的前提就是可复现（§5.5）。Raven 敢这么干是因为它的产物是"计划图+对话"，本来就不承诺可复现 |
| **Curator 自动重写策略代码** | 官方自己标 experimental 且**不随安装包发布**（`ships with the repository rather than the installed package`）。让 agent 自动改自己的判断代码，与「门必须有牙齿」直接冲突 —— 门可以被优化门的人改掉 |
| **Raven 的评测口径** | 它的 MAOB 指标是 **Node F1 / Edge F1 / Partial Order Accuracy / Exact Match Rate**，且论文「**只评分提交的计划图，不派发 worker 执行**」。也就是说它连"能不能交付"都没测。FlowEdge 的价值恰恰在那条它绕过去的路上 —— 别去对齐一个更弱的口径 |

#### 3.6.5 该借的第一件：`compose`（目标 → 图 → 任务书）

**为什么在 FlowEdge 做会比 Raven 强**：Raven 生成 DAG 之后只能靠 LLM 自检 + playbook 静态规则；
FlowEdge 生成之后有**四层现成的验伪手段**，别的项目没有：

```
1. Modules 契约   → 节点类型是否存在、必填参数是什么
2. PortKindAccepts → 每条连线两端模态是否兼容（不写节点白名单）
3. preflight      → 依赖服务是否就绪（缺什么、怎么起）
4. film-gates     → 产物是否达标（五层数值门）
```

**同样的 LLM 生成质量，有校验器的那个才可信。** 这是 FlowEdge 在这个方向上唯一的结构性优势。

接口草案：

```
POST /api/workflows/compose
{
  "goal": "30 秒竖屏修仙短片，夜间雨景，无台词，BGM 渐强",
  "constraints": { "total_seconds": 30, "aspect": "9:16", "no_speech": true },
  "reference_images": ["..."],          // 可选：走九宫格锁
  "max_repair_rounds": 2                // 校验失败回喂 LLM 重试的上限
}
→ 201 {
  "workflow_id": 57,
  "repaired_rounds": 1,
  "violations_fixed": ["port mismatch: text→image at n4→n5"],
  "spec": { ...CompileSpec 结果... },   // 任务书一并返回，人先看再决定跑不跑
  "warnings": ["node n7 必填参数无来源"]
}
```

三条设计纪律（不遵守就会变成"随机生成器"）：

1. **不自动 run.** 生成图是"提案"，跑是"决定"。Raven 是对话即执行，FlowEdge 必须留这一道 —— 出片成本是分钟到小时级。
2. **校验失败回喂而不是直接报错.** 把违规清单原样喂回 LLM 重试，最多 `max_repair_rounds` 轮；超限则返回**半成品 + 完整违规清单**（半成品比空结果有用）。
3. **必带任务书.** 返回 `spec`，让"图"和"规格"同时可见 —— 这是 FlowEdge 与 Raven 最实质的差别：**它给你一张图，我们给你一张图 + 一份可验收的任务书。**

**未验证**：LLM 在 29 个模块 + 端口类型约束下生成合法图的实际成功率未知，需要先跑 10 条 goal 标定（预计首轮合法率不高，修复轮次才是关键指标）。

### 3.7 外部智能体调度：借 Raven 的形态，砍掉它危险的一半（2026-10-22 落地）

**要解决的事**：FlowEdge 原来的执行单位只有确定性模块（出图/转写/合成/门）。
可复现、成本可预测，但**凡是需要判断的事都进不来** —— 写文案、审片意见、改代码、查资料，
只能人在外面做完再把结果粘进来。Raven 用「节点绑定模型+harness 对」解决了这个，
这里吸收它的**形态**。

#### 砍掉了三件（这是 FlowEdge 与 Raven 的实质差别）

| 砍掉 | 原因 |
|---|---|
| **图里不许出现 shell 命令** | 节点只能引用 `agent_id`，真正的命令行只存在 `data/agents.json`（本机文件、人写的）。否则一张工作流就变成任意命令执行器 |
| **不继承父进程环境** | 只透传白名单 + 用户在配置里显式声明的 env。**尤其不透传 `http_proxy`** —— 本机常驻代理，传下去会让 agent 的网络全被劫持（这条今天踩了三次，已有专门测试盯住） |
| **不做自动挑选 agent** | 选谁由节点数据写死，不由 LLM 猜。自动分配属于 `compose`，先把「能可靠地调一个」做对 |

#### 与 Raven 的对照

| | Raven | FlowEdge |
|---|---|---|
| 执行者是 | 内置 4 个 + 外部 13 个 agent 预设 | 任意 CLI 或 OpenAI 兼容端点，**名册自己写** |
| 产物验收 | 无（MAOB 只评计划图） | **产物要过门**（`quality_gate` / `film-gates`） |
| 可复现性 | 不承诺 | 确定性模块不承诺也不变；`agent_task` **在契约里标 `Nondeterministic`**，任务书写出来，评测须单独分组 |
| 硬件约束 | 无 | 显存由 agent 自己管，FlowEdge 不采样也不仲裁（`Side=""`）—— 不假装管 |
| 调参方式 | 对话 | 节点参数 + `spec/apply`（带四条硬拦） |

**最实质的差别在第二行**：Raven 的 agent 输出没人验。
FlowEdge 的 agent 输出后面接一个门，就能回答"它到底干成了没有"。

#### 实现

| 文件 | 内容 |
|---|---|
| `service/agent_registry.go` | 名册：`data/agents.json`，`kind: cli \| http`，Probe 区分「配置了」与「装好了」 |
| `service/agent_exec.go` | 执行器：CLI 子进程（argv 传参、不走 shell）+ OpenAI 兼容 HTTP；超时/输出上限/工作目录隔离 |
| `nodecontract.go` / `nodespec.go` / `engine_v2.go` | 三处登记 `agent_task`（漏一处测试就红，见 §架构约定） |
| `handler/agents.go` | `GET/PUT/DELETE /api/agents` + `POST /api/agents/:id/probe` |

节点参数：`agent_id` / `prompt`（留空吃上游）/ `timeout_ms` / `workdir` / `allow_failure`。
输出：`text` + `{agent, agent_kind, exit_code, elapsed_ms, nondeterministic}`，失败时带 `stderr`。

**内置示例全部默认停用**：装没装、路径在哪只有本机知道。给一个 `enabled=true` 的假想命令，
首次运行就会在节点上报 command not found，比空列表更误导。

#### 真机验证（临时实例 18087，用完已清理）

```
GET /api/agents          → 3 个示例全 enabled=false / available=false，detail="已停用"
PUT /api/agents {echo}   → available=true, detail="C:\Windows\system32\cmd.exe"
start → agent_task → end → run status=success
  节点输出: {text:"agent got: ...", agent:"echo", exit_code:0, nondeterministic:true, elapsed_ms:291}
spec?format=md           → "- ⚠ **非确定性**：同一输入不保证同一产出…"
```

`service/agent_test.go` 19 个用例：缺 id 列可用清单 / 未知 id / 停用 / 无 prompt / 上游取 prompt /
非零退出阻断 / `allow_failure` 如实记退出码 / 超时 / 命令不存在 / **环境不透传代理** /
显式声明可透传 / 模板渲染 / 输出截断 / 名册持久化 / 校验 / 探测三态 / 契约标非确定性 / 任务书标非确定性。

#### 前端与运行期配套（2026-10-22 补齐）

| 项 | 内容 |
|---|---|
| 画布入口 | 调色板「AI 推理」组新增**外部智能体**（`⇢`） |
| 参数面板 | 智能体下拉（只列启用项，各自带 `可用/不可用` 状态）+ 选中项探活详情 + 「重新探测」 + 任务描述（留空吃上游）+ 超时（默认 5 分钟）+ 「失败也往下传」 |
| 非确定性警示 | 面板顶部常驻一条：「这一步**不承诺可复现**……评测时本图要与确定性图分开统计」 |
| 名册为空 | 直接给出配置位置（`data/agents.json` / `PUT /api/agents`）并说明「内置示例默认停用」 |
| 节点级并发配额 | `AGENT_MAX_CONCURRENCY`，默认 **2**、夹在 16 以内。整图准入闸管不了「一张图里 5 个 agent 同时起 5 个进程」——那是提交后的扇出 |
| 超时回收进程树 | `taskkill /F /T /PID`。只杀父进程会留下 agent 自己 spawn 的 node/python/LSP 孤儿，它们在后台继续吃内存，下次执行还会撞上 |

**为什么节点级配额不能省**：准入闸只在提交时问一次「现在能不能跑」，而扇出发生在提交之后。
5 个 Claude Code 同时起，每个几百 MB 到几 GB，24G 机器会直接跪——而准入闸那时早就放行了。

**为什么用 `taskkill` 而不是 Job Object**：Job Object 要 `golang.org/x/sys/windows`，那是新增依赖；
`taskkill /T` 是系统自带，效果等价。边界写死：只杀本次 `agent_task` 自己 spawn 的进程树（pid 来自 `cmd.Process`），
不碰任何用户进程。

**验收**：前端 81 个用例全绿（新增 3 个：面板警示与下拉、名册为空指引、不可用时显示真实原因）；
`npx tsc --noEmit` 0；新构建 exe 冷启后首页引用新 hash、bundle 里能检到全部面板文案。

#### 未做（诚实标注）

- **compose 自动分配**：让 LLM 根据任务挑 agent —— 那是 §3.6.5 的 compose，另一步
- **agent 名册的图形化管理**：现在新增/编辑走 `PUT /api/agents` 或手改 json，画布上没有编辑表单
- **CLI 交互式提问的自动应答**：非交互模式靠 `args` 里写 `-p` / `--yes`，引擎不代答

### 3.8 CodeGraph 评估：机制很好，但**大部分不适用**（2026-10-23）

> 对象：`colbymchenry/codegraph`（MIT，★21k，v0.9.9）。本地代码知识图谱，MCP 服务接 9 个编码 agent。
> 官方数据（7 个真实仓库）：**少 88% 工具调用 / 少 62% token / 便宜 44% / 文件读取降到 0**。
> 做法：Rust 内核 + tree-sitter 把源码解析成符号与边（calls/imports/inheritance）→ SQLite + FTS5 → MCP 查询。

#### 3.8.1 它解决了什么

agent 探索陌生代码库时，是 grep → read → grep → read 的循环，token 烧在**重复发现结构**上。
CodeGraph 把这部分前置成索引，一次查询拿到：入口点 + 相关符号 + 调用路径 + **blast radius（改动爆炸半径）**。

#### 3.8.2 三条真金（可移植到 FlowEdge）

| 机制 | CodeGraph 怎么做 | FlowEdge 的对应问题 | 移植方式 |
|---|---|---|---|
| **blast radius** | 预计算 depth-3 reach 索引，"改这个符号会炸到谁"变成 O(seeds×reach) 查表 | `spec/apply` 现在只验四条硬拦，**不告诉用户改了会影响哪些下游门/产物** | 加 `POST /api/workflows/:id/impact`：给定 nodeId + 参数变更 → 列出受影响的下游节点、会失效的门、需要重跑的范围 |
| **结构化索引替代现场扫描** | 符号/调用边入库，查询不读文件 | 跨工作流检索没有索引，问"有没有做过类似的片子"只能靠名字猜 | 把 12+ 条工作流压成 `GraphShape`（已有）+ FTS5 索引，支持"按结构找相似图" |
| **增量同步** | 文件变更 300ms 后只同步变化部分，代价随"改动量"而非"仓库大小"增长 | 任务书每次全量编译；结构分每次全量算 | 低优先（当前 12 条图，全量算 <10ms，没有优化价值） |

#### 3.8.3 四条明确不适用（不移植）

| 机制 | 为什么不适用 |
|---|---|
| tree-sitter 源码解析 | FlowEdge 不索引源码。它的"代码"是**工作流图**，而图的真相源是 `Modules` 契约表，不是文本文件——解析没有对象 |
| 省 token 的核心价值 | FlowEdge 的 LLM 节点是**单轮/少轮**，不是长会话探索。省 token 解决的不是它的瓶颈 |
| MCP 多 agent 接入 | FlowEdge 已经**是** MCP 服务端（对外暴露 spec/run），再挂一个 MCP 客户端是反向的 |
| 35 语言 / 17 框架路由 | 与出片无关 |

#### 3.8.4 它自曝的一条劣势，反而最值得学

> "CodeGraph's responses leave about **80% more retrieval context resident** at the end of a session … **on VS Code, 67k tokens against 18k**."
> "Fewer tokens *processed* and a larger persistent *footprint* are both real at once."

**少处理 token ≠ 少占窗口**：一次给一份密的完整载荷，快了，但它一直占着上下文。

对 FlowEdge 的直接含义：`spec` 就是这种 dense payload。29 模块的大图产出的任务书是长文本，
**如果 compose 拿它当提示词，就会重蹈这个坑**。所以 compose 的提示词应当喂**结构化的候选清单 + 约束**，
而不是整份任务书。

作者还自曝了另两条使用边界，都很诚实：
- "CodeGraph only helps when queried **directly** … otherwise a sub-agent reads files regardless and CodeGraph becomes **overhead**"（交给探索型子 agent 就白建索引）
- "near-even where it got there in 7"（本来只需 7 次调用的简单问题，收益趋零）

⇒ 对应的纪律：**结构评分器必须被直接调用，不能被"让 agent 自己去看看图对不对"替代**。

## 五、定量评测：有 / 无 FlowEdge 对 AI 工作能力的影响

> 这一节回答"像 harness² 那样如何定量评价"。核心是：**先把"AI 工作能力"拆成三个不能混的层，再用三组对照 + 两个判分通道去测。**

### 5.1 命题拆解：先问"到底在测什么"

直接问"有 FlowEdge 的 AI 比没有的强多少分"是错的提问方式——它把三种完全不同的东西混成一锅，这正是 harness² 论文自己反复强调要避开的陷阱（"增益全部来自换 harness，不是模型变强"）。

| 层 | 测什么 | 有/无的差是什么类型 | 主指标 | 判分通道 |
|---|---|---|---|---|
| **L1 能力可及性** | 这件事**能不能做出来** | 0 / 1 的**存在性**差（不是分数差） | 任务可完成率 `CR` | 产物存在性 + 可解码性（ffprobe 流列表） |
| **L2 执行质量** | 做出来的**合不合格** | 通过率与分布差 | 门通过率 `GPR`、五层门分项、FAIL 数 | 数值门（**不用 judge**） |
| **L3 执行成本** | 同样的产出**花了多少** | 比值差 | 墙钟、GPU-分钟、峰值显存、卸载次数、token、**人类介入轮次** | trace / nvidia-smi / 人工台账 |

> L1 单独列出来是关键：**如果对照组根本产不出成片，那 L2/L3 的"分数"毫无意义**。评测报告必须先把 L1 的 `CR` 报出来，`CR=0` 的组不参与 L2 比较（否则会出现"没做出来的反而评分高"这种荒谬结果）。

### 5.2 三组对照（含消融，这条最容易被漏）

| 组 | 定义 | 用来回答 |
|---|---|---|
| **A · 裸 agent** | 同一模型 + 同等工具权限（ffmpeg / ComfyUI HTTP / ffprobe），**不给** FlowEdge 的 DAG、门、任务书 | FlowEdge 到底带来了什么 |
| **B · FlowEdge 全量** | 通过 `/api/workflows/:id/run` 或 MCP | 完整收益 |
| **C · FlowEdge 消融** | 用 FlowEdge 但**关掉门**（gate 节点旁路）+ 保留 DAG | **区分"是 DAG 在起作用"还是"是门在起作用"** |

C 组是全部关键。没有 C 组，你永远不知道收益来自结构还是来自验收——而这两者的改进方向完全相反（结构问题改图，验收问题改阈值）。FlowEdge 有版本回滚，做 C 组只需 clone 一份 workflow 把 gate 节点摘掉，成本极低。

**控制变量（必须写进报告）**：同模型同采样参数、同任务集、同种子、同机器、同 ComfyUI 实例与分辨率步数。任何一项不同，结论作废。

### 5.3 两个判分通道（不许混用）

**通道 1 · 数值门（默认，覆盖 L1/L2/L3 全部量化部分）**

```
passed := (ffprobe 流完整) && (nb_frames == 期望帧数) && (av_drift ≤ 1 帧)
       && (五层门全过) && (scene_lock 字节全等) && (ASR 无乱语)
```

已有工具链直接可用，退出码 0/1/2 = 通过/警告/硬失败，天然是可做门禁的二值信号。**这条通道不需要任何 LLM，成本为零，不可被话术影响。**

**通道 2 · 盲配对 judge（仅在数值门覆盖不到的维度启用）**

只用于：叙事连贯度、画面美学、台词味道。规则：

1. **盲**：不给 judge 知道哪份是 A 哪份是 B，随机化顺序
2. **双向**：A→B 与 B→A 各判一次，两次不一致判 tie（消除位置偏好）
3. **只出排序不出分数**：`better / worse / tie`，避免分数尺度漂移
4. **不计入主指标**：单列为"主观维度参考"，与 L1/L2 分开报

### 5.4 防作弊（harness² README 自己踩的坑）

harness² 官方在验证时撞见过一次：一个 Codex rollout **没有被指令，自己下载了任务评分标准**（JobBench 把 RUBRICS.json 挂在 HuggingFace）。官方给的解法不是靠工具设置挡，而是**在网络层断**。

FlowEdge 的同构风险更直接：`llm` 节点有 `exec_code` 能力，可以读到 `scripts/film-gates.py` 的阈值，甚至改它。隔离措施：

| 风险 | 措施 |
|---|---|
| 被测 agent 读到门阈值 | 评测期把门阈值编译进二进制或放只读卷，脚本不进被测 agent 的可见目录 |
| 被测 agent 改门脚本 | `film-gates.py` 在评测前算 sha256 记入信封，事后校验；变更即该 run 作废 |
| 旧产物冒充新产物 | `newerThanStart`（序策 `meta.quality` 已有此机制，直接沿用） |
| 直接复制上次成片 | 每条 case 带唯一 `datasetFingerprint`，产物哈希纳入比对 |

### 5.5 样本量与统计口径（纪律 0.3：报区间不报单点）

| 项 | 要求 | 理由 |
|---|---|---|
| 每条 case 重复 | **≥3 次**（不同 seed） | 单次结果不可信；harness² 也要 K 次参考执行 |
| case 数 | **≥8**，且 **≥2 个类别** | 直接沿用序策门禁常量 `minimumEvaluationCases: 8` / `minimumEvaluationCategories: 2` |
| 报告形式 | 中位数 + [min, max] + 样本数 | 禁止只报均值或单点 |
| 显著性 | 配对差值 + 符号检验（n≥8 时 p<0.05） | 配对设计天然消掉任务难度差异 |
| 成本口径 | 必须归一化：GPU-分钟 / 每合格产出 | 只报墙钟会掩盖"重跑 5 次才成 1 条" |
| **分母口径** | **必须双报** `CR_all`（全 case）与 `CR_clean`（可测 case），并单列 `unscored_rate` | 见 §5.9.2：只报一个分母，两侧都有作弊空间 |

**淘汰线（借用序策硬门禁，不改数值）**：候选相对基线的 token 回归 > 0%、p95 延迟回归 > 10%、critical 回归 > 0 → 直接 rejected，不看别的。
**另加一条**：`unscored_rate > 20%` 时**不许下结论**，先修环境再评（否则拿到的是环境的分数，不是 harness 的分数）。

### 5.6 最终报告长什么样（模板）

```
任务集: 出片-竖屏 v3, n=12 case × 3 seed = 36 run/组
控制: GLM-5 / flux-schnell-fp8 @512² / 3090 24G / seed 42,43,44

组别       CR_all  CR_clean  unscored  GPR    五层门最弱项  墙钟中位  GPU-分/合格产出  人类介入/任务
A 裸agent  2/12    2/9       3        0.17   audio 0.31   41.2 min  38.4           6.3
B 全量     12/12   12/12     0        0.92   audio 0.86   36.8 min  3.1            0.4
C 消融无门 12/12   11/12     1        0.61   audio 0.42   35.1 min  4.9            2.1

结论: L1 CR_all +83pp（A→B）；L2 GPR 0.61→0.92（C→B，门贡献 +31pp）；
      DAG 贡献主在 L3（GPU-分/合格产出 38.4→4.9，-87%）；门贡献主在 L2。
      可信度: A 组 unscored 3/12 偏高（25%），该组 CR 需谨慎引用，先查这 3 条的失败原因。
      未验证: 主观叙事维度未做盲配对，本报告不含该维度结论。
```

**三个数缺一不可**：`CR_all` 防美化（Raven 口径），`CR_clean` 防冤枉（harness² 口径），`unscored` 告诉你前两个该信哪个（两家都没有，我们加）。

这张表就是回答"有/无 FlowEdge 对 AI 工作能力影响"的最终形态——**它是一个三组 × 三层 × 六指标的矩阵，不是一个分数。**

### 5.7 评测本身要跑在 FlowEdge 上

不要写外部评测脚本。每条 benchmark case = 一张 workflow，三个对照 = 三个 workflow version，`shots/reroll` 就是重复采样，`trace` 就是指标源，`evidence.json` 就是信封。

这样"评测"就变成引擎的一部分，和 `管线质量门-规范-v1.md` 的 L1/L2 是同构的，也和序策状态机天然对接。**评测不是一次性的动作，是平台的一个常驻能力。**

### 5.8 harness² 的分数是怎么来的（原文核实，2026-10-22 读 docs/BENCHMARKS.md + docs/EXPERIMENTS.md）

这一节回答一个容易误解的点：**它一边宣称"开放世界没有标准答案也能改进"，一边报出 +11.5 分。两者不矛盾，因为改进和评分被物理隔离了。**

#### 为什么"有分数"和"不需要标准答案"能同时成立

| 阶段 | 需要分数吗 | 靠什么 |
|---|---|---|
| 改进（PPC） | **不需要** | 同一任务、同设置下不同 harness 的**行为对比**；唯一变量是被试编辑 |
| 报告（结果） | **必须有** | 上游 benchmark 自带的 rubric，由外部 judge 打分 |

关键在第三件事：**改进器从头到尾看不见分数。** 原文三处证据：

- LAB：「The adapter groups tasks by practice area and **removes criteria from the material passed to the improver**.」
- JobBench：「**Rubrics stay outside the improver's evidence.**」
- WorkBuddy：「The adapter reads the verifier's `score.json`; **the improver never receives verifier output.**」
- 时序：「The judge **reads outputs only after selection**.」

⇒ 结构是双信道：**改进信道只有行为差异，评分信道只有产出**。这既让它能"无标准答案也能改进"，又避免了改进器对着 rubric 过拟合。

#### 分数从哪来（三个 benchmark 三种口径）

| Benchmark | 上游 | 评分方式 | 分数形态 |
|---|---|---|---|
| LAB（法律，1143 任务） | `harveyai/harvey-labs` | rubric-based grading + Vertex judge patch | **Partial**（criteria 通过比例）+ All-pass（全过） |
| JobBench（专业工作） | `Job-Bench/job-bench-eval` | 上游 rubric **带权重** | 加权分（"uses the upstream rubric weights"） |
| WorkBuddy-Bench（办公/网页/代码） | `Tencent/workbuddy-bench` | 容器内 verifier 产出 `score.json` | 验证器原始分 |

judge 本身是 **LLM**（默认 Gemini via Vertex 的 OpenAI 兼容端点），可通过 `HARNESS2_JUDGE_MODEL` / `HARNESS2_JUDGE_BASE_URL` / `HARNESS2_JUDGE_API_KEY` 换 provider。

baseline 是**另外补跑**的：`harness2-judge --bases` 给基准参考执行打分，写 `base_judged.json` 与 `judged.json` 并列；`harness2-report` 只报 refined harness。所以「+11.5 分」= refined 相对 base 的配对差，不是绝对能力。

#### 三条必须照抄，三条不能照抄

| 照抄 | FlowEdge 怎么落 |
|---|---|
| **① 改进器看不见分数** | probe 阶段的 agent 只拿粗粒度回执（`passed: true/false`），**不拿五层门的具体数值与阈值**。比"阈值编译进二进制"更彻底 |
| **② Partial 分数优于二值** | 五层门本来就逐项检查（`quality_gate.go`），输出成 `timing/identity/audio/technical/budget` 各 0~1 的比例即可，信息量远大于"过/不过" |
| **③ unscored ≠ 0** | 信封 `passed` 改三态 `passed / failed / unscored`；`CR` 计算时 unscored 单列。原文：「Failed evaluations remain unscored rather than being counted as zero」——这一条我们自己也有同款纪律（AGENTS §0.6「不可达 vs 空结果」） |

| 不能照抄 | 原因 |
|---|---|
| LLM judge 作主判分 | 原文自己承认「**Changing the judge model changes the measurement.**」分数只在同一 judge 下可比。我们的门是确定性的，没有这个脆弱性，不该主动引入 |
| 靠断网防泄题 | 原文「The release **does not restrict network access**」，靠出口防火墙/DNS。我们更该在**数据可见性**上做隔离，而不是指望网络策略 |
| 把 `--seed` 当复现保证 | 原文明确「`--seed` Shuffle the task stream reproducibly; **does not control model sampling**」。所以它的分数本质不可完全复现，只能靠样本量摊平——这正是我们要求 ≥3 seed + 报区间的原因 |

#### 一句话

**harness² 的分数不是"改进的依据"，是"改进之后的独立审计"。** 我们照抄的是这条审计纪律，不是它的 judge。

### 5.9 harness² 与 Raven 评测法拆解：两家在哪里**相反**（2026-10-22 读原文）

> 两家都是 2026 年 9 月的同代工作，都在解决「怎么证明换了 harness 真的更好」。
> 结论先说：**它们评测的是 harness 的两个不同部位，而且在一个关键统计口径上南辕北辙。**
> 那个矛盾不是谁写错了，是**两个相反方向的作弊**各有各的门。

#### 5.9.1 评测对象不在同一层

| | harness² | Raven |
|---|---|---|
| 评什么 | **端到端产出**（报告/代码/文档） | **计划图本身**（DAG 与参考图比对） |
| 何时评 | 执行完之后 | **dispatch 之前** |
| 分数来源 | 上游 rubric + LLM judge | Node F1 / Edge F1 / Partial Order / Exact Match |
| 有 ground truth 吗 | 半结构（rubric 条目） | **完全结构化**（可精确匹配） |
| 主要成本 | 每条任务都要真跑 + 一次 judge | **不用跑 worker**，只比对结构 |

Raven 原文（`arXiv:2609.33439` §1）：

> "MAOB … measures specialist selection and dependency prediction by comparing proposed DAGs with reference graphs **before worker execution**."
> "Because validation precedes dispatch, a rejected graph consumes a host turn without starting a partial worker execution."

⇒ **MAOB 从来没测「能不能交付」。** 这是它省钱的原因，也是它最大的盲区。

**但 Raven 自己把这条盲区写出来了**（§2.6 末）——这句话是我们整个两段式评测的依据：

> "the graph agreement measures in Section 7.1 **should be complemented by semantic contract checks, end-to-end outcomes, cost accounting, and failure attribution**."

#### 5.9.2 两家在一个统计口径上完全相反（本节最重要的发现）

同一个问题——**测不了的样本怎么算**——两个项目给出了相反的规定：

| | harness² | Raven |
|---|---|---|
| 规定 | "Failed evaluations **remain unscored rather than being counted as zero**" | "Remaining infra failures **count as non-passes, not removed tasks**"；"**Do not shrink the reported denominator** to clean or beacon-fired tasks" |
| 防的是 | **冤枉**候选（把"没测到"记成不合格） | **美化**分数（把难测的样本剔除） |
| 代价 | 可能出现"只报合格样本"的美化 | 环境抖动会被算成候选的锅 |

**两边都没错，因为它们防的是两种相反的作弊。** 只做一边，另一边的漏洞就敞着：

- 只按 harness² 做 → 有人可以"多制造不可测样本"，把分母做小
- 只按 Raven 做 → 一次服务没起，候选就被记成 0 分，改进方向被误导

**正确做法：两个分母都报，且第三个指标告诉你该信哪个。**

| 指标 | 分母 | 回答什么 | 抄谁 |
|---|---|---|---|
| `CR_all` | 全部 case | 按最严口径，这批任务成了多少 | Raven |
| `CR_clean` | 只算 `passed + failed` | 在能测的里面成了多少 | harness² |
| `unscored_rate` | — | **这批分数可不可信**：>20% 就别看 CR，先修环境 | 两家都没有 |

**FlowEdge 的三态信封正好是唯一能算出这三个数的数据结构**：`failed`（测了不合格）与 `unscored`（没测到）分开记，才能同时给出两个分母。如果只有一个布尔 `passed`，这两个数字**根本算不出来**——这就是为什么 §6.1 那三个状态不是"更精细"，是"能不能正确统计"的前提。

顺带一提，Raven 在另一个地方做反了：

> "Under the availability fallback, a normally returned call is treated as accomplished **if the judge fails or times out**."

**判官挂了就判成功** —— 这是明确的假阳性（他们自己也在下一句承认 "the observed completed set … differs from the objective successful-prefix event"）。我们的做法相反：judge/门不可用 → `unscored`，**不算通过**。这条我们不改。

#### 5.9.3 Raven 自己标注的边界（都是我们该守的）

| Raven 原文 | 对 FlowEdge 的含义 |
|---|---|
| "the verdict **does not certify objective correctness**" | judge 的结论不能当成真理；我们的门只报"帧数/响度/字节全等"这类可复算的事实 |
| "does not impose a universal wall-clock limit on a graph … **Structural scheduling does not establish a cost advantage by itself**" | 图好看不等于便宜。成本必须实测（GPU-分/合格产出），不能靠结构推断 |
| "coordination benefits depend on task structure and **may be outweighed by overhead**"；"Additional nodes may **reduce subtask difficulty while increasing handoff cost and error**" | 多节点有代价。评测必须把交接开销算进去，否则"拆得越细"永远赢 |
| "**Measured average success rates alone do not establish** the conditional reliability premises" | 平均分不能证明机制成立 —— 这正是我们要做 A/B/C 消融（§5.2）的原因 |
| "The final deliverable is selected by **training score, never by searching for the highest test result** among candidates" | **选最优版本只看 shadow/训练分数，永不看 test 分数**。这条直接约束序策 registry 的 promoted 判据 |
| "**passing it is not promotion**"；"Screening cheaply removes clearly worse candidates" | 粗筛只淘汰明显更差的，晋升要另过确认门 —— 与序策 `evaluated → shadowing → promoted` 一致 |
| "A promoted candidate can have `credited_2sigma: false`; **that is not proof of a statistically significant improvement**" | 不要说"显著提升"，除非真的做了统计检验 |
| "Presence-level attribution proves that some instrumented code executed, **not that a particular mechanism caused the gain**" | 埋点触发 ≠ 归因。改好了要知道是哪一处改好的，需要单独消融 |

#### 5.9.4 学到的两段式评测（FlowEdge 的组合拳）

两家各占一头，**FlowEdge 可以把两头接起来**，因为它的门在产出上做确定性判定：

```
第一段：结构指标（廉价，不执行）        ← 学 Raven
  Node F1 / Edge F1   ：生成图 vs 参考图的节点集与边集
  PortOK 率           ：每条边是否过 PortKindAccepts
  ContractOK 率       ：模块是否声明、必填参数是否有来源
  → 成本 ≈ 一次 LLM 调用，秒级；用来淘汰明显不合格的生成

第二段：端到端指标（昂贵，要执行）      ← 学 harness² + 自己的门
  CR_all / CR_clean / unscored_rate
  GPR（五层门通过率）+ 分项
  GPU-分/合格产出、人类介入轮次
  → 只对第一段通过的图跑，省 10~100 倍
```

**FlowEdge 有一个 Raven 没有的便宜条件**：它自己就存着 **12+ 条人工画好的真实工作流**——这就是现成的 reference graphs。Raven 要自己标 MAOB，我们不用标。

⇒ **compose 的评测不需要先跑片子**。先用第一段（图结构 F1 + 契约违规率）标定生成质量，成本几乎为零；只有通过第一段的图才值得花 GPU 去跑第二段。这一步把「compose 值不值得做」的判断成本从"几十小时出片"降到"几分钟"。

#### 5.9.6 已在做：图结构评分器（2026-10-23 落地）

`service/graph_score.go` + `handler/graph.go` + `POST /api/graph/score`，14 个用例。

**分两级，因为前提不同**：

| 级 | 算什么 | 需要参考图 | 能回答 |
|---|---|---|---|
| **L0 结构合法性** | 契约覆盖 / 端口兼容 / 必填有源 / 无环 | ❌ 不需要 | 这张图**能不能跑** |
| **L1 结构相似度** | Node F1 / Edge F1（类型多重集） | ✅ 要配对 | 这张图**像不像人画的** |

L0 的加权：契约 0.3 + 端口 0.3 + 接线 0.3 + 无环 0.1（和必须为 1，有测试盯）。
`Legal` 是**独立的硬门槛**（无契约缺失 + 无端口冲突 + 无环），不是靠分数阈值——阈值会被调，门槛不会。

**用 12 条真实工作流定标（这一步抓出了两个真问题）**：

| 轮次 | 结果 | 说明 |
|---|---|---|
| 初版 | legal **5/12**，均值 0.922 | 5 条**跑通过的真实图**（含已出片的「修士斗法」）被判端口冲突 |
| 修 1 | legal **11/12**，均值 0.974 | 根因：`targetHandle` 为空时拿"契约第一个输入端口"冒充，但空 handle 的语义是**随便接**（引擎运行期就这么做的，否则那些图根本跑不起来） |
| 修 2（最终） | legal **11/12**，均值 0.987 | 孤立节点不再单独扣分——输入全可选的节点靠参数自给是合法接线（tts 的文本常写在参数里），扣分会让能跑的图永远拿不到满分 |

**最终剩下唯一的 legal=N 是真缺陷，不是误报**：

```
wf49「音频验收｜分镜直填」: start(text) → shotlist(json|image|audio)
shotlist 契约里根本没有 text 输入 —— 这条连线是无效的
```

⇒ 评分器第一次跑就找出了真实库里的一个无效连线。这比"分数好不好看"更能说明它有用。

**教训（值得记住）**：单元测试 13/13 全绿的那个版本，会把所有真实图判成坏图。
**必须拿真实产物定标**——否则你测的是"我的实现符合我的假设"，不是"工具在真实世界里成立"。

#### 5.9.5 纪律清单（写进评测器，不靠人记）

1. 报三个数：`CR_all` / `CR_clean` / `unscored_rate`。**少一个都不许下结论**
2. judge / 门不可用 → `unscored`，**绝不放行**（与 Raven 的 fallback 相反，理由见 5.9.2）
3. 分母永不缩小；要剔除必须先单独报 `unscored_rate`
4. 选最优版本只看 training/shadow 分数，**不许在 test 集里挑最高**
5. 说"显著"必须有检验；否则只说"观测到 X→Y"
6. 归因要单独消融（A/B/C 三组），埋点触发不算证据
7. 成本实测，不由图结构推断

### 6.1 P0 落地记录（2026-10-22）

**改动**：新增 `backend/service/evidence.go`（约 230 行）、`evidence_test.go`（11 个用例）；
`handler/workflow.go` 与 `service/run_service.go` 两处收尾各接 1 处调用。零新增依赖，不动 DB schema。

**核心设计：三态而非二态**

| result | 触发条件 | `passed` |
|---|---|---|
| `passed` | run 成功 + 有门节点 + 门全过 | `true` |
| `failed` | 门跑完了检查并判不过（有 `checks`） | `false` |
| `unscored` | 没接门（`no_gate`）/ 门自己崩了（`gate_error`）/ 非门节点崩了（`execution_error`） | `null` |
| `cancelled` / `paused` | 人为中止 / 暂停 | `null` |

**最容易写错的一处**：门的"执行崩溃"与"判定不过"在 run 上都是 `status=failed`。
若合并成一个布尔，就会把"服务没起导致没测"记成"产出不合格"，评测结论直接反向（AGENTS §0.6）。
判据 = 门有没有留下 `checks`（跑完了必然留痕）。这条在开发中被真机验证抓出来，已补两个用例。

**实测证据**（临时实例 18082 / 18083，临时 data，不碰 8080）

- `start → end`（无门）：`result=unscored, passed=null, reason=no_gate, humanInterventions=0` ✅
- `start → quality_gate(缺输入) → end`：`result=unscored, passed=null, reason=gate_error, gateNodes=["g"]` ✅
- 两例的 `caseId/datasetFingerprint/category/peakVramMb` 均为 `null` —— 引擎不知道的字段不编默认值

- `peakVramMb`：`TimelineEvent` 没有 `runId`，按时间窗反推会在并发 run 时张冠李戴。要真值先给 timeline 加 run 关联。

### 6.2 P0-2 落地记录：资源准入闸（2026-10-22）

**原计划改道**：方案原本写「执行前调 `gov.mjs preflight`」（spawn node CLI，靠退出码 0/2 判断）。
实测发现序策暴露了 HTTP 端点，改走 HTTP：

```
POST http://127.0.0.1:30002/api/flow/governor/preflight
  body: {"kind":"flowedge"}
  200 → {ok:true,  weight:3, level:"ok", effectiveMax:6, usedWeight:0, sample:{cpu,mem,gpu,loop,disk}}
  429 → {ok:false, ..., advice:"显存不足：…", reasons:["gpu_reserve",...]}
```

三个实测确认的事实：

| 项 | 值 | 来源 |
|---|---|---|
| 端口 | **30002**（不是 30000） | `server/index.js` → `FLOW_PORT \|\| 30002` |
| 权重档 | 序策配置里已有 **`flowedge: 3`**，注释写明「真实 VRAM 由 FlowEdge 侧再管一层」 | `resource-governor.js` weights |
| 返回形态 | 结构化（level/advice/reasons/sample），比 CLI 退出码信息量大得多 | 实测 curl |

**实现**：`service/governor_gate.go`（约 170 行）+ `governor_gate_test.go`（7 用例）；
`handler/workflow.go` 加 `SetGovernor` 注入 + `Run` 里一处检查；`main.go` 构造并打印开关状态。

**行为矩阵（fail-open 是关键）**

| 情况 | 结果 | Source |
|---|---|---|
| 治理器 200 / ok=true | 放行 | `governor` |
| 治理器 429 / ok=false | **拦住**，返回 429 `governor_declined` + 完整原因 | `governor` |
| 序策没起 / 超时 / 5xx / 响应不可解析 | 放行 + 日志 | `unreachable` |
| `FLOWEDGE_GOVERNOR=off` | 放行，**一次请求都不发** | `disabled` |

**为什么 fail-open 而不是 fail-closed**：FlowEdge 是独立可分发的产品。序策没起时拒绝出片，
等于把引擎变成"必须有另一个进程才能用"。问不到 → 我们的降级；问到了且说不 → 尊重别人的判决。

**必须绕代理**：本机常驻 `http_proxy=127.0.0.1:5751`，默认 Transport 会把 localhost 请求发给代理、
拿回假 502，于是「治理器没起」和「治理器拒绝」分不清（AGENTS §0.6 同款）。代码里 `Proxy: nil` 硬关，
并有一个专门的用例 `TestGovernor_BypassesHTTPProxy` 盯住。

**实测证据**（临时实例 18084/18085/18099，不碰 8080 与 30002，用完已清理）

- 序策在线（30002，level=ok）：`POST /api/workflows/1/run` → **202**，正常起跑
- 假治理器返回 429：`POST /api/workflows/1/run` → **429**
  `{"code":"governor_declined","governor":{"allowed":false,"level":"critical","advice":"显存不足：…","reasons":["gpu_reserve","cpu_pressure"],"source":"governor"}}`
  且 `GET /api/runs` → `total:0` —— **在入库前就拦住了，没有留下垃圾 run 记录**

**未接的入口（诚实标注）**：`/runs/:runId/resume`（续跑）与 `/runs/:runId/rerun-from` 尚未过闸。
两者同样能打爆机器，但它们在 service 层、要额外把闸传进去；本轮按「一次只动一个变量」不动它们。

**回归**：`go test ./...` 全绿，`go vet` 0。

### 6.3 P1 落地记录：任务书回写 `spec/apply`（2026-10-22）

**为什么这一步是闭环的关键**：`spec` 以前只能出不能进。智能体读得懂图却改不动，
「按任务书调参」只能靠人在画布上手点 —— Compose 那一半永远空着。

```
POST /api/workflows/:id/spec/apply
{
  "baseVersion": 3,            // 可选：粗粒度乐观锁
  "allowGateChange": false,    // 是否允许放宽门
  "dryRun": false,             // 只校验不落盘
  "edits": [{ "nodeId":"n12", "path":"data.min_frames",
              "from":124, "to":186, "reason":"…" }]
}
```

**四条硬拦（比原计划多一条）**

| Code | 状态 | 触发 | 为什么必须拦 |
|---|---|---|---|
| `node_not_found` | 404 | 图里没这个节点 | 基于过期任务书改 |
| `path_not_allowed` | 403 | 改 `data.*` 以外的字段 | id/type/position 是图结构，改它等于换一张图 |
| `gate_param_locked` | 403 | 动门层参数却没带 `allowGateChange` | **放宽验收必须留名**，否则门不再有牙齿 |
| `from_mismatch` | 409 | 现场值与 `from` 不符 / 路径不存在 | 期间别人改过，不能覆盖 |
| `bad_edit` | 400 | 空 edits / `from` 缺失 / 门参数无 reason | — |

门层键集合从 `spec.go` 的 `gateParamKeys` **派生**，不另立一份 —— 否则任务书说的门和回写锁的门会漂成两套。

**`from` 是必填的乐观锁，不是冗余**：智能体读到任务书之后、提交之前，人可能已经在画布上改过了。
没有 `from` 就无法区分「我基于旧值改」和「我要覆盖别人的改动」。比较用 JSON 语义（`124` 与 `124.0` 视为相等），
避免 float64 / int 的类型分支。

**原子性是硬要求**：一批里有一条不过，整批不生效。半批生效是最危险的失败形态 ——
每一条单独看都"成功"，但图会停在一个谁都没设计过的状态，且没人知道停在哪。

**快照先于写图**：apply 生效前先 `CreateVersion` 把改动前的状态存成新版本。顺序反了就会出现
"改了但没版本可回"。快照失败不阻断改图，但 `snapshotVersion` 会返回 0 让调用方知道"这次没留下版本"。

**实测证据**（临时实例 18086，临时 data，用完已清理；`service/spec_apply_test.go` 13 用例覆盖纯逻辑）

| 场景 | 结果 |
|---|---|
| `dryRun` 改 prompt | 200 `{applied:[…], dryRun:true, wouldWrite:true}`，图未变 |
| 真改 prompt | 200 `{count:1, snapshotVersion:1}` |
| 图里确认 | `prompt = "a black cat"` |
| 快照内容 | v1 保留 `prompt="hello"`（改动前），v2 保留改后值 |
| 用旧 `from` 再改 | **409** `from_mismatch`，提示"这期间图被改过了，请重新取任务书" |
| 门参数无授权 | **403** `gate_param_locked` |
| 门参数授权 + reason | 200，`snapshotVersion:2` |
| 改 `type` | **403** `path_not_allowed` |
| 回滚到 v1 | 200，`prompt` 回 `hello`、`min_frames` 回 `124` ✅ **旧版仍可回滚这条判据成立** |

**MCP 侧已同步**：新增 `flowedge_apply_spec`（`workflow_id` / `edits` / `allow_gate_change` / `dry_run` / `base_version`）。
外部智能体现在走 MCP 就能读任务书 → 预演 → 回写，不必自己拼 HTTP。
引擎返回 4xx 时 `request()` 会带出状态码与响应体前 400 字符，agent 能直接看到 `gate_param_locked` / `from_mismatch` 这类原因。

**回归**：`go test ./...` 全绿，`go vet` 0。

## 八、综合对比与评分（2026-10-23）

### 8.1 先分类：所有方案不能塞进一张表

拿 CodeGraph 跟 Raven 比"编排能力"，等于拿螺丝刀跟车床比转速——**它们不在同一层**。

| 层 | 是什么 | 成员 | 判据 |
|---|---|---|---|
| **L-A 系统层** | 决定"这件事怎么被拆解、执行、验收、改进" | harness²、Raven、序策、**FlowEdge** | 有编排 + 有改进循环 |
| **L-B 底座层** | 决定"单个动作能不能确定地做出来" | ComfyUI、vLLM、Temporal、n8n、Dify | 有执行引擎，无自我改进 |
| **L-C 工具层** | 决定"agent 查信息快不快" | CodeGraph、Gortex、MegaMemory | 只服务查询，不执行不进化 |

**FlowEdge 的特殊性**：它是这个样本里**唯一同时站在 L-A 与 L-B 上**的——
既有 DAG 编排与任务书，又有确定性执行器与数值门。harness²/Raven 只有 L-A，ComfyUI/Temporal 只有 L-B。

这个组合是它的护城河，也是它的负担：**两层都要维护，所以每一层的深度都不如专做那一层的**。

### 8.3 但总分没有意义：这是短板决定论的系统

FlowEdge 的 4.03 里藏着两个 2 分。这两个 2 分不是"稍微弱一点"，是**闭环断了两处**：

```
                        ┌──────────────┐
   一次 run ──────────→ │ evidence.json │
                        └──────┬───────┘
                               │  ✗ 没人消费
                               ▼
                        （改进循环缺失）D4 = 2

   做过的片子 ─────────→ 经验？          D5 = 2
                        ✗ 不沉淀，下次从零开始
```

对比 harness² 的 2.90：它只有 D4/D5 两个高分项，但那两个**是连成环的**——经验进库、库喂改进、改进产出的分数再进库。**它能自己变强，FlowEdge 不能。**

这就是为什么总分 4.03 > 2.90 却不能说"更优秀"：**一个是闭环的 2.90，一个是开环的 4.03。**

| **1** | **证据信封没有消费方**：`evidence.json` 写得再好，没有东西读它 | **P0** | 有一条命令能跑「最近 N 次 run → 聚合 → 与上一个版本比 → 输出 candidate/reject」 |
| **2** | **知识库空转**：9 条向量，其中 2 条是**测试残留**（`kb-test.pdf` / `kb-test.docx`），无一条出片域经验 | **P0** | 出片域经验卡片 ≥30 条，且 `rag_query` 能命中"amix normalize"这类具体教训 |
| **3** | **无运行中执法**：准入闸只在提交时问一次，跑起来后没人管 | P1 | 并发 run 超配额时能被 governor 叫停，且 `evidence` 里有 `stopped_by=governor` |
| **4** | **resume / rerun-from 未过准入闸** | P1 | 两个端点各有一个 429 用例 |
| **5** | **无 compose**：意图到不了图 | P1 | 10 条 goal 标定，legal 率与结构分可报 |
| **6** | `peakVramMb` 恒空 | P2 | timeline 加 runId，信封里有真实峰值 |
| **7** | 前端看不到结构分 | P2 | 画布节点/工具栏显示 Legal 与分项 |
| **8** | 名册无图形化管理 | P3 | 面板能增删改 agent 并即时探活 |

### 8.5 三件最该做的事（按投入产出比排序）

| 优先 | 事项 | 为什么是它 | 成本 |
|---|---|---|---|
| **1** | **把 evidence 接进序策 registry** | 信封已经写好并实测过，**只差最后一跳**。接上之后 D4 从 2 直接跳到 4，且不需要新设计——序策的状态机和配对评测已经在跑 | 小（一个聚合器 + 一次 HTTP） |
| **2** | **灌出片域经验卡片（§3.4 的 D 方案）** | 素材全在 AGENTS/出片手册/MEMORY/skill 里，只是没进引擎。这是唯一能让 D5 从 2 起来的动作 | 中（编译 30 条卡片 + 验证命中） |
| **3** | **compose** | 缺口最大但依赖前两项：没有经验库，生成的图只能靠契约校验（结构对但创意平庸） | 大（标定 + 生成 + 回喂） |

**注意顺序**：先 1 后 2 后 3。理由不是难易，是**依赖**——compose 的质量取决于它能检索到什么经验。

### 8.6 一句话结论

> **FlowEdge 的底座是这批样本里最强的，系统层是这批样本里最"开环"的。**
> 它已经能稳定做出可验收的片子（D3=5，别的项目都是 0 或靠 judge），
> 但它**不会因为做得多而变强**——每次 run 的证据散落在文件里，每次踩的坑留在会话里。
>
> 差距不在能力，在**把能力变成积累的那条回路**。

## 九、界面：从"工具"到"平台"（2026-10-23 落地）

### 9.1 改造原则：只做加法，不动语义

现有视觉底子（玻璃拟态卡片、渐变顶栏、dash 连线）是好的，缺的是**动态信息**与**第一印象**。
所以这一轮全部是"补"，不重写：新增 225 行 CSS + 14 个节点文件的一行 className + 一个空态 Panel。
**零新增依赖，81 个前端用例全绿。**

### 9.2 五处"流"的表达

| 位置 | 做了什么 | 为什么是它 |
|---|---|---|
| **连线** | 从"整条虚线在闪"改成 `stroke-dasharray: 2 14` 的一串光点沿边流动 | 一条边只有一个 `<path>`，做不出双层光路；短 dash + 快位移在视觉上就是"光点在管里跑"，比闪整条线更像数据流 |
| **节点运行时** | 自上而下的扫描光带（`::after` + `translateY`） | 让"正在跑"变成一个**持续可见的过程**，而不是只靠一个小圆点在闪 |
| **节点完成** | 一次性绿色涟漪（`fe-ripple`） | 完成是事件，该有一次性的反馈；但不是每个节点都值得弹 toast |
| **节点失败** | 静态红描边（**不闪**） | 闪烁会让人焦虑，且掩盖真正要看的内容 |
| **画布** | 远景双光斑 46s 极慢漂移 + 暗角 | 静止网格是"电子表格"，缓慢呼吸是"活的系统"。周期取 46s —— 短于 20s 会让人分心 |

**踩到一个坑并修正**：第一版在 `.react-flow` 上画了 CSS 点阵，和 React Flow 自带的 `<Background>` 叠成**双重网格**（缩放时错位）。点阵属于随视口对齐的东西，只能由组件画；CSS 只管它画不了的光斑与暗角。

### 9.3 四处"平台感"

| 项 | 做法 |
|---|---|
| **品牌 mark** | `conic-gradient` 旋转能量环 + 3.6s 呼吸。位置 `z-index: -1` + `blur(1.5px)`，是光不是贴图 |
| **顶栏** | 底部一条 9s 周期的流光分割线（覆盖原有的静态渐变线） |
| **状态栏** | 运行时顶部扫过黄色进度光。用 `:has(.sb-warn)` 把"子元素是运行中"翻成"父元素显示进度光"——**不改组件逻辑** |
| **数字** | `font-variant-numeric: tabular-nums`，计数值变化时不会左右跳 |
| **空画布** | 品牌环 + "从一条流开始" + 真实快捷键提示（`Ctrl+K` 已核实存在，不是编的） |

**无障碍**：全部动画都在 `prefers-reduced-motion: reduce` 下关闭；焦点环统一为 2px 深底 + 4px 靛蓝，键盘可达。

### 9.4 验证

| 项 | 结果 |
|---|---|
| `npx tsc --noEmit` | 0 |
| 前端用例 | **81/81**（未改任何测试） |
| 产物 | `dist/FlowEdge.exe` 32.7 MB 重建 |
| 内嵌核实 | 冷启后首页引用新 hash；空态三段文案 + 10 个新 CSS 关键帧/类名**全部命中** |
| 未验证 | 无真机截图（本机截图通道不可用），视觉效果需人工确认 |

### 9.5 "碾压"到底要补什么（按维度，不按心情）

UI 能立刻超过这批样本——它们要么没界面（harness²/Raven 的 TUI），要么界面与执行脱节（n8n/Dify 不能出片）。
但 §8.2 里那两个 2 分不是改界面能动的：

| 维度 | 现状 | 补到 4+ 需要什么 | 是否改 UI 能解决 |
|---|---|---|---|
| **D4 自我进化** | 2 | evidence → 聚合 → 与上个版本比 → candidate/reject（接序策 registry） | ❌ |
| **D5 记忆与知识** | 2 | 出片域经验卡片 ≥30 条 + 检索验证 | ❌ |
| D7 资源治理 | 3.5 | 运行中执法（governor 叫停 + `stopped_by`） | ❌ |
| D1 编排表达力 | 4.5 | 动态重规划（失败后自动改图） | ❌ |
| D6 外部 agent 调度 | 3.5 | compose 自动分配 | ❌ |

**结论**：界面上已经"看起来像超级平台"了。**但平台之所以是平台，不是因为它长得像，是因为它用得越久越强。**
那一条回路（D4+D5）不补，界面再漂亮也只是"一个很好用的单体工具"。

## 十、证据闭环：从"观测"到"可登记"（2026-10-23 落地）

### 10.1 开工前的评估：不接 registry，先补诊断

原计划（§8.5 第 1 件）是"把 evidence 接进序策 registry"。动手前先侦察，发现三件事改变了方案：

| 侦察结果 | 对方案的影响 |
|---|---|
| `运行/data/evidence/` **0 个文件** | 信封是前一天才做的，125 次历史 run 全在它之前。只接 registry 会得到一份空报告 |
| `workflow_runs` 表有 **125 条**（105 success / 20 failed） | 历史状态仍在，可以当"降级数据源"用，不必从零攒 |
| 序策有 `POST /api/flow/registry/register` | 不用直接写 registry.json（避免与序策进程并发写） |

**更关键的判断**：D4（自我进化）的闭环是「观测 → 诊断 → 提候选 → 评测 → 判定」。
接 registry 只补了**最后一段**。中间的"诊断"完全没有——没有东西把 125 条散落记录变成"哪里在漏"。

⇒ **先做聚合+诊断（能独立产生价值），再接登记（最后一跳）。** 只接登记等于把断链当闭环。

### 10.2 做了什么

| 文件 | 内容 |
|---|---|
| `service/evidence_agg.go` | 聚合 + 规则诊断（纯函数，不读盘不碰库） |
| `service/evidence_agg_test.go` | 11 个用例 |
| `handler/evidence.go` | `GET /api/evidence/summary`、`POST /api/evidence/register` |

**两个数据源归一**：`evidence/*.json`（有门明细）+ `workflow_runs`（只有状态）。
evidence 里已有的 runID 覆盖历史记录。**不能因为老数据没门明细就丢掉它**——125 条分布仍能回答"哪条流水线最容易挂"。

**五条诊断规则**（每条都能指到具体数值或 runID）：

| 规则 | 触发 | 级别 |
|---|---|---|
| `env_unstable` | 不可测占比 > 20%（n≥5） | **P0** |
| `gate_weak` | 某门检查项失败率 > 30%（n≥3） | P1 |
| `pipeline_weak` | 某工作流失败率 > 50%（n≥3） | P1 |
| `long_tail` | p95 > 2.2×均值（n≥5） | P2 |
| `evidence_missing` | 全部来自历史表 | P2 |

**为什么诊断是规则而不是 LLM**：规则可复算、可解释、可测。LLM 诊断可以作为后续增强，
但**必须先有确定性基线**——否则"为什么判这批 run 不好"永远说不清。

### 10.3 真机验证抓到一个会撒谎的 bug

用 125 条真实历史数据跑第一版，报告显示：

```
CR_all=0.840  CR_clean=1.000  unscored=0.160     ← 错
```

原因：我把历史 `failed` 全映射成 `unscored`（理由是"那时没有门记录"），于是
`CR_clean` 的分母只剩 passed，恒等于 1.000 —— **把 20 次失败伪装成"全过"**。

这正是 §5.9.2 那个"分母不许缩"的坑，我自己踩了。修法是拆成四个桶：

| 桶 | 含义 | 进 CR_clean 分母 |
|---|---|---|
| `passed` | 成功 | 仅当来源是 evidence（真过过门） |
| `failed` | 门跑完了判不过 | ✅ |
| `aborted` | 执行中断/失败，没走到门 | ❌ |
| `unscored` | 没测到（no_gate / gate_error） | ❌ |

**并且 `CRClean` 改成可为 null**：一条门样本都没有时返回 `null`，不是 1.0。
"没测过"必须显示为没测过。

修正后同一批数据：

```
pass=105  门判失败=0  执行中断=20  未评=0
CR_all=0.840  CR_clean=null  中断率=0.160  未评率=0.000
可信: True | 全部来自历史 runs 表，没有门明细 —— 只能看成败，看不出哪个门在漏
诊断: 1 条 [P2] evidence_missing
```

**这是两次真机定标（图结构评分器、证据聚合器）连续抓出"看起来合理的假数字"。**
共同点：单元测试全绿，但工具对真实数据给出误导性结论。**只有拿真实存量跑一遍才会现形。**

### 10.4 登记：只登记，不晋升

`POST /api/evidence/register` 把一条诊断变成 registry candidate：

```json
{ "target":"workflow",
  "hypothesis":"（规则诊断，待人工确认）不可测占比 40%…",
  "change":"先查依赖服务是否稳定…",
  "tags":["flowedge","env_unstable"],
  "sourceEvidence":[{"observationId":"flowedge:env_unstable:unscoredRate=0.40",
                     "project":"flowedge","check":"unscoredRate=0.40","runIds":[…]}] }
```

三条约束：

1. **不自动登记**。诊断是规则推的，不是人确认的结论。自动往 registry 塞"机器猜的原因"会把它淹没，
   而 registry 一旦被淹没就没人看了——比没有更糟。
2. **不晋升**。晋升要过序策门禁，不在 FlowEdge 权限内。
3. **fail-open 但不假装成功**：序策没起时返回 503 + 完整 payload，调用方可直接重放补登记。

`hypothesis` 默认带「（规则诊断，待人工确认）」前缀——不让机器结论冒充人工结论。

### 10.5 这一步把 D4 从 2 推到哪

| 环节 | 状态 |
|---|---|
| 观测（聚合 N 条） | ✅ |
| 诊断（找最弱环节） | ✅ 规则 5 条 |
| 提候选 | ⚠️ **只有"把诊断变成 candidate"的通道，没有"改什么参数"的建议生成** |
| 评测（重跑对比） | ⚠️ 有 `rerun-from`，但没有一键"改前后各跑 K 次"的封装 |
| 判定（登记） | ✅ |
| 回滚 | ✅（`spec/apply` 快照 + 版本回滚） |

⇒ **D4 从 2 到约 3.5**：观测与诊断补齐了，登记通道通了，但"提出具体改动"和"自动跑对照"仍缺。
把它叫"闭环"是不诚实的——它现在是**半闭环：机器能告诉你哪里在漏，但还得人决定改什么**。

**未做**：前端没做诊断面板（现在只有 API）；`rerun-from` 未接入这个流程；候选生成未做。

## 十一、候选生成与一键试验：把 D4 补成闭环（2026-10-23 落地）

### 11.1 上一轮停在哪

§10 做到「观测 + 诊断 + 登记」，但缺「提出具体改什么」和「改完自动验证」。
所以 D4 只是半闭环——**机器能说哪里在漏，还得人决定改什么**。

这一轮补这两段。

### 11.2 候选生成的三条硬规矩

「让 AI 提议改参数」最容易做成噪音生成器。定死三条：

| 规矩 | 不遵守的后果 |
|---|---|
| **只提议有标准答案的参数** | 提议"把提示词写得更丰富"这类无法验证的改动，人试一次没效果就再也不看 |
| **`from` 必须从图里真读** | 猜当前值 → 提议看起来成立、应用时说值不对，信任直接崩 |
| **每条带预期指标 + 风险 + 依据** | 没有预期效果的改动不是候选，是折腾 |

**只收有行业标准的四项**（`candidateRules`）：

| 门检查匹配 | 参数 | 标准值 | 依据 |
|---|---|---|---|
| 响度 / loudness | `loudness` / `loudness_min_db` | **-14 LUFS** | 短视频平台基准，偏离会被二次压缩 |
| 静音 / silence | `max_silence_gap` | **0.5s** | 超过 0.5s 会被感知为卡顿 |
| 音轨 / audio | `require_audio` / `audio_muxed` | **true** | 曾有 `-map` 漏写产出纯视频而时长正常 |
| 人声 / speech | `forbid_speech` | **true** | 氛围片出现人声属硬伤 |

**图里没有这个键就不提议**——主动新增参数等于替用户做决定，且 `from` 无从核对。

`env_unstable` / `long_tail` 这类环境诊断**不产生改图候选**：那时改参数只会掩盖症状。
`pipeline_weak` 只给一条"先做结构检查"的只读建议。

### 11.3 一个真实的设计冲突，以及它为什么不是冲突

候选要调的参数（`loudness`/`fps`/`max_silence_gap`）**全部是门层参数**，
而 `spec/apply` 有一条硬拦：门参数默认禁止回写（§6.3 的 `gate_param_locked`）。

trial 第一版因此全部 403。但这不是 bug，是两套机制的边界正好咬合：

> **门锁的用意不是"永远不能改门"，是"改门必须留名"。**
> 候选的每一条都带 `Why`，传下去正好就是 `Reason`。

所以 trial 显式传 `AllowGateChange: true`，而**直接调 `/spec/apply` 时仍然拦着**——
这条有专门用例守着（`TestCandidate_ToSpecEditsCompatible` 先验被锁、再验授权后可应用）。

### 11.4 试验（trial）的四道关

```
① 校验   ApplySpecEdits（复用四条硬拦，dry-run 不落盘）
② 守卫   结构评分对比：改完不能从 Legal 变 Illegal → 否则 409
③ 快照   先存旧版本，再写新图（顺序反了就会出现"改了但没版本可回"）
④ 可选起跑 默认 false
```

**②是这一轮新增的守卫**：改参数不能把一张能跑的图改坏。之前只有 `spec/apply` 的字段级校验，
没有"整体可执行性"校验——那是图结构评分器给出的能力，这里复用。

**④默认不跑**：出片成本是分钟到小时级、占显存。"一键"该省的是复制粘贴与手工改图，
不是替你决定花 40 分钟渲染。想连跑就显式 `run: true`。

### 11.5 前端：诊断面板

顶栏「诊断」按钮 + 命令面板「运行诊断（哪里在漏）」。

- **主视觉是诊断卡片，不是评分仪表盘**——人不需要看 CR 曲线，需要知道下一步做什么
- 三数退到顶部次要位置，且 `crClean` 为 null 时显示「—」+ 提示「没有门样本」（不显示 100%）
- 候选区展示 `from → to`（`-20 → -14`），附依据 / 预期 / 风险
- 两个按钮分开：**只应用（不跑）** / **应用并重跑**

### 11.6 端到端实测（18092 临时实例，用完已清理）

构造 5 条带「响度」门失败的 evidence，跑完整链路：

```
① GET  /api/evidence/summary
   total=5 evidence=5
   [P1] gate_weak      wf=1 | 门检查「响度」在 5 次里失败 5 次（100%）
   [P1] pipeline_weak  wf=1 | 这条流水线 5 次里失败 5 次 —— 不是偶发

② POST /api/evidence/candidates
   候选：按标准对齐「响度」相关参数 | 置信 high
     pp.loudness  -20 → -14
     依据：短视频平台（抖音/视频号）普遍以 -14 LUFS 为基准…
     预期：audio 门通过率（loudness 项）
     风险：改后需重听一次，确认 BGM 没有被压过头

③ POST /api/evidence/trial  {"run": false}
   applied=1  快照版本=1  scoreBefore=0.850  scoreAfter=0.850

④ 验证
   GET /api/workflows/1        → post_production.loudness = -14      ✅ 已改
   GET /api/workflows/1/versions → v1 快照里 loudness = -20          ✅ 可回滚
```

### 11.7 D4 现在到哪

| 环节 | 状态 |
|---|---|
| 观测（聚合 N 条） | ✅ |
| 诊断（找最弱环节） | ✅ 规则 5 条 |
| **提候选（改什么参数）** | ✅ **有标准答案的 4 项，带依据/风险/预期** |
| **试验（改完验证）** | ✅ 校验 + 结构守卫 + 快照 + 可选起跑 |
| 判定（登记 registry） | ✅ |
| 回滚 | ✅ |

**D4: 2 → 约 4.0。** 还差的 1 分在哪：
- 候选只覆盖**有标准的参数**，prompt/模型/分镜权重这些真正影响质量的维度仍靠人
- 没有"改前后各跑 K 次 + 配对比较"的自动封装（现在是一次一跑，人看 summary）
- 没有自动闭环（诊断→候选→试验→再诊断的全自动循环，现在是人在中间点四步）

**未验证**：前端面板未做自动化测试（tsc 通过、81 个既有用例全绿，但没有渲染断言）；
诊断/候选/试验没有在真实出片任务上验证过（用构造的 evidence 验证的链路）。

## 十二、出片域经验卡片：把十年踩坑变成可检索的 30 条（2026-10-23 落地）

### 12.1 为什么先做这个

§8.2 里 D5（记忆与知识）= 2，是最弱的一维，也是唯一"不做就永远卡住"的一维：

- D4 已经能自己转（§10–§11）
- compose 可以被放弃
- 但**经验库不做，compose 做出来也是空壳**——生成的图结构对、创意平庸

而它有个别处没有的条件：**素材全在本地**。AGENTS.md 的 7 类坑、出片手册、MEMORY 的出片节、
skill 里的失败档案，都是已经付出代价换来的，只是没进引擎。

用户选的范围：**只收硬约束**（违反就出废片的），不收工具坑与判断失误史——后两者版本一变就过期，
且检索时噪声大（容易把"某次误判"当"通用规则"）。

### 12.2 资产形态：30 个 markdown，不是一整篇

`docs/出片硬约束/01-…md` ~ `30-…md`，每条一主题、100–250 字，结构固定：

```
# 标题（含关键词，便于检索命中）
**规则**：必须/禁止什么
**数值**：具体阈值
**为什么**：踩过什么（可验证的因果）
**验证**：怎么查
```

**为什么一条一文件**：RAG 按块检索，一篇长文档会被切成噪声块；一条一文件 + 语义化文件名，
`source` 就是天然的分类标签，检索出来人一眼知道该看哪条。

**分组**：响度 4 · 音画与帧数 5 · 静音与语音 4 · 混音与后期结构 6 · 场景一致性 4 · 字幕 3 · 画幅与时长 4。

### 12.3 导入：三个坑

| **JSON 里的 Windows 路径** | `files=0`，静默什么都不导 | `C:/Users/.../flowedge/docs` 里的 `\f` 是合法 JSON 转义（换页符），路径变成 `…\Desktop` + 换页 + `lowedge\docs`。**用正斜杠**（`cygpath -m`），Windows 接受 |

| **嵌入模型缺失** | 检索全是无关结果 | `bge-m3` 不在本地（只有 qwen2.5），会静默降级成词面哈希向量。必须 `ollama pull bge-m3`（1.1GB） |

**必须确认 `GET /api/kb/status` 的 `embedder` 是 `ollama` 而不是 `simple`** —— 降级不报错，
只是检索质量塌方，这是最难发现的一类降级。

## 十三、compose：一句话目标 → 可执行的图（2026-10-23 落地）

### 13.1 补的是哪半条腿

以前 FlowEdge 的 `spec` 只能「从图生成规格」（出口），**图本身必须人画**。
Raven 的 playbook、harness² 的 Compose 都指向同一个动作：**规格 → 图**。这里补上。

`POST /api/compose` → `service/compose.go`（约 330 行）+ 12 个用例。

### 13.2 与「让 LLM 随便画个图」的三条区别

| # | 做法 | 不做会怎样 |
|---|---|---|
| ① | 只给 LLM **模块目录**（29 行），不给整份契约 | 整份契约 6k+ 字，吃满上下文（CodeGraph 自曝的坑：少处理 token ≠ 少占窗口） |
| ② | 生成后用**确定性校验器**验伪（`ScoreGraph` + `PortKindAccepts`），违规**逐条回喂** | 只能靠 LLM 自检 = 没有人验 |
| ③ | **不自动 run、不自动存库** | 生成是提案，跑与存是决定 |

温度固定 0（`deterministicChat`）：构图是结构决策，不是创作。同一句话两次生成不同的图，评测就无从比较。

### 13.3 校验器补的一条守卫

`end`（`RoleSink`）是终点，**它后面不能再接节点**——接了那些节点永远不会执行。
`ScoreGraph` 原来只查"边两端存不存在、端口通不通"，不查这个。已补：

```
节点 "e" 是终点（end），它后面不能再接 "t2i" —— 那个节点永远不会执行
```

**诚实说明**：我最初是在标定输出里看到 `start→upscale→end→text2image` 才去查的，
但那是 **bench 脚本按节点数组顺序打印**的结果，不是拓扑顺序 —— 我误读了，校验器本来没漏。
这条守卫仍然保留（防御性，有测试 `TestCompose_NodeAfterEndRejected`），
但**不能把它写成"标定抓到的 bug"**。

### 13.4 标定：四轮调提示词，70–80%

控制：qwen2.5:14b（本机 Ollama）/ 温度 0 / 10 条中性目标（不绑具体业务）/ `maxRepairRounds=2`。

| 轮次 | 改动 | 合法率 | 首轮即合法 | 平均轮次 |
|---|---|---|---|---|
| 1 | 初版 | **8/10 (80%)** | 7 | 1.12 |
| 2 | 补 end-守卫 + 两条规则 | **8/10 (80%)** | 7 | 1.25 |
| 3 | 加 asr 专用 few-shot | **7/10 (70%)** | 5 | 1.43 |
| 4 | 撤 few-shot，改通用规则 | **7/10 (70%)** | 6 | 1.14 |

**稳定在 70–80%，平均 1.1–1.4 轮。** 结构分恒为 1.00（合法的图都是满分，因为评分器只认结构）。

### 13.5 三类失败，只有一类是提示词能救的

| 失败样本 | 现象 | 归因 |
|---|---|---|
| "转写一段录音并总结要点" | 反复尝试 `start(text)→asr(audio)` | **模型没有"孤立节点合法"的概念**：它认为不连线就是错 |
| "把横屏视频改成竖屏并加 BGM" | 反复尝试 `data_transform(text)→post_production(video)` | 同上 |
| "把长文本拆成 3 段分别配音" | 编造 `split_text` 类型，越改越乱（13 节点 + 成环） | **复杂图超出 14b 能力**（需要 loop + 扇出） |

**一轮 few-shot 反而更差**（70%）：给了 asr 专用例子后，模型只学会 asr 那一条，没有泛化到
upscale / post_production。撤掉例子改成通用规则后回到 70%，但首轮率回升（5→6）。

**结论**：`start` 只输出 text，而外部文件类输入（音频/图片/视频）需要一个**文件源模块**才能自然表达。
现在的绕法是"孤立节点 + `xxx_path` 参数"，这在引擎里合法（`inputCoveredByParam` 认它），
但**模型不知道这是合法的** —— 这是模型能力与模块设计共同造成的，不是提示词能单独解决的。

### 13.6 按纪律停手

AGENTS §0 的纪律：同类方法连试 ≤2 轮。提示词已调 4 轮（few-shot → 泛化 → 再泛化），
边际收益转为负（第 3 轮反而降 10pp）。**停下来记录，比继续磨提示词更有价值。**

### 13.7 这一步的判据达成情况

| 原定判据 | 结果 |
|---|---|
| 生成图必须过 `Modules` + `PortKindAccepts` 双校验 | ✅ |
| 违规回喂 LLM 最多 N 轮 | ✅（默认 2，上限 4） |
| **不自动 run** | ✅ 默认只返回 draft |
| 返回必带 spec | ✅ 返回带 `spec`（markdown 任务书）。实测一条 20 秒竖屏片：5 节点 → **1904 字符**任务书，含概览/显存侧分布/验收门 |
| 先跑 10 条 goal 标定 | ✅ 跑了 4 轮共 40 次 |

**全链路实测**（18094）：


**未做（诚实标注）**：
- 前端没有构图入口（只有 API）
- 复杂图（需要 loop + 扇出）14b 模型做不好
- 缺「文件源」模块：外部音频/图片/视频只能靠"孤立节点 + 参数"，模型不认这是合法写法

## 十四、文件源：补一个结构缺口（2026-10-23 落地）

### 14.1 不是"再加一个便利节点"

上一轮 §13.5 的结论是：**`start` 只输出 text，而 asr 吃 audio、upscale 吃 image、
post_production 吃 video**，于是「转写这段录音」这类目标在图上**根本无法表达**。

当时的绕法是让 asr 孤立站着、把路径塞进它的 `data.audio_path`。引擎认（`inputCoveredByParam`），
但标定里 3/10 条目标就是死在这 —— 模型反复硬连 `start(text)→asr(audio)`，
修 2 轮还是同一条错。**人和模型都认为"不连线就是画错了"**，这不是提示词能教的。

`input_source`（文件源）让"外部文件"变成一条正常的边：

```
转写录音      start(text) → input_source(kind=audio, path="待提供") → asr → llm → end
图片放大      input_source(kind=image, path="待提供") → upscale → end
横屏改竖屏    input_source(kind=video, path="待提供") → post_production → end
```

图的结构与直觉一致，不用再记一条例外规则。

### 14.2 四个输出端口**互斥**

| kind | 输出端口 | 可接 |
|---|---|---|
| `image` | `image` | 图生图 / 超分 / 视觉理解 / 局部重绘 |
| `audio` | `audio` | 语音转写 |
| `video` | `video` | 视频合成 / 后期 |
| `text` | `text` | LLM / 语音合成 / 提示词优化 |

运行时**只填 kind 对应的那一个键**，其余不出现。

**为什么不合成一个 `any` 端口**：`any` 会让下游的类型检查全部失效 ——
一个 mp4 的路径接到吃 audio 的节点上，静态检查放行，ffmpeg 跑到一半才炸。
**为什么四个都填同一个路径也不行**：audio 节点会拿到 mp4 路径，报一句与真实原因无关的错，
排查方向直接跑偏。

### 14.3 四条硬规矩（都有用例）

| 规矩 | 为什么 |
|---|---|
| **kind 留空按扩展名推断** | 填了 `.wav` 就是音频，让人再选一次只是多一个可以填错的地方 |
| **占位值单独报「还没给文件」** | 与"路径不存在"是两件事。后者会让人去查拼写，而真正该做的是补文件 |
| **声明类型与扩展名冲突 → 拒绝，不猜** | 猜错的代价是下游跑到一半才炸，那时错误已经离原因很远 |
| **相对路径转绝对** | 下游 ffmpeg/ASR 的工作目录不一定与引擎相同 |

占位值统一用「待提供」：图可以先搭起来，运行时明确报「文件源（audio）还是占位值 "待提供" ——
还没有指定实际文件」。

### 14.4 静态判据：不写节点类型字面量

新增 `exclusiveSourceConflict`（`graph_score.go`），判定依据是**契约形态**而不是类型名：

```
Role == source（无输入） + 输出端口多于一个 + 带 kind 参数
```

这正是"运行期按 kind 只输出一路"的定义。以后再有同类模块，自动被这条覆盖，不用改代码。

实测：

```
src(input_source:kind=image) → a(asr:audio)
  → legal=False
    「src(input_source:kind=image)→a(asr:audio)（这个源只输出 image，接不到 audio 端口）」
src(input_source:kind=image) → u(upscale:image)
  → legal=True
```

**只在 handle 非空时判**：空 handle 的语义是"随便接"，引擎运行期真的会自己找，
硬判会误伤（§8.2 那次把 5 条真实图判成端口冲突就是这个坑）。

### 14.5 标定：首轮合法率 6/10 → 8/8

同 10 条中性目标，qwen2.5:14b / 温度 0 / `maxRepairRounds=2`：

| 指标 | §13.4 第四轮 | 加文件源 | 再加回喂改进（§14.6） |
|---|---|---|---|
| 合法率 | 7/10 (70%) | 8/10 (80%) | **9/10 (90%)** |
| 首轮即合法 | 6/10 (60%) | **8/8 (100%)** | 8/9 (89%) |
| 平均轮次 | 1.14 | 1.00 | 1.11 |
| 需要外部文件的 4 条 | 反复失败 | **4/4 合法，且 4/4 正确用了 input_source** | 同左 |

第三列是**同一份提示词、只改回喂**的结果：#1（30 秒竖屏氛围短片）从"连错 3 轮、三轮的图一字不改"
变成**第 2 轮修对**（补上 `video_compose` 把图变成片，再进后期）。

**首轮 100% 是关键**：说明模型不再"试探式硬连"。它一次就把文件源摆对位置 ——
因为这本来就是它想画的样子。

剩余 2 条失败（与文件源无关）：

| 失败样本 | 现象 | 归因 |
|---|---|---|
| 30 秒竖屏氛围短片 | `text2image → post_production`，**连续 3 轮一字不改** | 见 §14.6，修复循环的缺陷 |
| 长文本拆 3 段配音 | 编造 `split_text` + 端口错乱（唯一剩下的失败） | **缺一个「文本拆分」模块** + 复杂图超 14b 能力。前者是真实缺口：`data_transform` 只能改结构，不能按语义切段 |

### 14.6 标定暴露的第二个缺陷：回喂只说"哪里错"，不说"怎么改"

第 1 条失败连错 3 轮，三轮的图**完全一样**。查回喂提示才发现：

```
## 上一版的问题（逐条修，不要重画整张）
- 第1轮：端口不兼容：t2i(text2image:image|json|text)→pp(post_production:video|audio)
```

两样东西都缺：

1. **没附上一版的图** —— 模型不知道要改哪条边，只能凭记忆重画（于是画出同一个）
2. **没说怎么修** —— "端口不兼容"是症状，不是处方

已补：回喂带上上一版 JSON（截断 2400 字）+ 一条修法指引（查上输出/下输入 → 中间补一步转换 →
不许靠删下游节点消错）。

**刻意只写元规则、不写具体节点链条**：§13.4 第三轮试过给 few-shot 示例，
模型把示例当模板套到底（只会了 asr 那一条，upscale/post_production 全不会），合法率反降 10pp。

**效果（同一份提示词，只改回喂）**：

| 用例 | 改前 | 改后 |
|---|---|---|
| 30 秒竖屏氛围短片 | FAIL，3 轮全同（`t2i→pp`） | **OK，第 2 轮修对**（`t2i→video_compose→pp`） |
| 合法率 | 8/10 | **9/10 (90%)** |

⇒ **"模型不听话"经常不是模型的问题，是回喂没有给它可操作的信息。**

## 十五、文本拆分与构图入口：把最后两处"点不到"补上（2026-10-23 下午）

### 15.1 `text_split`：一个被模型逼出来的模块

上一轮标定只剩一条失败：「把一段长文本拆成 3 段分别配音」。
模型每次都**编造一个不存在的 `split_text`**，改 2 轮还是在编。

查下来的根因不是模型蠢：`data_transform` 只能改结构（JSON 取字段、拼字符串），
**没有任何模块能把一段中文按语义切成几段**。模型想要这个能力，目录里没有，
它只能编一个名字出来。

`text_split`（第 34 个模块）四种切法：

| mode | 行为 | 典型用途 |
|---|---|---|
| `by_sentence` | 每句一段 | 逐句配音、逐句上字幕 |
| `by_paragraph` | 按空行；无空行退化为按行 | 剧本的「一句一行」排版 |
| `by_count` | 先按句切，再合并成 N 段 | 「拆成 3 段」 |
| `by_length` | 每段不超过 N 字，切点在句末 | 口播稿控制单条时长 |

输出：`text`（拼回全文）、`parts`（纯文本数组）、`count`、`chars`、`mode`。

### 15.2 三个必须做对的地方

**① 中文句号**。光看 ASCII 的 `.!?` 会把整段中文当成一句 —— 这是最常见的切分错误。
现在认 `。！？!?…` 与 `；;`，并且：

- 连续标点（`……！`、`？!`）算同一个句尾，不切成两句
- 句末紧跟的右引号/右括号留在句内（`他说：「走吧。」` 切不出「他说的」半句）
- **保留句末标点**：TTS 靠标点判停顿与语调，切完把句号扔掉会让每段听起来都像被突然掐断

**② `by_count` 从句子合并，不按字数硬切**。硬切会从句子中间下刀，某段以「他说」开头、
另一段以「我不同意」开头 —— 配音时听感是断的。现在保证切点永远在句末，并按字数均匀分配。

**③ 空文本当场失败**，不返回空数组。下游拿到空文本会一路跑下去（TTS 合成 0 秒、字幕空），
最后表现为「成片某段没声音」，而根因在最上游。这类静默故障最难查。

### 15.3 顺带发现的第二个问题：构图阶段不能用 `loop`

加上 `text_split` 后，#9 不再编造类型了 —— 它正确地画出了 `start → text_split → loop → tts → ...`。
但 **`loop` 在构图阶段是不可用的**：引擎的 loop 必须引用一条**已经存在的**工作流
（`data.workflow_id`），而生成时还没有这个 id，模型硬画的结果是**成环 + 端口错**（连错 3 轮）。

所以规则里加了一条明确禁令：

```
构图阶段不要用 loop：loop 必须引用一条已经存在的工作流（workflow_id），
现在还没有这个 id，画出来一定成环或端口错（已实测连错 3 轮）。
需要「逐段处理」时：把 text_split 的 parts 接给下游，或在节点数上限内顺序展开几个同类节点。
```

**这条不是提示词技巧，是引擎能力的真实边界**，所以同时写进了 `loop` 的契约 `Agent` 字段 ——
那样 compose、外部智能体、画布面板看到的是同一个说法，不会再有人（或模型）从别处学到一个错误的用法。

### 15.4 构图入口：从"只有 API"到"点得到"

`POST /api/compose` 落地后一直没有界面，等于能力不存在（这个项目已经踩过一次：
2026-10-21 盘点发现「5 个新能力全部 0 暴露」）。

顶栏新增 **构图**，面板做四件事：

| 区域 | 内容 |
|---|---|
| 输入 | 目标（越具体越准）+ 总时长 / 画幅 / 无台词 |
| 结果 | 合法徽章、节点数、**生成了几轮**、结构分 |
| 违规 | 生成过程中出现过的全部问题（模型靠什么修对的，人得看得见） |
| 出口 | **载入画布** / 直接保存 + 可展开的任务书 |

三个刻意的取舍：

- **没有任何"跑起来"的按钮**。生成是提案，出片是分钟到小时级。载入画布后跑不跑由人决定。
- **失败要露违规明细**。只说"生成失败"，人不知道该改目标措辞还是该补模块。
- **载入画布时清空 `currentWorkflowId`**。否则下一步「保存」会覆盖原来那条工作流 ——
  人在画布上看的是新图，存掉的却是旧图。这是最容易在演示时出丑的一类 bug。

面板有 6 个渲染用例：空目标不发请求 / 成功后显示轮次与任务书入口 / 不合法时不提供载入 /
载入时补齐边 id 并关闭面板 …

### 15.5 又一处"门没有牙齿"：`loop` 缺 `workflow_id` 却判满分

加上 `text_split` 后，#9 的画法变成 `start → text_split → loop → tts → subtitles → end`，
结构分给了 **1.00 / legal=true**。但它跑不起来 —— 执行器第一句就是：

```go
wfID := uint(dataInt(node.Data, "workflow_id", 0))
if wfID == 0 {
    return nil, fmt.Errorf("loop node has no workflow_id")
}
```

**契约里根本没声明 `workflow_id` 这个参数**（只有 mode / iterations / max_iterations / separator）。
于是：面板不显示这个字段（幸好面板是手写的，另有下拉）、任务书不写它、compose 不知道它需要。

这是"门没有牙齿"的第三种形态 —— 比"判不过"更糟：

| 形态 | 危害 |
|---|---|
| 门判不过但实际没问题 | 冤枉，浪费一次修订 |
| 门不检查关键项 | 漏网，问题在运行期才炸 |
| **门给满分但图跑不起来** | **人以为图是好的**，直到花了 40 分钟渲染才发现 |

修法两处：

1. **契约补 `workflow_id`**（带 Help 说明"必须是已保存的工作流"）—— 契约是单一事实源，
   执行器要读的参数必须在契约里出现，否则任务书与面板都会漏。
2. **compose 校验加一条**：契约里声明了 `workflow_id` 的模块，在构图阶段 data 里没有 id → 违规，
   并在错误里给替代方案（"把 text_split 的 parts 接给下游"）。

**判据用参数名而不是节点类型**（`kp.Key == "workflow_id"`），这样 `sub_workflow` 自动被同一条覆盖，
以后再有同类模块也不用改代码 —— 与"不写节点类型字面量"是同一条纪律。

修完 #9 变成 `start → text_split → llm → tts → subtitles → end`（第 2 轮修对，合法）。

### 15.6 标定：10 条目标只剩 1 条不稳定

同一套 10 条中性目标 / qwen2.5:14b / 温度 0 / `maxRepairRounds=2`：

| 版本 | 合法率 | 首轮即合法 | 编造类型 | #9 |
|---|---|---|---|---|
| §13.4 初版 | 7/10 | 6/10 | 有（`split_text`） | FAIL |
| + 文件源（§14.5） | 8/10 | 8/8 | 无（不用拆分） | FAIL |
| + 回喂改进（§14.6） | 9/10 | 8/9 | 无 | FAIL |
| + `text_split` + 规则 10 | 8/10 | 7/8 | **0 次** | FAIL（改用 loop 成环） |
| + 规则 11 + `workflow_id` 判据 | **10/10 (100%)** | **9/10** | 0 次 | **OK（第 2 轮）** |

最后一轮连跑 3 遍，三轮结果**逐条一致**（100% / 100% / 100%，首轮均 9/10）。

**一个方法论上的发现**：这个本机模型在温度 0 下是**确定性**的 ——
连跑 3 轮，10 条目标的结果与违规字符串**完全一致**（80%/80%/80%）。

这有两个后果：

- 好的一面：标定**可复现**，改一处 prompt 就能干净地归因。
- 坏的一面：**单条 prompt 的蝴蝶效应被放大**。加规则 10 后，与拆分毫无关系的 #4
  （"生成 4 张风格一致的图"）从 OK 变成 FAIL —— 仅仅因为 prompt 变长改变了模型注意力分布。
  所以判断一条规则是否该留，不能只看总合法率涨跌 1 条，要看**它针对的那条是否修好**
  以及**是否引入新的系统性错误**（比如编造类型、成环）。

剩余的那 1 条非首轮合法（有时是 #1 氛围短片，有时是 #3 文字转语音）属于 14b 的能力边界，
不是引擎缺陷 —— 记录在案，不再为它调提示词（AGENTS §0：同类方法不超过 2 轮）。

**标定纪律：必须单实例。** 有一次我在 18100 上跑标定，同时 18099 的实例还活着，
两个进程打同一个 Ollama（qwen2.5:14b 只有一份），耗时从 1–5 秒涨到 14–59 秒，
其中一条直接 120 秒超时 → 结果掉到 9/10。**环境竞争会伪装成模型能力问题**，
所以标定前要先确认没有第二个实例在跑（`netstat` 查端口，别只看 health 有没有返回）。
