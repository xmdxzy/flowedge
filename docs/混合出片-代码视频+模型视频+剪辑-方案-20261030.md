# 混合出片方案：代码视频 + 模型视频 + 剪辑（2026-10-30）

> 结论先行：**lemo 与 H3 不是竞争关系，是镜头级互补**。知识内容要「讲得准」（图表/数据/文字/结构图），
> 这是 H3 的死穴、lemo 的主场；情绪与实拍质感要 H3。FE 缺的不是渲染器，是
> **「镜头源选择 + 统一母版链」**。按本文分期做，vibe 知识片预计快 2–3×，且文字/数据 100% 准确。

---

## 一、三者定位（一句话各司其职）

| 层 | 谁 | 管什么 | 不吃什么 |
|---|---|---|---|
| 镜头源 A | **lemo `code_video`** | 确定性画面：图表、数据动效、关键词、章节卡、转场卡、片头片尾 | 不吃显存（无头浏览器 + ffmpeg，纯 CPU） |
| 镜头源 B | **H3 `text2video`**（现有） | 实拍质感、人物、氛围、动作、情绪镜头 | 画不出可读文字、数据不可控、每镜抽卡 2–7 分钟 |
| 镜头源 C | **已有素材 `clip`** | 用户上传/历史产物 | 需归一分辨率/fps/响度 |
| 编排 | **storyboard**（扩展） | 按「表达需求」给每镜分配 source + 风格 + 时长 | — |
| 装配/母版 | **shotlist 装配链 + 剪辑层**（扩展） | 时间轴、转场、统一响度、字幕合并、验收 | — |

**边界铁律**：lemo 不做「写实 footage」，H3 不做「要可读文字/精确数据的画面」。
越界即返工——这两条都在 FE 的历史坑里（flux 画字成笔画、H3 中文台词变伪中文）。

---

## 二、为什么现在能接（三方证据）

1. **lemo 是可参数化的命令行工具链**，不是黑盒：
   - 页面契约：`window.READY / render(t) / DUR / EV / TEXTS(t)`（`core/README.md`）
   - 渲染：`node core/render/video.mjs <demo> --fps 24 --workers N --out x.mp4`
   - 母版：`mux.sh video.mp4 mix.wav out.mp4`（两遍 loudnorm −14 LUFS / TP −1.2dB / grain）
   - 校验：`readcheck.mjs`（文字停留够不够读）、`srt.py`（cues→srt）
   - 每风格目录带 `style.json / STYLE.md / DEMO.md / demo/`（完整可跑源码 + `build.sh` 10 步），可反推模板
2. **FE 的剪辑/母版链已经比预想强**：`assembleShots`（xfade/acrossfade）、`masterLoudness`、
   `mixBGM`（duck）、`mixRoomTone`（−36dBFS 声床）、`alimiter`、`subtitles.go`（实测时间戳 srt）、
   `text_overlay`（libass 烧录）、plan 级一致性门、ASR 验词门。**缺的只是「混合的镜头源」这一环。**
3. **资源道天然可并行**：FE 队列已有 CPU 道（`cpuOnlyNodeTypes`，默认并发 2）与 GPU 道（默认 1）。
   lemo 走 CPU ⇒ 与 H3 抢显存的时代结束，**同一条片里 code 段和 gen 段可以同时跑**。
   （注意 lemo 自身有 `RENDER_SLOTS` 并发闸，需与 CPU 道统一，见 §七 风险 3。）

## 三、数据流（混合片怎么跑）

```
用户填 topic/outline/style
        │
        ▼
storyboard（LLM）→ ShotPlan: 每镜 {source: gen|code|clip, code_style, code_spec, seconds}
        │
        ├── source=gen  ──▶ text2video(H3, GPU 道) ──▶ 片段 A + 音轨
        ├── source=code ──▶ code_video(lemo, CPU 道) ──▶ 片段 B + 自带 mix
        └── source=clip ──▶ ffmpeg 归一 ──▶ 片段 C
        │            （A/B/C 并行，按资源道排队）
        ▼
edit/装配：按实际帧数排时间轴 → xfade/acrossfade → 统一响度一次 → 声床 → 字幕合并 → 烧录
        ▼
verify-media（帧数/音画差/静音/响度/ASR）+ readcheck（code 段文字停留）
```

**关键不变量**：时间轴按**实际帧数**排（lemo `DUR` 精确、H3 吸附 17k+5 网格），
不按声明秒数——这是 FE 已有教训（`-shortest` 让容器比视频流长 4 帧 ⇒ 整段画面丢失）。

## 四、镜头级契约（Shot 扩展字段）

`backend/service/shotplan.go` 的 `Shot` 增加：

```go
Source     string          `json:"source"`      // gen | code | clip，缺省 gen（向后兼容）
CodeStyle  string          `json:"code_style"`  // lemo 风格 slug：dataviz / briefing-board / dark-keynote …
CodeSpec   json.RawMessage `json:"code_spec"`   // 该镜要渲染的数据/文字/结构（图表数据、标题、要点）
ClipPath   string          `json:"clip_path"`   // source=clip 时的素材路径
```

兼容策略：缺省 `gen` ⇒ 现有 film 行为一字不变（`pipeline_test.go` 与现有 plan 全绿）。
`HasDialogue()` 对 code 段的语义：code 段若带台词，走 FE 的 TTS（不信 lemo 自带 TTS，除非显式指定）。

理由：写渲染脚本是代码生成任务，稳定性远低于「填模板字段」；先拿下 80% 的知识片型。

## 六、音频/字幕/母版统一规则（三个必踩陷阱）

1. **响度只能归一一次**：lemo `mux.sh` 已做两遍 loudnorm −14 LUFS。若 FE 再 `masterLoudness`，
   就是二次归一 → 动态被压扁、峰值乱跳。
   **约定**：lemo 侧只出「画面 + 未母版化 mix.wav」（或成品但标 `mastered=true` 跳过 FE 归一）。
2. **声床位置不变**：`mixRoomTone` 仍在 `masterLoudness` 之后、`mixBGM` 之前（AGENTS 已定案）。
   code 段的 `mix.wav` 若自带底噪，装配时按片段裁掉首尾静音再接声床，避免双底噪叠加。
3. **字幕单轨**：lemo 的 `TEXTS(t)` 输出的是「画面内文字」，FE 的 srt 是「对白字幕」——
   两者合并成一条轨但**分层**（画面文字不重复进字幕），否则观众看到两套字。

## 七、vibe 知识场景配方（60s 模板）

| 时间 | 内容 | 源 | 为什么 |
|---|---|---|---|
| 0–3s | 钩子大字卡 + 音效 | code | 秒级迭代文案，改十版不心疼 |
| 3–10s | 情绪/场景建立 | gen | 只有 H3 有实拍质感 |
| 10–40s | 主体讲解：图表/示意/关键词推进 | code + TTS | 数据准确、文字可读、卡点 |
| 40–52s | 案例/证据镜头 | gen 短镜 + code 数据卡交替 | 质感 + 精确数字 |
| 52–60s | 收尾字卡 + BGM 收束 | code | 确定性收口 |

**配比起点**：code 60% / gen 40%（24s code + 5 个 5s gen 镜）。按片子调，不照抄。

## 八、效率账（实测口径，不跨参数外推）

| 项 | 实测 | 来源 |
|---|---|---|
| lemo 1080p 1200 帧（50s）@workers2 | **≈30s 渲染**（CPU，零显存） | `styles/dataviz/demo/build.sh` 注释 |
| H3 608×352×124 帧 @12 步 | 冷 6.6min / 热 2m10s | AGENTS §0.16 |
| H3 单帧成本 | 0.85–0.93s/帧 | AGENTS §5.10 |
| 全 H3 60s 片（12 镜） | ≈ 80min | 按 6.6min/镜外推（含冷启动的最坏口径） |
| 混合 60s 片（5 gen + code 并行） | **≈ 25–35min** | 5 镜 H3 + code 并行，取得 2.3–3× |

**文字/数据准确性**：code 段 100%（确定性渲染），H3 段 0%（画不出可读文字）——这不是速度差，是能力差。

## 九、分期与验收

| 期 | 内容 | 验收判据 |
|---|---|---|
| **P0**（1–2 天） | `code_video` 节点 + 3 个知识向风格模板（dataviz / briefing-board / dark-keynote）+ `knowledge_film` 纯 code 流水线 | 一条 30s 知识片：渲染成功、readcheck 通过、`verify-media` 全绿、字幕可读 |
| **P1**（3–5 天） | Shot.source 混合 + CPU/GPU 并行调度 | 60s 混合片：code/gen 混排、帧数/音画差/静音全绿、墙钟 ≤35min |
| **P2**（1 周） | 剪辑层升级：章节卡/转场卡/音乐卡点/多轨字幕 | 转场卡渲染 ≤2s/个；音乐卡点误差 ≤1 帧 |
| **P3**（后置） | LLM 从零写渲染脚本 | 连续 3 条生成脚本可跑通且 readcheck 通过（不稳定则不发布） |

**P0 必须先做**：它单独就能交付「纯知识动画片」，且不碰 H3，风险最低、收益立竿见影。

## 十、风险与不做

| 风险 | 缓解 |
|---|---|
| LLM 写渲染脚本不稳定 | P0 只做模板参数化；P3 后置且要求连续 3 条通过 |
| 双母版响度冲突 | 单一母版点（§六），lemo 侧出未母版化音轨 |
| CPU 道并发 vs `RENDER_SLOTS` 冲突 | 统一信号量，二者取小 |
| 时间轴按声明秒数排 | 一律按实际帧数（已有铁律 §0.12 ⑤） |
| 风格素材版权 | lemo 是 MIT·CC BY 4.0；素材看 `CREDITS`，商用前核对 |

**不做**：实时预览、lemo 塞进 H3 批量构图（不同资源道，混批反而阻塞）、
把 code 段伪装成 gen 段（验收要能分辨来源）。

**与原方案的偏差（诚实记录）**：

1. **没有参数化 lemo 的 blueprint demo**：它的 `film.js` 27KB + `machine.js` 25KB 是「一部具体片子」的手写源码，
   不是模板。改为**自建知识卡渲染器**（复用蓝图视觉语言 + lemo 渲染链），这才对准知识片真正缺的部分。
2. **P0 只做了 blueprint 一个风格**（按你的选择），其余风格未接。
3. **H3 混排（`Shot.source`）未做**，是 P1；现在 code 段与 gen 段还不能在同一张分镜表里按镜分配。
4. **`tts_text` 旁白路径代码已通、未跑真实样本**（需要 Kokoro 服务在线）；默认出无声片，
   由剪辑层统一配音。这一点未验证，不当成已完成。

**用法**：

```bash
curl --noproxy '*' -X POST http://127.0.0.1:8080/api/produce \
  -H 'Content-Type: application/json' \
  -d '{"pipeline":"knowledge_film","params":{"title":"混合出片的三层结构",
       "points":"代码渲染讲准\n生成模型给质感\n剪辑层统一母版",
       "figure":"bars","labels":"H3,lemo,混合","values":"82,12,46",
       "duration":6},"invoked_by":"mcp"}'
```

多卡整卷填 `spec`（JSON，结构见 `codetpl/blueprint/spec.json`，`cards[]` 每卡含
`kicker/heading/points/figure/labels/values/note`）。

**改哪个参数能重跑**：`title / points / figure / labels / values / duration / width / height`；
改文案即秒级重渲——没有抽卡、没有节点缓存（重跑就是真重跑）。
