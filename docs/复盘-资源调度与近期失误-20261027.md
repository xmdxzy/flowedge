# FlowEdge 近期问题复盘 + 资源调度优化（2026-10-27）

> 结论先行：最近 24 小时 70 次运行里 **38 次失败（54%）**，失败运行累计白烧 **5.0 小时**墙钟。
> 失败主因不是模型不行，而是**调度层的四类错**：排队被当成在算、中止只管正在跑的那一层、
> 承诺过的事没实现、常数冒充基准。本次把调度层四处补齐（分道 / 可取消 / 状态如实 / 开跑前复判），
> 代码已落地、单测全绿；**真机 A/B 未做**，见 §4。

## 2. 失误清单（按「错在哪一层」分，不按时间）

### 2.1 承诺写在文案里，实现根本没写
- `shotlist.go` 报错文案承诺「已完成镜已落盘、重跑复用」，而 `reusedCount` 只初始化、从没被加过；
  `shot_jobs` 表建好了（`prompt_hash/seed/elapsed_ms/vram_peak_mb`）**0 行**。
  结果：一晚 6 次失败，每次从第 1 镜重烧。
- 判据未变：**「写了」不等于「做了」**。验收要落到「表里有行 / 计数 > 0 / 文件存在」。

### 2.2 中止只在最内层生效——两层都有洞，只修了一层
- 已修（10-26）：ComfyUI prompt 级——`/interrupt` 对**排队中**的 prompt 无效，改成「删 pending + 停 running + 复核」。
- **本次发现同一错还在上面一层**：`/runs/:id/cancel` → `EngineV2.CancelRun` 只查 `activeRuns`，
  **排在引擎队列里的运行一律 409「已结束或未在进行中」**。用户以为停了，20 分钟后照样开跑、照样烧卡。
- 规则：**「停」必须覆盖全部生命周期状态**（排队 / 执行 / 收尾），任何一层漏掉都等于没停。

### 2.3 把「排队」当「在算」——同一个错犯了两层
- 已修（10-26）：ComfyUI 侧看门狗从提交时刻计时，run 224 排队 6.1 分钟后被 5m35s 看门狗误杀。
- **本次发现引擎侧也在犯**：`produce.start` 在 `queue.Enqueue` **之前**就把 `job.status` 写成 `running`。
  于是「在队列里等 20 分钟」和「正在烧卡」在面板、看门狗、ETA 三处长得一模一样。
- 修法：入队即 `pending`，真正被调度起来那一刻由队列写 `running`（`queue.go: runOne`）。

### 2.4 常数冒充基准（三处）
| 常数 | 错法 | 后果 |
|---|---|---|
| `shotSecPerFrame=1.2` | 只对 608×352/12 步成立 | 768×448@20 步每镜都被「慢镜告警」误判，预算少给一半 |
| `vramAdvisoryReserveImageMB=2048` | 注释写「对齐 8188 `--reserve-vram 2`」，**实际 deps.json 是 1** | 前瞻差 1GB：本该报 `reserve` 的被算成 `ok`（假绿灯）|
| 节点超时 180s 固定 | 与工作量无关 | 合法长任务被误杀 |

### 2.5 预检只看数字，不看「谁占着」——两次同型误伤
- 第一次（10-26）：只看「空闲 < 模型体积」，把**热实例**（模型已在显存）判成装不下 → run 247 被 409 拦掉。
  修法 `AlreadyResidentForNodes`（已用显存 ≥ 需求 60% 即认定已驻留）。
- **第二次（本次）**：只看「空闲 < 模型体积」，把**自家队列正在跑的任务**判成外来占用 → 409。
  用户要等那条 20 分钟的片子跑完再手动重提。修法：自家占用 → 排队等待（开跑前复判）；外来进程 → 仍然开机前拦
  （外来占用不会自己消失，这是两者的分界）。

### 2.6 两个「平时好好的」
- `attachDepLog` 在持 `s.mu` 时再取同一把不可重入锁 → 永久死锁。症状极具误导：`/api/deps` 全卡、
  start 返回 202 却不派生进程，而 `/api/health`、`/api/runs` 正常（看起来像「H3 起不来」）。
- 进程重启 = 在跑任务全灭（6 条/24h），托管依赖（ComfyUI/ASR/TTS）被连带杀掉，恢复要重新 `deps start`。

### 2.7 作业方式（元失误，比 bug 更容易重犯）
1. **拿单例当归因**：先按显存算术断定「27 倍慢是 reserve-vram 4」，实测 reserve=0 后仍慢；
   直到读 ComfyUI 自己的日志才发现主因是 `--cache-none` 让每次提交重做 4 分 14 秒的模型 staging。
   ——「报错字符串/显存算术都不是根因」，日志里的 `Model Initializing 4:14` 才是。
2. **报「已验证」但只跑通、不开 A/B**：`low_vram` / `interp` 两个字段从未被节点读取，
   却报过「低显存模式验证成功」。新开关必须开/关各跑一次并打印实际生效值。
3. **跨参数外推估时**：拿 608×352 的 118s/段去推 736×416@20 步，还漏了插帧、LLM 分镜、实例启动。
4. **事后才想起文档**：本机已有 `docs/视频链路性能与队列卫生-20261026.md` 记着 reserve/cache-none 的实测，
   却先花时间做显存算术。**先查 `.workbuddy/memory/INDEX.md` + `docs/` 再动手**。

## 3. 本次改动（资源调度优化）

| # | 问题 | 改动 | 文件 |
|---|---|---|---|
| 1 | CPU 任务被 GPU 长任务堵住 | 队列按资源**分道**：GPU 道串行（默认 1），CPU 道并行（默认 2，`FLOWEDGE_QUEUE_CPU_CONCURRENCY`）；判类走白名单，认不出的节点一律 GPU | `service/queue.go`、`handler/produce.go`、`main.go` |

> **⚠️ 本条初稿的前提当天被真机推翻，结论已改**：初稿写「voice 的 TTS 已 `device=cpu`，所以它不再排在长片后面」。
> 2026-10-27 01:39 实测与另一处修改纠正了它——**Breeze TTS 2 的 fast streaming 是 CUDA-only**
> （CPU 上合成直接 `RuntimeError: fast streaming requires a CUDA device`，表现为 500 或直接超时），
> 而它常驻要吃 10–16GB：留在 CPU 道等于允许 voice 与 H3（20.5GB）并发，正好复现「H3 被挤成部分加载 → 12 分钟超时」。
> 因此 `cpuOnlyNodeTypes` 里**移除了 `tts`**，voice 仍走 GPU 道；分道机制保留，
> 但**当前没有真实的 CPU 类任务**，等换成能在 CPU 上跑的 TTS（如 Kokoro）再加回白名单。
> 教训同 §0.4：配置写着 `device=cpu` 不等于它真能跑在 CPU 上——要跑一次并看后端报错原文。

| 2 | 排队中的运行取消不了 | `JobQueue.Cancel(runID)` 从队列撤掉并标记 `interrupted`；`/runs/:id/cancel` 先试执行中、再试排队中 | `service/queue.go`、`handler/produce.go` |
| 3 | 排队冒充运行中 | 入队 `pending`，调度起跑才写 `running` + `started_at`；`RecoverInterrupted` 连 `pending` 一起回收 | `service/queue.go`、`handler/produce.go`、`service/run_service.go` |
| 4 | 显存预检误伤自家占用 | 自家 GPU 道在跑/排队时**不拦**，排队等待；开跑前复判（三次、间隔 2s，容忍 CUDA 异步释放），仍装不下才快速失败 | `handler/produce.go`、`service/vram_advisory.go` |
| 5 | reserve 常数与实际启动参数不符 | `vramAdvisoryReserveImageMB` 2048 → **1024**，并注明必须逐字对齐 `deps.json` | `service/vram_advisory.go` |
| 6 | 续跑留下永久 `running` 的僵尸 job、且续 voice 也占 GPU 道 | 续跑按节点判类入队；改为更新受理行而非再插一条 | `service/run_service.go` |

新增/更新的测试：`service/queue_class_test.go`（判类保守性 / CPU 道不被 GPU 挡 / CPU 道自己的上限 /
排队取消后绝不执行 / 取消正在跑返回 false / `HasGPUWork` 区分自家与外来 / pending 回收），
现有 `queue_test.go`、`queue_nonblocking_test.go`、`run_service` 相关用例保持绿。

顺带修掉一个真 bug：`wg.Done()` 在 `dispatch()` **之前**调用会让计数器短暂归零 →
`Wait()` 提前返回 → 下一条任务 `Add(1)` 触发 `WaitGroup is reused before previous Wait has returned` panic
（本轮测试实测踩到，已改为先补位再 Done）。

## 5. 下一步建议（按性价比排序）

1. **重启前 drain**：`3-应用更新并重启.bat` 先查 `/api/queue`，有在跑就等或明确提示，而不是直接停进程。
2. **队列可见**：面板显示 `QueueState`（pending/running × gpu/cpu），让「排队 20 分钟」和「卡死」分得开。
3. **短任务优先**：GPU 道内按预估成本做一次排序（voice 已分道，剩 image 61s vs film 20min 的场景），
   但要防饿死——先只做「同成本档内 FIFO」。
4. 把 §2.7 的四条元失误收敛成检查清单（新开关 A/B、先查文档、报区间不报单值）。

## 6. TTS 后端的最终决策（2026-10-27 08:00–08:25，实测定案）

### 6.1 三个候选的实测对比

| 候选 | 设备 | 实测速度 | 显存 | 能克隆 | 结论 |
|---|---|---|---|---|---|
| **Kokoro-82M** | CPU | **RTF 0.33–0.95**（19 字 → 5.58s 音频，1.85–4.8s 合成） | **0** | ✗（固定音色表） | **选它做默认** |
| Breeze TTS 2 | CPU | 跑不动：一句短台词 87s 预算超时、第二次 180s 节点超时 | 0 | ✓ | 否决 |
| Breeze TTS 2 | CUDA | 声称 RTF 0.66，但**在引擎托管的进程里起不来**：`Failed to set CUDA device device=cuda rank=0 … device_count=0`（同一 venv 手工跑 `torch.cuda.device_count()=1`） | 8–16GB，与 H3 的 20.5GB **不能共存** | ✓ | 只能作「克隆专用、手动模式」 |
| Audio8-TTS 0.6B | CUDA | RTF 7.9（默认）/18–32（克隆），58 字 ≈157s | 2.4GB | ✓ | 太慢，别用 |

**判据口味**：voice 是「一句话配音」，用户对 5 秒 vs 30 秒敏感；对「不能克隆」只在明确要克隆时才敏感。
所以默认必须选**快且不占显存**的 Kokoro；克隆是少数场景，值得为它付「切后端 + 腾卡」的手工代价。

### 6.2 为什么必须同时改引擎，而不是只换服务

只换服务不够。`execTTSNode` 原来无条件 `enterSide(sideAudio)`，而 `enterSide` 会：
1. 抢 `heavyMu`（全局只剩一个重节点在跑）→ 实测 voice 排在 image 后面**102 秒**才说完一句；
2. 换侧时 `releaseDiffusionAndWait` → 把**正在生成图**的 flux 卸掉，那个 image 任务当场
   `comfyui generation failed` 崩掉（2026-10-27 08:11 现场）。

改法（`engine_v2_nodes.go`）：CPU 上的 TTS **不进显存仲裁**（不抢 heavyMu、不逼别人让位）。
判据与队列共用 `ttsOnCPU()`（读 `deps.json` 的 `tts.device`），切换后端时两边自动一致。

  为什么同一个 venv 手工跑能看到卡、被引擎 spawn 后看不到（怀疑是父进程环境或 `windowsHide` 下的
  会话/桌面上下文差异）。在此之前，`ref_audio` 只会得到一句明确的 501。
- 含台词的 film：走的是 `SynthesizeDubTrack`（不经 tts 节点、不抢 heavyMu），Kokoro 在 CPU 上
  与 H3 共存没有显存冲突——**代码路径上成立，但没有跑一次带台词的 2 镜片做端到端验证**（成本约 6–7 分钟/镜）。
- 期间有**另一个会话在并发修改同一份配置**（08:05 我改成 Kokoro，08:1x 被改回 Breeze/CUDA，
  08:21 我又改回 Kokoro）。最终代码对两种配置都成立（`ttsOnCPU()` 自适应），但运维上必须一个人说了算。
